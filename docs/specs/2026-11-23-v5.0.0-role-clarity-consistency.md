## 1. 背景与目标（what & why）

ship-it 经 v4.7.0/4.7.1/4.7.2 三轮治理已建立"状态+证据"闸门，但仍存三类残余问题制约"项目可控"：模糊判据未机器化、角色身份失焦（无名无身份、三名含"审查"易混）、前后矛盾检测有缺口（角色名/通用区间/跨文件硬属性无校验）。

目标：不改 9 步骨架与监督分离，把模糊判据换成可核验检查单、给 8 角色赋专业身份并完成 2 个改名、把前后矛盾检测机器化，使 ship-it 从"跑得对"升级为"每个角色是谁/干什么/前后不矛盾都可机器核验"的可控流程。

## 5. 契约条款（C1 / C2 / …）

### C1 角色改名：审查员→监察员

- **前置条件**：team-mode.md / SKILL.md / README.md / deploy-runbook.md / check_roles.py 存在。
- **后置条件**：正文范围"审查员"全部替换为"监察员"（实测 158 处：SKILL.md 28 + team-mode.md 109 + README.md 8 + deploy-runbook.md 13）；check_roles.py 4 处字符串同步；角色卡标题改为"### 监察员（异常与偷懒审查）"；能力表/矩阵/失败处理表/信息流图同步。
- **失败行为**：正文范围残留"审查员"（非历史 CHANGELOG/历史 spec）→ check_terms.py FAIL。
- **不变式**：监察员职责/闸门/生命周期/C14/C15/C16/C17 机制全部保留，只改名字；历史记录不改写。

### C2 角色改名：需求澄清员→需求分析师

- **前置条件**：同 C1。
- **后置条件**：正文范围"需求澄清员"全部替换为"需求分析师"（实测 12 处：SKILL.md 4 + team-mode.md 7 + README.md 1）；角色卡标题改为"### 需求分析师"。
- **失败行为**：正文范围残留"需求澄清员"（非历史）→ check_terms.py FAIL。
- **不变式**：需求分析师职责/闸门保留，只改名字；历史记录不改写。

### C3 8 角色身份赋予（角色卡顶部加"身份"字段）

- **前置条件**：8 张角色卡存在于 team-mode.md。
- **后置条件**：每张角色卡在"### 角色名"标题下、"职责"字段前新增一行"**身份**：一句话身份赋予"。8 个身份：主脑=项目负责人与技术总指挥；需求分析师=需求分析师；后端开发=后端工程师；前端开发=前端工程师；代码安全员=代码审查与安全工程师；监察员=过程监察与调度督导；测试员=验收测试工程师；裁判员=契约合规审计师。
- **失败行为**：任一角色卡缺"身份"字段 → check_docs.py FAIL。
- **不变式**：身份字段位于角色卡顶部，与现有"职责/输入/输出/能力要求/形态/闸门"字段并列，不取代任何现有字段。

### C4 主脑派发措辞优化

- **前置条件**：主脑角色卡"职责"含"统一派发所有 subagent"；派发规则含同句。
- **后置条件**：改为"统一创建与管理所有团队成员（一次性 subagent 用 subagent/subagent_fork/workflow，持久 teammate 用 spawn_teammate）；teammate 缺工具时由主脑代派其所需的一次性 subagent"。派发规则同步更新。
- **失败行为**：残留"统一派发所有 subagent"（无"创建与管理"限定）→ check_docs.py FAIL。
- **不变式**：派发决策规则（默认优先+动态挑选）不变，只改措辞消除一次性 vs 常驻误会。

### C5 监察员形态字段澄清

- **前置条件**：监察员角色卡"形态"字段为"subagent（异常时深度审查…）"。
- **后置条件**：形态字段改为"持久 teammate 常驻巡视（宿主不支持时降级为事件触发 subagent）"。
- **失败行为**：形态字段未体现"持久 teammate 常驻"首选 → check_docs.py 角色硬属性检测 FAIL。
- **不变式**：巡视间隔（默认 1 分钟）、契约生命周期（不得主动结束）不变，只改形态字段表述。

### C6 需求分析师形态升级

- **前置条件**：需求分析师角色卡"形态"为"subagent（一次性，主脑统一派发）"。
- **后置条件**：形态改为"优先持久 teammate（复杂/多轮澄清时）；简单澄清降级为一次性 subagent"。
- **失败行为**：形态字段未体现"优先持久 teammate" → check_docs.py 角色硬属性检测 FAIL。
- **不变式**："不直接面对用户"闸门保留；形态升级只为支撑分轮追问，不改职责边界。

  2. **派发前查 list_agents 含监察员 running 校验**：主脑每次派发 subagent/teammate 前，必须调用 list_agents，且确认监察员状态为 running（若 inactive 先唤醒）。脚本通过 patrol log 的派发记录核对主脑派发时点是否有对应的 list_agents 调用与监察员 running 确认。
- **失败行为**：监察员 inactive 超阈值，或主脑派发前未查 list_agents/未确认监察员 running → check_roles.py FAIL。
- **不变式**：只校验能机器化的两项；信息流主脑不直接对接下游属行为约束，由 C33 三查 + 监察员巡视 + 裁判员 J2/J3 审计保障；本条是 C5 + C33 的机器闸门落地。
- **watchdog_daemon.py**：独立常驻后台程序（不依赖 subagent 唤醒），每 N 秒机械巡视：查 list_agents 状态、查产出落盘、查超时、追加 patrol log、监察员 inactive 超阈值报警。只做机械检查，分析判断仍归监察员 subagent。
### C35 主脑汇报降噪（等待静默，有实质结果才汇报）

- **前置条件**：主脑在等待下游角色（wait_agent）期间。
- **后置条件**：
  1. **有实质进展时汇报**：角色完成、测试结果、需用户决策、发现问题时立即汇报。
  2. **纯等待时静默**：角色还在运行、无新结果时不得汇报"还在等""继续等"等噪音；安静等待。
  3. **长时间无果时简短状态**：等待超过较长时间仍无结果，最多一句状态（在等谁/多久/下一步），不说废话。
  4. **不重复催用户**：同一内容（如签约确认）只说一次，不得反复催促；用户未回复时安静等待，不重复发送相同请求。
  5. **只给必要更新**：只汇报有新信息或有变化的更新，相同内容不重复发；用户已知晓的状态不重述。
  4. 不每分钟/每轮发噪音；与 C27（需要你段灵活省略不写空话）+ C14（不复述流程）一致。
- **失败行为**：主脑在纯等待期间频繁发噪音汇报 → 违反 C14 去机器感，监察员巡视判定提醒。
- **不变式**：本条强化 C27 的"不打扰"精神；汇报价值密度优先于频率；有结果才说，没结果不说。
