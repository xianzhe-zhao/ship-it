## 1. 背景与目标（what & why）

**现状**：ship-it 团队模式已有 6 个角色（需求澄清员 / 后端开发 / 前端开发 / 代码审查员 / 测试员 / 改动说明员），但缺三类能力：

1. **运行期异常与偷懒没有分诊层**：子代理报错、超时、空产出、只回元信息、产出不可追溯条款、明显偷懒时，主脑要么直接重派、要么自己做，没有统一的失败分类、优先级判断、重试计数与升级路径；「反复尝试仍失败」没有可核销的阈值。
2. **规则符合性没有独立检查层**：主脑可能在子代理结论未返回或只返回部分结论时就推进下一步；可能自判核销通过、自判验收通过；子代理可能超出文件作用域、跳过自检、只回元信息、伪造测试结果。现有「代码审查员」只审代码内容四项，不审「角色是否按规则工作」。
3. **角色命名与中间层问题**：原「代码审查员」与新增「审查员」撞名；「改动说明员」只起草报告，主脑仍需汇总并最终负责，属可删除的中间层。

**为什么要改**：用户明确要求——① **删除改动说明员**：主脑获取并总结团队内容后直接向用户汇报；② 原「代码审查员」改名 **代码安全员**：负责**代码审查（正确性/质量/注释/重复功能）+ 安全检查（安全漏洞/依赖/权限/敏感信息/安全相关重复接口）**；**测试员只做验收测试**；代码安全员在团队模式下**必须执行**；③ 新增 **审查员**：审查子智能体是否偷懒、鞭策重试、异常上报；④ 新增 **裁判员**：读取限制条件、agent 目录、rules 规定与用户限制，检查每个角色是否按主脑要求工作，防止主脑偏移/偷懒与子代理越权/偷懒，在关键节点把流程拉回规则并最终确认契约完成度。

**改完是什么样**：团队模式 **8 个角色**（主脑 / 需求澄清员 / 后端开发 / 前端开发 / 代码安全员 / 审查员 / 裁判员 / 测试员），删除改动说明员；代码安全员在团队模式必须执行；审查员在子代理返回/异常时产出「分诊单」，并**默认每 1 分钟主动巡视所有成员（含主脑 / 裁判员 / 代码安全员 / 测试员 / 开发）**，主脑不轮询审查员；同一任务最多自动重试 2 次（共 3 次尝试），第 3 次失败带证据与尝试次数上报主脑，由主脑在封闭决策集内决定换模型重派、换方式重派、基于已有产出续派、主脑自做或报用户；裁判员在 4 个检查点产出「裁判单」，有 BLOCK 权（阻断进入下一步），但 PASS **不替代**用户验收与 `check_spec.py` 机器校验；Step 6 五项报告由主脑汇总团队产出后起草；9 步流程、核销、用户验收语义不变。

### 需求澄清记录（Step 1 产出，签约时展示给用户确认）

- **原始需求**（用户原话要点）：
  1. 「添加审查员机制：当子智能体报错或出现异常时，审查员查看报错内容并判断优先级。若可直接重试或继续，则向子智能体下达继续或重试的指令；若反复尝试仍失败，则将报错信息及尝试次数上报主脑。主脑判断后，重新发起新的智能体，或基于原有内容对未完成部分继续派发任务，派发时可更换模型或调整方式。审查员直接向主脑汇报，仅负责审查和汇总，不干涉主脑的决定。审查员还需审查子智能体和主脑的后台，并及时反馈给主脑。」
  2. 「增设裁判员，检查每个角色是否按照主脑的要求工作。与审查员不同，裁判员负责防止主脑在未等待子智能体结论或部分结论时产生偏移或偷懒的迹象，同时防止子智能体越权或偷懒。裁判员还需读取限制条件、agent目录、rules规定以及问题发起者（即用户）提出的限制条件或规则，并确保严格遵守。最终由裁判员确认契约是否已完成、是否按要求制定计划或内容。如果主脑和子智能体发生偏移或者不符合裁判的规则的时候，由裁判员拉回正确的规则中，报给主脑。总之，裁判员是规则的检查者。」
- **优化后需求（可执行版）**：
  - **R1 异常与偷懒分诊**：新增只读角色「审查员（异常与偷懒审查）」，在子代理失败/超时/空产出/仅元信息/产出不可追溯条款/工具被拒/上下文超限/明显偷懒/主脑怀疑偏移时触发；输出结构化分诊单（失败分类 + 严重度 + 证据 + 处置建议枚举）。**可直接向子代理下达 `continue` / `retry_same` 指令**（同任务、同条件）；**换模型 / 换 prompt / 缩范围 / 新派发 / 续派剩余部分必须交主脑决定**；审查员不干涉主脑决定。
  - **R2 升级阈值**：同一任务**初次尝试 + 最多 2 次自动重试 = 共 3 次尝试**；第 3 次尝试仍失败 → 必须上报主脑并附尝试次数、报错原文、已试方案；总尝试 ≤3；主脑决策集封闭为 {换模型重派 / 换 prompt 或缩范围重派 / 基于已有产出续派剩余部分 / 主脑自做 / 报用户}，决策写入当步汇报与任务树/看板。
  - **R3 规则裁判**：新增只读角色「裁判员」，在 4 个检查点（J1 签约前 / J2 编码后 / J3 核销前 / J4 验收前）核对「角色是否按 spec 与用户约束工作」，输出结构化裁判单；发现偏移 → 拉回（BLOCK 或 DEVIATION）+ 报主脑。
  - **R4 裁定边界**：裁判员有 **BLOCK 权（阻断进入下一步）**，但 **PASS 不替代用户验收与 `check_spec.py`**；主脑不得自行推翻 BLOCK，只能修正或取得用户显式批准并记入 spec；裁判员不是最终裁定者。
  - **R5 证据口径**：「审查后台」降级为「主脑证据包 + 仓库落地物（spec / git diff / 报告文件 / 任务树快照 / 共享看板）」；报告中必须写明可见性口径，**禁止声称审查了不可见对象**。
  - **R6 代码安全员必执行 + 主脑汇总**：原「代码审查员」改名「代码安全员」，团队模式形态 1–3 必须派；职责 = **代码审查（正确性/质量/注释/重复功能）+ 安全检查（安全漏洞/依赖/权限/敏感信息/安全相关重复接口）**；**测试员只做验收测试**；删除「改动说明员」；Step 6 五项报告由主脑汇总团队产出（安全报告/测试报告/裁判单/核销表）后起草，裁判员 J4 只审合规、不代写。
- **优化说明**：① 把用户口语化的「看报错、判优先级、下指令、反复失败上报」翻译为可核销的失败分类枚举、严重度枚举、尝试计数与封闭决策集；② 把「审查后台」按本宿主实际能力降级为证据包 + 仓库落地物，并强制声明可见性口径；③ 把「裁判员最终确认契约」收敛为「规则一致性审计 + BLOCK 权」，避免与「执行者 ≠ 裁定者」和用户验收冲突；④ 按用户裁定：删除改动说明员、原代码审查员改名代码安全员并设为团队模式必执行、审查员负责异常与偷懒/重试/上报，消除「审查员 vs 代码审查员」撞名；⑤ 本次改动属 skill 规则变更，按反偷懒红线 #2 走完整 spec，不走 mini-spec / 纯文档免流程。
- **用户问答**：本会话 `ask_user_question` 返回 `no user-questions answerer accepted the request`（宿主未配置问答应答器，never-ask 模式下无法交互提问）。因此按用户「现在就用这个模式尝试更新该代码」「继续」的明确推进指令，采用以下 6 项推荐决策执行，并在 Step 6 验收时请用户逐条否决/确认：
  1. 改动范围：只改本仓库 ship-it skill，不碰 DSH 宿主配置或其他仓库。
  2. 角色关系（按用户 2026-11-18 裁定更新）：新增「审查员（异常与偷懒审查）」与「裁判员」；原「代码审查员」改名「代码安全员」并设为团队模式必执行；**删除「改动说明员」**，Step 6 五项报告由主脑汇总团队产出后起草。
  3. 审查员触发：主脑对每个子代理返回做一次轻量分诊（可内联）；命中异常才派审查员深度审查；同一任务初次 + 最多 2 次自动重试 = 共 3 次尝试，第 3 次失败上报。
  4. 裁判员权限：4 个检查点 + BLOCK 权；PASS 不替代用户验收与机器校验；争议交用户。
  5. 证据来源：主脑证据包 + 裁判员自读仓库/spec/任务树/看板；不读会话日志与凭据。
  6. 本次执行：团队模式 + 目标树 + dogfood 新角色。

## 5. 契约条款（C1 / C2 / …）

### C1 角色分工、改名与删除改动说明员

- **前置条件**：团队模式启用；现有角色表有「代码审查员」与「改动说明员」。
- **后置条件**：`team-mode.md` 角色表/角色卡调整为 **8 个角色**——主脑 / 需求澄清员 / 后端开发 / 前端开发 / **代码安全员** / **审查员（异常与偷懒审查）** / **裁判员** / 测试员；**删除「改动说明员」**。分工：
  - **主脑**：只派活、决策、对用户交付；**不亲自开发/测试/审代码**；所有下游回报经**审查员**汇总；不直接等裁判员。
  - **审查员**：**审查员是主脑唯一汇总接口**；实时巡视所有成员状态/回复，收集开发、测试员、代码安全员、裁判员的报告，整理给主脑判断；可直发 `continue`/`retry_same`，换模型/换范围/新派发交主脑；不审代码、不做测试；**优先具备图像输入能力**，收到图片/截图时报告主脑，由主脑决定是否派临时识图子智能体。
  - **测试员**：**只做验收测试**（按 spec + `design.md` / 后端标准 / 数据库标准），执行测试、找问题、给更正建议；**不审代码、不做安全检查**；测试执行权归测试员。
  - **代码安全员**：负责**代码审查**（正确性 / 质量 / 注释 / 重复功能）+ **安全检查**（安全漏洞/依赖/权限/敏感信息/安全相关重复接口）；测试员不审代码；问题 → 告审查员 → 汇总主脑 → 开发修 → 再测试/再安全检查，循环。
  - **裁判员**：**不执行测试、不审代码**；在**测试员验收测试 + 代码安全员审查/安全检查都通过后**审契约符合性，并核查安全检查是否通过（防主脑偷懒）；裁判单报审查员汇总。
  - **前端开发**：有 `design.md` 必须遵循；无 `design.md` → 主脑询问是否建立标准（首次使用/新项目必须问），否则按用户经验总结规范并记录。
  - **后端开发**：遵循后端标准 + 数据库标准（项目文档/`design.md`/runbook）；无标准 → 询问/总结并记录。
  - **前后端开发**：按主脑派活开发/修代码，接收测试员/代码安全员/审查员反馈，循环至测试+审查/安全通过。
  - 命名消歧：单写「审查员」= 异常/偷懒审查角色；安全职责一律写「代码安全员」；skill 正文范围（SKILL.md / team-mode.md / README.md / runbook / spec-template.md）内同步，历史 CHANGELOG / 历史 spec 不改写。
- **失败行为**：残留改动说明员 / 角色表仍 9 个 / 代码安全员被降为可选 / 裁判员审代码或跑测试 / 主脑直接等裁判员 / 测试员审代码 → 校验 FAIL，退回补正。
- **不变式**：主脑仍是唯一对用户交付者与决策者；审查员只汇总不决策；代码安全员不承担异常处置；裁判员不审代码、不测试、不审技术方案优劣。

### C2 审查员触发条件与失败分类

- **前置条件**：任一子代理返回（正常/失败/超时/空产出/仅元信息/产出不可追溯条款/工具被拒/上下文超限/明显偷懒），或主脑告知/证据包显示后台异常，或主脑怀疑偏移。
- **后置条件**：**主脑对每个返回做一次轻量分诊（可内联）**；命中异常/偷懒特征时才派审查员做深度审查；失败分类必须落入固定枚举：`dispatch_failed`、`timeout`、`empty_output`、`meta_only`、`unreachable_clause`、`tool_denied`、`context_overflow`、`laziness`、`suspected_drift`；严重度取 `P0`（阻断且无法继续）/`P1`（可重试或降级）/`P2`（可继续但需记录）；分类决定建议动作，不得跳过分类直接给结论。
- **失败行为**：无法分类 → 归入 `suspected_drift` 并标 P1，要求主脑补证据；审查员编造分类/证据 → 报告作废并记违规。
- **不变式**：分类与严重度枚举不得随意扩张；新增枚举须先改 spec。

### C3 审查员输出、只读与指令边界

- **前置条件**：审查员完成审查。
- **后置条件**：输出结构化「分诊单」，字段固定：`task`（任务/派发轮次）、`attempt`（1–3）、`failure_class`、`severity`、`evidence`（错误原文摘录或 `path:line` 或命令+退出码）、`recommended`（`continue` / `retry_same` / `retry_with_changes(model|prompt|scope)` / `main_do` / `escalate_user`）、`reason`、只读声明；审查员**只读文件/代码/spec/任务树**，但**可直接向子代理发送 `continue` / `retry_same` 指令，以及 `question`（仅质疑/澄清，不含新范围/模型）**（同任务、同条件；DSH `send_message` 支持同树任意成员）；**换模型 / 换 prompt / 缩范围 / 新派发 / 续派剩余部分不得由审查员直接执行**，必须交主脑；向主脑汇报不受「不直接下令」限制。
- **失败行为**：审查员越权写文件/改 spec、直接对用户下结论、或直接执行换模型/换范围/新派发 → 报告作废，主脑记违规并重派；缺只读声明或证据字段 → 退回补全。
- **不变式**：审查员只审不裁；`continue`/`retry_same` 之外的处置、换模型、换方式、拆任务、自做，均由主脑决定；审查员报告原文由主脑保存，可附入汇报但不得篡改。
- **建议/决策映射**：`continue` → 审查员直发（同任务同条件），主脑记录不重派；`retry_same` → 审查员直发（同模型同 prompt），主脑记录；`retry_with_changes(model)` → 主脑决策①；`retry_with_changes(prompt|scope)` → 主脑决策②；`main_do` → 主脑决策④；`escalate_user` → 主脑决策⑤；续派剩余部分 → 主脑决策③（由主脑基于已有产出选择，审查员不直接执行）。

### C4 审查员升级阈值与尝试计数

- **前置条件**：同一任务出现执行失败或异常。
- **后置条件**：同一任务**初次尝试 + 最多 2 次自动重试 = 共 3 次尝试**；第 3 次尝试仍失败 → 必须上报主脑，报告含报错原文、尝试次数、已试方案、建议；总尝试 ≤3；尝试计数以分诊单 `attempt` 序号为准，由主脑持有并写入证据包；换模型/换 prompt/缩范围算新尝试但仍计入同一任务；**不得**用汇报次数、重试按钮次数或时间窗口替代尝试计数。同一 `failure_class` 重复 2 次也应提前上报（不必等满 3 次）。
- **失败行为**：达到阈值未上报 → 裁判员 J2/J3 判 DEVIATION；超过 3 次仍自动重试 → 违规，停止并报用户。
- **不变式**：审查员不自行决定第 4 次尝试；主脑的决策必须留痕（汇报 + 任务树/看板）。

### C5 主脑决策集与重派/续派规则

- **前置条件**：审查员上报失败或异常（含第 3 次尝试失败）。
- **后置条件**：主脑在封闭决策集内选一：① 换模型重派；② 换 prompt / 缩范围重派；③ 基于已有产出续派剩余部分（必须带已有产出路径 + 剩余范围）；④ 主脑自做；⑤ 报用户。决策写入当步汇报与任务树/看板；**派发失败**（权限/模型路由/工具缺失，重派必白跑）仍按反越权红线 #6 直接主脑自做；**执行失败**（已跑但报错/超时/空产出）允许按本条款重派或续派，但受 C4 尝试上限约束。**审计角色例外**：审查员/裁判员本身是只读审计角色，其派发失败不适用「主脑自做」——审查员失败由主脑内联并声明「无独立审查」；裁判员失败按 C12 换新 subagent/`workflow`，仍失败报用户，**不得自判 PASS**。
- **失败行为**：主脑无记录地重复原样重派、或把执行失败误判为派发失败绕过重试、或超过尝试上限、或对裁判员失败自判 PASS → 裁判员判 DEVIATION/BLOCK。
- **不变式**：重派/续派不得改变 spec 条款与验收标准；续派必须保留已有产出，不从头重做；派发失败与执行失败的区分、审计角色例外必须显式写入汇报。

### C6 裁判员规则源与检查点

- **前置条件**：团队模式启用；裁判员被派发。
- **后置条件**：裁判员按优先级读取规则源：① 用户本轮明确指令/限制（**主脑摘录进 spec §1 用户约束或证据包**；裁判员不读会话日志）；② 项目规则：本仓库根**无** `AGENTS.md` / `CLAUDE.md`，`.agents/` 无规则文件，规则以 `docs/deploy-runbook.md`（系统形态/部署通道/核心功能清单/服务红线）为准；③ 全局 `~/.dsh/AGENTS.md`；④ skill 正文（SKILL.md / team-mode.md）；⑤ spec 契约；⑥ 任务树/共享看板快照。**agent 目录**：本机 `~/.dsh` 下无 `agents/` 目录，`~/.agents/skills/` 是 skill 目录而非 agent 预设；裁判员按宿主实际存在路径读取，不存在则记录「未找到」，不得编造。检查点为 J1 签约前（Step 2 末）、J2 编码后（Step 3 末，**流程/文档/自检审计，不审代码**；代码审查+安全检查归代码安全员，测试员只做验收测试；J2 PASS 后主脑才进 Step 4）、J3 核销前（Step 4 末/Step 5 前）、J4 验收前（Step 5 末/Step 6 前）；J4 结论在 Step 7 复用，若 Step 6 后有任何代码/spec 变更必须重跑 J4。
- **失败行为**：裁判员未读规则原文、只凭主脑转述、或编造规则 → 裁判单无效；规则源缺失未记录「未找到」→ 退回补全。
- **不变式**：裁判员只读；规则源优先级不得颠倒；裁判员不审技术方案优劣与代码质量。

### C7 裁判员输出与效力

- **前置条件**：裁判员完成某个检查点。
- **后置条件**：输出结构化「裁判单」，字段固定：`checkpoint`（J1–J4）、`rules_source`（每条含路径/条款号）、`checks`（每条 `{rule_id, status: pass|deviation|na, evidence}`）、`verdict`（`PASS` / `DEVIATION` / `BLOCK`）、`required_action`、非最终裁定声明；`BLOCK` → 主脑不得进入下一步，须修正或取得用户显式批准（批准记入 spec §1，属受保护变更）；同一检查点 BLOCK ≤2 轮，超 2 轮停止循环报用户；`PASS` **不替代**用户验收与 `check_spec.py`。
- **失败行为**：主脑自行推翻 BLOCK 且无用户批准 → 违规；裁判员无证据 PASS/BLOCK → 裁判单无效；裁判员直接改代码/spec/任务树 → 越权，报告作废。
- **不变式**：裁判员报告原文由主脑附入汇报，主脑可回应但不得删除/篡改；最终裁定仍是用户验收 + 机器校验 + 机器可读任务状态；裁判员不是最终裁定者。

### C8 证据口径与后台可见性声明

- **前置条件**：审查员/裁判员出具任何结论。
- **后置条件**：每条 deviation/BLOCK 必须有 `path:line` 或「命令 + 退出码」或错误原文摘录；后台审查必须写明「后台可见性：完整 / 降级 / 不可见」；DSH 下默认写「降级」并说明证据包范围（报错原文、退出码、耗时、job 状态、任务树快照、派发记录、diff、测试报告）；证据不足 → 标 `evidence_missing`，要求主脑补齐，不得凭空判定；**禁止声称审查了不可见对象**。
- **失败行为**：无证据 PASS/BLOCK、或声称审查了主脑会话日志/后台 job 但无证据 → 报告作废，裁判员 J2/J3/J4 判 DEVIATION。
- **不变式**：报告不含凭据、密钥、token；不读取 `.jsonl.zstd` 会话日志；证据只引用环境变量名，不引用值。
- **只读/报告落盘边界**：审查员/裁判员「只读」= 不改代码/spec/任务树/仓库产物；唯一允许写入是 `tmp/` 审计报告或内联汇报（Step 9 必删）；PR 引用内联内容，不引用已删除文件；报告路径可写「`tmp/...`（Step 9 删除）」或「内联：Step 5 汇报 / PR 描述」。

### C9 反偷懒/反越权检查表 + 主脑时序/子代理越权检查

- **前置条件**：裁判员 J2/J3 工作。
- **后置条件**：检查表分三组，每条给 `pass` / `deviation` / `na` + 证据位置：
  - **A 组（红线映射 11 条）**：反偷懒 4 条 + 反越权 7 条——mini-spec 资格不可自判、纯文档资格不可自判、Step 1 不可跳过、测试从契约派生/核销不可自填✅、禁止 AI 合并 PR、模糊授权最窄解释、高危动作确认、跨仓库主体确认、批量文本 UTF-8、subagent 派发权限预检、外部服务故障降级。**口径说明**：v4.6.0 新增的 2 条监督红线（监督角色形同虚设 / 监督角色越权）由 C7/C8/C12 覆盖，不纳入 19 条映射；若要扩为 21 条，需用户重新签约。
  - **B 组（主脑时序 3 条）**：B1 主脑是否在子代理返回前/仅部分返回时就推进下一步（证据：派发记录、返回消息、步骤汇报时序）；B2 主脑是否自判核销/自判验收/自判 PASS（证据：核销表、验收汇报、裁判单）；B3 主脑是否未按 spec 条款派发或擅自扩大范围（证据：派发 prompt、diff vs spec 文件作用域）。
  - **C 组（子代理越权/偷懒 5 条）**：C1 是否超出文件作用域（diff vs `write_scopes`）；C2 是否跳过自检（自检记录/命令+退出码）；C3 是否只回元信息不带产出；C4 是否伪造测试结果或擅自改需求（测试报告/条款号追溯）；C5 是否明显偷懒（只做部分、无证据、把活推回主脑）。
  - 合计 19 条；A5 验收按 19 条核对。
- **失败行为**：检查表缺项、或全部标 `na` 无理由 → 裁判单无效；裁判员把「没发现问题」写成 PASS 但无逐条证据 → 退回。
- **不变式**：检查表是规则映射，不新增/放宽红线；红线原文仍以 SKILL.md 为准。

### C10 与 9 步流程、既有闸门和角色的关系

- **后置条件**：9 步标题仍为 9 个（Step 1–9），核销规则、用户验收归属、代码审查闸门（打回 ≤2 轮）、测试员两支柱**不变**；审查员/裁判员是团队模式内部增强，不是第 10 步；Step 5 核销表增加「裁判员」行（J3/J4 结论 + 报告路径；**允许写「内联：spec §9/PR 描述」**，不要求长期文件），但不计入条款核销率；Step 6 汇报附裁判单摘要；Step 7 PR 前复用 J4 结论做交付合规复核；单干 / mini-spec 降级为内联检查表并注明「无独立审计」，不强制启用；**主脑汇总与报告**：Step 6 五项报告由主脑汇总团队产出（安全审查报告/测试报告/裁判单/核销表）后起草；裁判员 J4 只审合规、不代写；**两套阈值独立**：安全审查打回 ≤2 轮（内容质量）与执行尝试 ≤3（跑挂）互不抵扣；**用户决策展示**：主脑向用户展示决策点必须在正文完整列出选项（不得只依赖工具 UI），工具选项不可见时用正文清单 + 字母回复；**主脑是用户唯一对接人**：用户提问优先回复当前状态/在等什么；主脑**只派活/决策/对用户交付，不亲自开发/测试/审代码**；**所有下游回报经审查员汇总，主脑不直接等裁判员**；**5 分钟无审查员消息 → 主动询问/唤醒审查员重试**。
- **失败行为**：把新角色写成替代用户验收/机器校验、或把 9 步改成 10 步、或强制单干启用 → 校验 FAIL；若未来改动破坏 9 步语义，才按 major 递增；本次不破坏，按 C11 的 4.6.0 minor。
- **不变式**：9 步编号与语义不变；用户验收仍是最终闸门；`check_spec.py` 仍是独立机器闸门。

### C12 降级与关闭开关

- **前置条件**：宿主能力不足、审查员/裁判员派发失败/超时、用户拒绝、单干模式。
- **后置条件**：审查员派发失败/超时 → 主脑内联做同样审查并注明「无独立审查」；裁判员派发失败/超时 → 主脑**不得自判 PASS**，改用新 subagent 或 `workflow`，仍失败 → 报用户并暂停进入下一步；单干 / mini-spec → 内联检查表并注明；用户拒绝/要求关闭 → 行为回退到 4.5.0，不创建角色、不派发；审计报告落 `tmp/` 或内联，Step 9 必删。
- **失败行为**：裁判员失败后主脑静默跳过、或把「内联自查」写成「裁判员 PASS」→ 违规；用户拒绝后仍强制派发 → 越权。
- **不变式**：降级必须显式声明，不得静默；关闭开关不改变 9 步与用户验收。

### C13 角色按需启用矩阵与可选专项能力

- **前置条件**：团队模式启用；主脑按改动规模/风险判定执行形态。
- **后置条件**：`team-mode.md` 新增「角色按需启用矩阵」，按四档决定派谁：
  - **形态 0 单干 / mini-spec**：主脑独立；Step 1 主脑兼任；不派任何角色。
  - **形态 1 小改**（多文件但单模块、低风险、无外部输入）：主脑 + 相关开发 + 代码安全员 + 审查员（轻量分诊，异常时深度）+ 测试员 + 裁判员（J1/J3/J4；J2 流程审计轻量）。
  - **形态 2 中改**（跨模块 / 前后端联动 / 有外部输入）：主脑 + 相关前后端开发 + 代码安全员 + 审查员（异常/偷懒时深度）+ 测试员（验收测试）+ 裁判员 J1–J4；需求澄清员（模糊时）。
  - **形态 3 大改/高风险**（全栈 / 多模块 / 对外暴露 / 不可逆 / 安全敏感）：全部 8 角色 + 裁判员 J1–J4 + 审查员待命；按需启用可选专项——深度安全审计（代码安全员专项扩展）、方案评审（独立 subagent）、发布验证（有正式环境时）。
  - **需求澄清员为按需**：清晰需求/小改由主脑兼任；模糊需求/大改才派。
  - **代码安全员、审查员、裁判员、测试员在团队模式形态 1–3 必须执行**；只有主脑单干例外，主脑必须自测并注明。
  - **前后端开发只派相关侧**，不强制双端。
  - **Step 6 五项报告由主脑汇总团队产出后起草**；裁判员 J4 只审合规、不代写。
  - 可选专项**不新增常设角色**；代码安全员是常设必执行角色，不属可选专项；未启用专项时在 spec/汇报注明「未启用及理由」。
- **失败行为**：小改强制全角色上阵 / 团队模式缺裁判员 / 可选专项被写成常设角色 / 未说明未启用理由 → 校验 FAIL。
- **不变式**：9 步、裁判员 J1–J4、用户验收、`check_spec.py` 不变；矩阵只决定「派谁」，不降低任何闸门。

### C14 审查员主动巡视协议（watchdog）

- **前置条件**：团队模式启用；审查员已派发/已就绪；存在主脑与至少一个其他成员。
- **后置条件**：**审查员是主脑唯一汇总接口**：收集开发、测试员、代码安全员、裁判员的报告，整理后给主脑判断；主脑不直接等裁判员。审查员按**默认 1 分钟**间隔（可配置 1–5 分钟；高风险项目必须 1 分钟）**主动巡视所有成员**——主脑、需求澄清员、后端/前端开发、代码安全员、裁判员、测试员；每次巡视检查：① `list_agents` 状态（running / inactive / corrupt / unsupported / unavailable；failed 语义按证据包归入对应状态）；② 任务树/看板叶子与成员状态是否一致；③ 最近产出/最后活动（**以主脑证据包/看板快照为准；子代理无 `timeline_*`，不能直读主脑后台/会话日志**）；④ 是否超时、空产出、仅元信息、明显偷懒。处置：成员 inactive 且有未完成任务 → 直接发 `continue`/`retry_same`/`question`（question 仅质疑/澄清）；**主脑 idle 且仍有未完成叶子/待派发任务 → 提醒主脑继续**；成员 running 但长时间无进展 → 催办/上报；同一成员连续 2 次巡视无响应 → 带尝试次数上报主脑；3 次尝试仍失败 → 停止自动重试交主脑。报告：异常即时上报主脑；无异常时每 5 分钟一次心跳（或按检查点）；**主脑不持续轮询，但 5 分钟未收到审查员任何消息必须主动询问/唤醒审查员重试**；审查员 5 分钟未收到主脑确认 → 再次上报/唤醒主脑；双方都卡住 → 主脑换新审查员并记录尝试次数（这是角色替换，不释放 C23 生命周期；新审查员立即接续）。形态：优先持久 teammate 循环；宿主不支持时降级为**事件触发巡视**（每次派发/返回/检查点触发一次完整巡视），并在报告中声明「无主动定时巡视」；不得要求主脑持续轮询。
- **失败行为**：主脑每 5 分钟手动查审查员 / 审查员不巡视或只看不催 / 审查员改代码/换模型/新派发 / 审查员只盯开发不盯裁判员与主脑 → 校验 FAIL；宿主无定时能力且未声明降级 → FAIL。
- **不变式**：审查员只读、只审不裁；巡视不改变任务范围；主脑仍是决策者；1 分钟为默认值，可配置但不得高于 5 分钟；主脑不得被要求定时轮询。

### C15 裁判员不执行测试、不审代码，只审契约

- **前置条件**：团队模式启用；测试员已执行验收测试；代码安全员已执行代码审查+安全检查；J3/J4 契约审核点。
- **后置条件**：**测试执行归测试员**（只做验收测试：执行测试、找问题、给更正建议；不审代码）；**代码审查（正确性/质量/注释/重复功能）+ 安全检查归代码安全员**；**裁判员不执行测试、不审代码**，只审契约符合性；裁判员在**测试员验收测试 + 代码安全员审查/安全检查都通过后**才审契约，并核查安全检查是否通过（防主脑偷懒）；裁判员可运行 `check_spec.py` 作为契约结构校验（非测试）；裁判单必须引用测试员报告路径/用例名与代码安全员代码审查/安全结论，并声明「未执行测试、未审代码；测试归测试员，代码审查+安全检查归代码安全员」；裁判单报**审查员汇总**，不直接报主脑。
- **失败行为**：裁判员运行测试 / 审代码 / 替代测试员或代码安全员出结论 / 测试或安全未过就审契约 → 裁判单作废，记违规；裁判单未引用测试员报告与代码安全员结论 → 退回补全。
- **不变式**：测试执行归测试员；代码审查+安全检查归代码安全员；裁判员只审契约与证据；用户验收与 `check_spec.py` 仍是独立闸门；裁判员报告经审查员汇总给主脑。

### C16 信息流与循环升级顺序（审查员为唯一汇总接口）

- **前置条件**：团队模式启用；开发/测试/安全/裁判角色已就位；存在用户与主脑。
- **后置条件**：
  - **信息流**：用户 ↔ 主脑 ↔ 审查员 ↔（代码安全员 / 裁判员 / 前后端开发 / 测试员）；**主脑不直接等裁判员**；所有下游回报经审查员汇总后给主脑判断。
  - **主脑**：只派活、决策、对用户交付；不亲自开发/测试/审代码；用户提问优先回复当前状态/在等审查员汇总/下一步，不得以等待下游为由沉默。
  - **审查员**：实时巡视所有成员状态/回复，收集开发、测试员、代码安全员、裁判员报告，整理给主脑；可直发 `continue`/`retry_same`/`question`（question 仅质疑/澄清），换模型/换范围/新派发交主脑；不审代码、不做测试、不决策。
  - **开发**：按主脑派活开发/修代码；接收测试员/审查员反馈。
  - **测试员**：**只做验收测试**（按 spec + `design.md` / 后端标准 / 数据库标准），执行测试、找问题、给更正建议；不审代码；不通过 → 审查员汇总主脑 → 主脑让开发修 → 再测试，循环。
  - **代码安全员**：**代码审查（正确性/质量/注释/重复功能）+ 安全检查**；不通过 → 告审查员 → 审查员汇总主脑 → 开发修 → 再测试/再安全检查，循环。
  - **裁判员**：测试 + 安全都通过后审契约（不审代码、不测试；核查安全检查是否通过，防主脑偷懒）→ 报审查员汇总 → 主脑 → 用户。
- **失败行为**：主脑直接等裁判员 / 跳过审查员汇总 / 裁判员审代码或测试 / 测试员审代码 / 安全未过就裁判审核 / 用户提问不回复 → 校验 FAIL。
- **不变式**：9 步/核销/用户验收/`check_spec.py` 不变；审查员只汇总不决策；主脑决策；裁判员不审代码不测试；测试员只验收测试；代码安全员代码审查+安全检查。

### C17 代码安全员安全审查库与工具适配

- **前置条件**：团队模式启用；测试员验收测试通过；代码安全员做代码审查+安全检查。
- **后置条件**：新增 `references/security-kb.md` 作为代码安全员的安全审查库，包含：数据源（OSV / GitHub Advisory / NVD / CISA KEV / EPSS / endoflife.date / 厂商公告 / OWASP·CWE）、工具矩阵（SonarQube·SonarScanner 可选、Semgrep、CodeQL、Bandit、ESLint security、npm audit、pip-audit、OSV-Scanner、Trivy、Grype、OWASP Dependency-Check、gitleaks、trufflehog、Checkov、kics、Syft/CycloneDX、ZAP）、严重度规则（KEV/可达性/修复版本/CVSS/EPSS）、审查流程、报告模板、更新机制、离线降级。代码安全员每次审查必须：① 按依赖/锁文件查 OSV/GHSA/NVD 与 EOL，记录包名+版本+来源 URL+查询日期；② 按技术栈跑 SAST/SCA/密钥/IaC 工具；SonarQube 仅作为可选适配（`SONAR_HOST_URL`/`SONAR_TOKEN`/`SONAR_PROJECT_KEY` 只从环境变量读，禁止入库/入报告），无服务时写「SonarQube 未接入」并改用替代工具；③ 按第 4 节定级（P0–P3）；④ 报告交审查员汇总，不通过 → 审查员汇总主脑 → 开发修 → 再测试 → 再安全检查；⑤ KB 每周/每月复核，结论必须附来源+日期，无网络标「未联网核验」，不得声称最新。
- **失败行为**：凭记忆断言「最新/无漏洞」/ 无来源或日期 / 伪造 SonarQube 或工具结果 / 把 token 写进报告或 commit / 未查依赖版本 / 无工具未标缺失 → 报告作废，记违规。
- **不变式**：代码安全员只读；不写生产数据、不执行破坏性扫描；不替代测试员（验收测试）与裁判员（契约审核）；9 步/核销/用户验收不变。

### C18 执行中需求变更 / 重签约协议

- **前置条件**：团队模式已签约并执行中；用户追加需求或修改已签约内容。
- **后置条件**：
  1. **主脑先回应用户**：当前状态/影响/下一步，不得沉默。
  2. **回 Step 2 改 spec（spec-first）**：主脑分析影响，更新契约、验收、范围、非目标；不得绕过 spec 直接改代码。
  3. **通知审查员暂停子智能体**：主脑告知审查员「暂停所有子智能体新工作、保留已有产出、待命」；审查员转达并盘点进度（各角色做到哪/产出/未完成/阻塞），汇总给主脑。
  4. **暂停期间不跑旧契约**：不派新活、不让子智能体继续旧契约；避免 token/时间浪费；宿主无中断能力时，等在跑子智能体到安全点/自然结束，只停止新派发并记录「未能立即停住」。
  5. **更新契约给用户重新签约**：把 spec diff/新增条款/验收变化展示给用户，用户重新签约后才继续。
  6. **签约后判断继续/重派**：审查员向主脑汇报最新进度；主脑按角色判断——未受影响的角色可继续（如后端不需要重开发），受影响角色重派/重跑；更新任务树。
  7. **受影响闸门重跑**：契约变更影响已完成的测试/安全/裁判结论时，必须重跑对应 J1/J2/J3/J4；不得拿旧结论冒充新契约。
- **失败行为**：变更后继续跑旧契约 / 不暂停 / 不重新签约 / 不盘点进度 / 重新签约后不判断哪些可继续 / 旧结论冒充新契约 → 校验 FAIL。
- **不变式**：用户重新签约是硬闸门；审查员只汇总不决策；主脑决策；9 步不变；已产出保留，不浪费。

### C19 角色边界：代码安全员审代码+安全；测试员只做验收测试；设计/后端/数据库标准

- **前置条件**：团队模式启用；开发交付代码；进入代码审查/测试阶段。
- **后置条件**：
  - **代码安全员**：负责**代码审查**（正确性 / 质量 / 注释 / 重复功能）+ **安全检查**（安全漏洞 / 依赖 / 权限 / 敏感信息 / 安全相关重复接口）；测试员**不审代码**。
  - **测试员**：**只做验收测试**（按 spec + `design.md` / 后端标准 / 数据库标准），执行测试、找问题、给更正建议；不审代码、不做安全检查。
  - **前端开发**：项目有 `design.md` 必须遵循；无 `design.md` → 主脑在 Step 1/2 **询问用户是否建立前端设计标准**（首次使用 / 新项目必须问）；用户不建立 → 降级为根据用户经验总结前端规范并记录。
  - **后端开发**：遵循后端标准 + 数据库标准（项目文档 / `design.md` / runbook）；无标准 → 询问/总结并记录。
  - 测试员必须按上述标准测试；无标准时按降级规范测试并注明。
  - **团队模式形态 1–3 测试员必执行**；只有主脑单干例外，主脑必须自测并注明。
- **失败行为**：测试员审代码 / 代码安全员不审代码 / 无 `design.md` 未询问 / 测试员未按标准 / 团队模式小改不派测试员 / 主脑单干不自测 → 校验 FAIL。
- **不变式**：9 步/核销/用户验收不变；代码安全员只读；测试员只做验收测试；标准缺失必须显式降级。

### C20 审查员图像审查与测试执行环境

- **前置条件**：团队模式启用；下游返回图片/截图/报告；测试需要浏览器/OS 操作。
- **后置条件**：
  - **审查员优先使用具备图像输入能力的模型**；收到图片/截图/报告时，向主脑报告并说明需要识图；**主脑判断是否派临时识图子智能体**分析，结果交审查员汇总给主脑；审查员不得假装识图。
  - **测试员在必要时使用实际可控的 Windows/macOS 工具/方法执行测试**；浏览器测试必须真实浏览器操作 + 截图汇总；Playwright 等环境**提前适配**；不可用 → 声明降级/替代。
  - 测试报告包含截图/路径/操作步骤/结果；无 UI 则注明无 UI。
- **失败行为**：审查员无识图能力却假装分析图片/不报告 / 测试员该跑浏览器却只跑 API / Playwright 未适配却声称跑过 / 无截图汇总 → 校验 FAIL。
- **不变式**：审查员只汇总不决策；主脑决定临时识图子智能体；测试员执行测试；不伪造截图/结果。

### C21 契约互审与质疑机制（需求模糊/跳过澄清员 + 审查员反问 + 前瞻全局）

- **前置条件**：需求模糊/有歧义，或未派需求澄清员；或审查员汇总子代理报告；或主脑质疑审查员总结。
- **后置条件**：
  - **需求模糊 / 跳过需求澄清员**：主脑必须组织**契约互审**——主脑 + 审查员 + 裁判员（如已派需求澄清员则一并参与）各自提出假设、反驳、替代方案、风险与全局影响；至少 1 轮互相质疑；主脑收敛后向用户总结最终契约，不得直接开工。
  - **审查员汇总每个子代理报告时**：必须自己分析；至少提出 1 个质疑/反问（为什么这样做 / 有没有更好方法 / 边界与异常 / 替代方案）给下游子代理；拿到回答后再总结给主脑；主脑可反向质疑审查员总结；未解决疑问不得向用户呈现为最终结论。
  - **质疑清单**：假设是否成立、有没有更好方法、边界/异常、跨模块/全局影响、前瞻性（未来扩展/维护/成本）、证据是否充分。
  - **主脑第一版契约后自审（尤其单干）**：主脑完成第一版契约后必须自我质疑/审视——假设是否成立、有没有更好方法、是否便于后期管理/扩展、前瞻性是否足够；**不要等实现完再质疑改契约**（返工成本更高）。
  - **质疑语气**：友善、对事不对人；对方解释合理就直接总结给上游（主脑），不纠缠。
  - 审查员/裁判员只读；不替主脑决策；主脑收敛并负责最终契约。
- **失败行为**：需求模糊未互审 / 跳过澄清员未互审 / 审查员只汇总不反问 / 主脑质疑未回应 / 未解决疑问就向用户呈现 → 校验 FAIL。
- **不变式**：用户仍是最终验收；审查员只汇总不决策；主脑决策；9 步不变。

- **后置条件**：README / SKILL / `team-mode.md` 包含作者署名与商用说明：**MIT 协议，可免费使用/修改/商用**；**商用请注明出处与作者，并邮件告知 971554652@qq.com**（友好请求，不构成 MIT 之外的额外许可限制）；作者背景：**互联网公司 8 年 IT 技术岗，转 AI 产品架构师**；语气和蔼、有自信。
- **失败行为**：删除署名 / 把商用请求写成 MIT 之外的强制限制 / 缺联系方式 / 语气冒犯 → 校验 FAIL。

### C23 审查员生命周期：契约结束前不得结束

- **前置条件**：团队模式契约已开始；审查员已创建。
- **后置条件**：
  - 审查员是**契约生命周期内常驻/可复用角色**：从签约到 PR 创建/Step 9 完成，不得主动结束或被视为结束；同一审查员会话复用（宿主支持持久 teammate 则持久；否则一次性 subagent 由主脑在每次派发/返回/检查点/等待时唤醒）。
  - **审查员 inactive 不是结束标志**；主脑必须唤醒并确认其是否还有下游任务/未汇总报告。
  - 审查员下游（开发/测试/代码安全员/裁判员）没有任务、且 PR 已创建/Step 9 完成，才可结束。
  - **C12 内联降级是临时措施，不释放审查员角色**：主脑必须唤醒/重派审查员；内联仅当唤醒失败并记录「无独立审查」，不得把 C12 当结束依据。
  - **C14 的「换新审查员」是角色替换，不是结束角色**：旧审查员可退役，但新审查员必须立即接续，契约生命周期不断；PR/Step 9 前不得无审查员。
- **失败行为**：契约结束前审查员被结束 / 未唤醒 / 主脑把 inactive 当结束 / PR 前释放审查员 → 校验 FAIL。
- **不变式**：审查员只读、只汇总；主脑决策；9 步/核销/用户验收不变。

## 7. 边界与异常

| 场景 | 期望表现 |
|---|---|
| 审查员 subagent 派发失败/超时 | 主脑内联做同样审查并注明「无独立审查」；不跳过（C12） |
| 裁判员 subagent 派发失败/超时 | 主脑不得自判 PASS；换新 subagent/`workflow`，仍失败报用户暂停（C12） |
| 审查员与主脑结论冲突 | 主脑决定并留痕；审查员报告原文附入汇报；涉及规则/契约交裁判员（C3/C7） |
| 裁判员与主脑结论冲突 | 主脑可回应，不得删除裁判单；争议交用户裁定；未解决不得进入下一步（C7） |
| 证据包缺失/后台不可见 | 标 `evidence_missing` 或「后台可见性：降级」，要求补齐；不得凭空 PASS/BLOCK（C8） |
| 子代理只回元信息不带产出 | 分类 `meta_only`，建议主脑直做或重派并明确要求最终消息含完整产出物（C2/C5） |
| 同一异常反复失败/换模型 | 尝试计数累计，总尝试 ≤3；第 3 次失败上报；禁止无限重试（C4） |
| 用户中途改需求 | 按 C18：主脑先回复→通知审查员暂停子智能体并盘点→回 Step 2 改 spec→用户重新签约→受影响 J1–J4/测试/安全闸门重跑；不得绕过 |
| 单干模式被要求启用 | 降级内联检查表并注明；不创建角色、不派发（C12） |
| 宿主无 subagent/无 timeline | 内联检查表 + 文字版进度；裁判员失败不得自判 PASS（C12） |
| 审查员/裁判员越权 | 报告作废，主脑记违规并重派；必要时报用户（C3/C7） |
| 凭据/日志泄露风险 | 禁止读取会话日志与 `.jsonl.zstd`；报告只写环境变量名（C8） |
