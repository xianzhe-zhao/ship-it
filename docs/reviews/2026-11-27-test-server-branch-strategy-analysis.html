测试服务器分支策略增强 — 方案分析

1. 问题背景

当前 ship-it SKILL.md Step 7 流程只支持直接提 PR 到 main，但很多项目有测试服务器，需要先合并到 test 分支测试通过后再合并到 main。

2. 问题清单与根因分析

问题：SKILL.md 不支持测试服务器分支策略

现象：用户说"其他项目肯定是有测试服务器的这个时候要先合并到test"

根因：SKILL.md Step 7 只写了"创建 PR 到 main"，没有考虑有测试服务器的场景

影响：有测试服务器的项目无法按规范流程操作

3. 解决方案

方案 1：SKILL.md Step 7 加测试服务器分支策略

修法：在 Step 7 加一段"测试服务器分支策略"，说明有测试服务器时先提 PR 到 test，测试通过后再提 PR 到 main

改动：ship-it/SKILL.md Step 7 节

为什么：当前流程只支持直接提 PR 到 main，需要支持有测试服务器的场景

方案 2：判定方式查 runbook

修法：Step 2 方案自审时查 docs/deploy-runbook.md 里有没有测试服务器配置

改动：ship-it/SKILL.md Step 2 节 + ship-it/references/project-adaptation.md

为什么：runbook 是项目配置的唯一事实源，查 runbook 最准确

4. 方案推导过程（需求分析员视角）

4.1 需求分析员做了什么

作为需求分析员，我的工作流程是：

  1. 收集问题：从用户反馈中收集问题
  2. 分类归因：把问题按根因分类（流程缺失）
  3. 盘点现有能力：查 SKILL.md Step 7/8 流程
  4. 推导方案：对每个问题，问"怎么修最合理"，给出推荐方案和备选方案
  5. 评估影响：分析每个方案的影响范围、风险、成本
  6. 做决策：综合所有方案，给出最终推荐

4.2 问题分析与方案推导

问题：SKILL.md 不支持测试服务器分支策略

  • 分析：当前 SKILL.md Step 7 只写了"创建 PR 到 main"，没有考虑有测试服务器的场景。很多项目有测试服务器，需要先合并到 test 分支测试。
  • 推导：既然是流程缺失，就应该在 SKILL.md 里加"测试服务器分支策略"。判定方式查 runbook 最准确，因为 runbook 是项目配置的唯一事实源。
  • 方案：在 SKILL.md Step 7 加测试服务器分支策略，判定方式查 runbook

4.3 方案对比与决策

问题 推荐方案 备选方案 为什么不选备选
SKILL.md 不支持测试服务器分支策略 在 Step 7 加测试服务器分支策略，判定方式查 runbook 不改 SKILL.md，只补充说明 治标不治本，下次遇到同样问题还要问

5. 决策

决策树：从三个选项中选择最终方案。

选项：

  • 选项 A：在 SKILL.md Step 7 加测试服务器分支策略，判定方式查 runbook —— 彻底解决，贡献回社区
  • 选项 B：test 和 main 并行 —— 复杂，用户需要手动管理两个分支
  • 选项 C：只补充说明到当前 PR —— 快但治标不治本

推荐：选项 A（在 SKILL.md Step 7 加测试服务器分支策略，判定方式查 runbook）

理由：

  • 当前流程只支持直接提 PR 到 main，需要支持有测试服务器的场景
  • runbook 是项目配置的唯一事实源，查 runbook 最准确
  • 改 SKILL.md 可以彻底解决问题，避免下次遇到同样问题还要问

最终决策：按推荐方案修复

  • SKILL.md Step 7 加测试服务器分支策略
  • 判定方式查 runbook
  • references/project-adaptation.md 加"测试服务器配置"检查项

改动文件：2 个（ship-it/SKILL.md + ship-it/references/project-adaptation.md）

改动行数：约 30 行

风险：低（不改既有流程，只在有测试服务器时启用新流程）
