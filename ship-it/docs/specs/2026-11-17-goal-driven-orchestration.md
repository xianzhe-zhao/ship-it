## 1. 背景与目标（what & why）

**现状**：团队模式（v3.1.0+）已有 7 个角色、能力要求表、派发协议、失败降级与共享看板映射，但**主脑的进度状态只存在于会话上下文里**——没有外部持久化的目标与任务状态。后果有两个：

1. **上下文一断就失忆**：换模型、上下文压缩、跨天续做时，主脑必须重读 `SKILL.md` + `deploy-runbook.md` + `team-mode.md`（三份合计约 1100 行，v4.4.0 实测）才能恢复"做到哪、剩什么、卡在哪"。2026-11-17 上午本会话真实发生过一次（模型切换 + 上下文重置，重读成本约 40k token）。
2. **契约核销靠自觉**：Step 5 核销表由主脑自己填，`check_spec.py` 只校验 spec 结构，不校验"任务是否真的全做完"——与「禁止自证」红线存在缝隙。

**为什么要改**：DSH 已提供 `create_goal` / `update_goal`（目标生命周期）与 `timeline_tree` / `timeline_tasks` / `timeline_pull`（任务树，状态持久化、机器可读、GUI 任务面板可见）。把这些原语写进团队模式流程，可把"进度"从会话上下文外置为**机器可查的状态**，同时给 Step 5 增加一个不可自证的校验项。

**改完是什么样**：需求签约时用户决定是否启用目标；启用后主脑建任务树、按叶子派活、把进度写回树；Step 5 核销表多一行「目标树完成度」由树状态机器读取；Step 6 用户验收后关闭目标。同时修正 runbook 中已实测失配的模型配置（含分环境记录）。

### 需求澄清记录（Step 1 产出，签约时展示给用户确认）

- **原始需求**：「我想加一个功能就是现在用户提交需求之后是否可以跟智能体工具的目标进行呢？添加目标，有一个主脑指挥这些团体去干活。然后通过目标进行管理之后核对契约。可以实现吗 别人是怎么做的 你去网上搜搜」；补充：「Deepseek 是主脑 上下文大但是 可以派活儿给GLm 和Qwen」。
- **优化后需求**：在团队模式中引入「目标驱动编排」：spec 签约时由用户选择是否创建目标（`create_goal`）；启用后主脑以「目标 + 9 步分组的任务树」指挥各角色，叶子为可检查动作；角色产出后主脑把进度/阻塞写回任务树；Step 5 契约核销表增加「目标树 100% 完成」机器校验项（状态由 timeline 读取，非主观填写）；Step 6 用户验收通过后关闭目标。runbook 的模型能力清单与角色分配改为**按环境分节**，并修正与宿主实际配置失配的模型 ID。（注：C5 已于 2026-11-17 修订——核销分母限定为 Step 1–5 叶子，全树 100% 于 Step 9 收尾汇报；以第 5 节 C5 为准。）
- **优化说明**：① 把口语需求拆成可核销条款（C1–C9）；② 明确"目标"不是新机制而是 DSH 既有原语（`create_goal` + timeline）写进流程，属**扩展**非新建；③ 补出"分环境"维度（用户提出家/工作两套模型）；④ 联网调研业界做法（见第 2 节复用盘点）；⑤ 澄清了 token 增量（见成本预算）。
- **用户问答**：
  - 问「目标管理适用于哪些执行形态」→ 用户答：**仅团队模式**（主脑单干不引入）。
  - 问「何时创建目标」→ 用户答：**签约的时候就询问用不用目标**（不自动创建，用户选择）。

  - 问「本次是否启用目标管理（目标 + 9 步任务树）」（C1 必答项）→ 用户答：**启用**。据此调用 `create_goal` 并建树，Step 5 核销读取树状态。

## 5. 契约条款（C1 / C2 / …）

### C1 目标创建时机由用户在签约时决定

- **前置条件**：团队模式判定成立，spec 已写完待签约（Step 2 末）。
- **后置条件**：主脑在签约汇报中以一个问题询问"本次是否启用目标管理（目标 + 任务树）"；用户选择（启用 / 不启用）逐字记录进 spec 第 1 节「需求澄清记录」；启用则在签约确认后调用 `create_goal`，objective 取自优化后需求 + 验收标准。
- **失败行为**：用户未回答或回答含糊 → **不创建目标**，按原流程执行，spec 注明"用户未选择，未启用目标"；不得替用户默认启用或默认跳过。
- **不变式**：任何时刻，未完成签约（用户未确认 spec）不得创建目标。

### C2 任务树按 9 步分组、叶子为可检查动作

- **前置条件**：C1 判定为启用目标，且已调用 `create_goal` 拿到目标。
- **后置条件**：调用 `timeline_tree` 建树，根下按 Step 1–9 分组；每组叶子至少 1 个，每个叶子是可检查动作（含可验证的完成判据，如"check_spec.py 退出码 0"）；叶子状态仅使用 pending / active / done / blocked / paused / retired。
- **失败行为**：某步无法拆出可检查叶子 → 该步建单叶，并在描述中写明"不可拆分"的具体原因；`timeline_tree` 调用失败 → 主脑降级为在汇报中维护文字版进度表，并注明"任务树不可用"。
- **不变式**：树节点总数（含根与分组）不超过 40 个；超出说明拆分过度，必须合并——防止更新开销失控。

### C3 派发协议携带任务标识与完成标准

- **前置条件**：主脑向任一角色派发任务。
- **后置条件**：subagent prompt 必含三要素——spec 条款号、文件作用域、自检要求（沿用既有派发协议），**并额外包含**任务标识行（格式为 `Timeline: tree=tree-8f8ac828ae16da2f; tasks=clarify,design` 这样的"树 ID + 叶子 ID 列表"键值行）与完成标准。
- **失败行为**：子代理无 timeline 工具或读取失败 → 主脑在 prompt 内**内联完整任务描述**，不依赖子代理自行读取；内联后仍失败一次 → 主脑自己做，不再重派。
- **不变式**：引入任务标识后，spec 条款号仍必须出现在 prompt 中（不得用任务 ID 替代条款号）。

### C4 进度与阻塞写回任务树

- **前置条件**：任一角色产出返回主脑。
- **后置条件**：主脑在进入下一步前更新对应叶子：完成 → `done` 并附结果摘要；受阻 → `blocked` 并附具体阻塞条件；每步汇报中说明任务树当前完成度（已完成叶子数 / 总叶子数）。
- **失败行为**：写回失败 → 主脑在汇报中以文字列出当前状态，并显式注明"任务树未同步"；不得静默跳过。
- **不变式**：任务树状态与主脑汇报内容一致——两者冲突时以任务树为准并立即修正汇报。

### C5 Step 5 核销表增加目标树完成度机器校验项

- **前置条件**：进入 Step 5 契约核销（启用目标时）。
- **后置条件**：核销表新增一行「目标树」，取值形如"完成 X/Y"；**分母 Y 只计核销时点应完成的叶子，即 Step 1–5 分组下的叶子**（Step 6–9 的叶子只能在核销之后完成，纳入分母即死锁，2026-11-17 自举实测发现）；通过条件为 X = Y **且** `timeline_pull` 中 Step 1–5 分组无未完成叶子；该行的 X/Y 由 timeline 状态读取，不由主脑主观填写。全树完成度（含 Step 6–9）在 Step 9 收尾汇报中给出，届时必须为全树 100%。
- **失败行为**：Step 1–5 存在未完成叶子 → 核销不合格，不得进入 Step 6；须回到对应步骤补齐或显式 `retired` 并说明理由。
- **不变式**：目标树完成度与 `check_spec.py --stage verify` 退出码 0 是两个**并列且独立**的必要条件，任一不满足即核销不通过；核销通过后 Step 6–9 的叶子仍须全部 `done`，否则 Step 9 不得收尾。

### C6 用户验收通过后关闭目标

- **前置条件**：Step 6 用户明确表示验收通过。
- **后置条件**：调用 `update_goal` 置 `complete`，并在汇报中说明目标已关闭。
- **失败行为**：用户未明确验收 → 目标保持 `active`，不得 `complete`；同一阻塞条件连续 3 轮未解除 → 置 `blocked` 并写明具体条件（不得以"困难/不确定"为由置 blocked）。
- **不变式**：目标 `complete` 与用户验收一一对应，禁止提前关闭（与 SKILL.md「禁止自证」一致）。

### C7 runbook 模型配置按环境分节记录

- **前置条件**：记录或更新 `docs/deploy-runbook.md` 的模型能力清单与角色分配。
- **后置条件**：按环境分节（至少「办公环境」与「家用环境」两节）；每节标注**环境识别依据**（实测：办公环境 `USERDOMAIN=CORP` 且存在公司 HTTP 代理；主机名 `XIANZHE-ZHAO01`）；每节记录 provider、配置真源路径、模型池与角色分配。
- **失败行为**：当前环境无法匹配任一环境节 → 记录为"未知环境"，只允许使用会话默认模型，并在汇报中提示用户补充该环境配置；不得套用其他环境的分配。
- **不变式**：任一环境节内出现的模型 ID 必须与宿主实际配置逐字一致（大小写、后缀），不得使用别名。

### C8 模型 ID 一致性可机器校验且"可派发"须实测

- **前置条件**：在 runbook 中记录某模型"可用于派发"。
- **后置条件**：该结论必须由一次实测支撑——用 `list_subagent_models`（provider + model）验证路由可用；记录中同时标注验证方式、验证日期与**验证时的会话**（因下述固化机制，配置变更只对新会话生效）。
- **会话固化约束**：宿主把 `allowedModels` 在会话创建时写入会话事件流（`subagent/model-selection-policy`）并持久固化，已有策略不再被覆盖（源码 `packages/subagent/tool-subagent/src/model-selection-settings.ts`，写入条件为 `firstLiveSeq === 0`）。因此改宿主配置后，**当前会话仍持有旧策略**，必须新开会话才能验证；runbook 记录"可派发"时须注明验证于哪个会话。
- **失败行为**：`list_subagent_models` 返回"provider has no configured model"或"route is not allowed for this Session" → 该模型标注为"**不可派发**"并写明原因，不得宣称可派发；若根因是 `allowedModels` 与模型池 ID 不匹配，记录为宿主配置缺陷并给出修复项（把白名单改为模型池真实 ID）。
- **不变式**：runbook 中标记"可派发"的模型集合，必须是通过实测的子集；未实测的模型一律标注"未验证"。

### C9 团队模式扩展不改变 9 步语义

- **前置条件**：任何对 `SKILL.md` 或 `team-mode.md` 的流程规则改动。
- **后置条件**：9 步、闸门、核销、用户验收的语义保持不变；本次新增的仅是"谁来执行 + 进度怎么管"。

## 7. 边界与异常

| 场景 | 期望表现 |
|---|---|
| 用户不启用目标 | 原流程照跑，spec 注明未启用，无任何 timeline 调用（C1） |
| 目标已存在（同一需求续做） | 复用既有目标与树，不重复 `create_goal`；先 `timeline_pull` 恢复状态再继续 |
| 上下文中断后恢复 | 先 `timeline_pull` 取未完成叶子，按树恢复进度，不重读全部文档 |
| `timeline_*` 工具不可用（其他宿主环境） | 降级为文字版进度表，注明"任务树不可用"，流程继续（C2 失败行为） |
| 子代理无 timeline 工具 | 主脑内联完整任务描述，不依赖外部读取（C3） |
| 任务树节点超过 40 | 合并叶子；合并后仍超限 → 说明拆分过度，重做树结构（C2 不变式） |
| 环境无法识别 | 记"未知环境"，只用会话默认模型，提示用户补配置（C7） |
| 模型 ID 与宿主配置不匹配 | 标注"不可派发"+ 原因 + 修复项，不得宣称可派发（C8） |
| 配置已改但当前会话仍报 not allowed | 判定为会话策略固化（非配置错误）；提示用户**新开会话**后重测，本次不重复改配置（C8） |
| 目标树 Step 1–5 叶子未完成却要进 Step 6 | 核销不合格，退回补齐或 `retired` 并说明（C5） |
| 用户验收含糊 | 主动询问"测试是否无异常？可以进入下一步吗"，明确肯定才关闭目标（C6） |

> 本表即 Step 4 异常路径测试的清单来源：**只测这里声明的项**，不强制通用清单。
