## 1. 背景与目标（what & why）

- **现在**：ship-it v5.1.0 的变更类型只有 bug/spike/refactor 三种且只影响 Step 3/4 检查项，无显式步骤序列表，模型易跳步；角色矩阵无性能专项；代码安全员只指出问题不给修复方案；"签约才编码"是事后 git-check，非事前拦截；核销表条款可被偷偷改弱而无机器校验；需求澄清无量化清晰度；中途发现新 bug/新需求一刀切暂停重签，已通过工作被牵连重跑。
- **为什么**：上述每一项都是真实返工/越权/假绿的根因。借鉴 trellis（轨道状态机/规划期只读保护/局部 Git 校验）与 omd（咨询顾问角色/criterion amendments/graceful degradation/deep-interview 歧义度/leaf-guard）的成熟机制，把"纪律"升级为"机器可查 + 物理锁"，补齐防作弊闭环。
- **改完**：5 条变更轨道 + 显式步骤序列；新增性能工程师（咨询顾问模式）；代码安全员升级为咨询顾问模式；check_writes_before_sign.py 事前拦截；C 条款版本号 + 修订台账；Step 1 歧义度自评；核销 ai/human 双模；Step 9 局部 Git 校验；可选能力显式降级；leaf-guard 叶子代理工具隔离（DSH 建议启用）；中途变更三分流 + 冻结已通过 + backlog。

### C2 新增性能工程师角色（咨询顾问模式）（revision: 1）

- **前置条件**：`references/role-glossary.md` 角色词典新增"性能工程师"（第 9 个角色）；`references/team-mode.md`「角色按需启用矩阵」形态 3 的"按需/可选专项"列追加"性能调优专项（性能敏感时）"。
- **后置条件**：性能工程师定义为"性能验收与调优工程师"，三项职责：①性能验收（指标达标，把性能条款变可执行压测/性能测试）；②更优解评估（算法/数据结构/缓存/并发策略，附复杂度分析）；③高并发能力检测（压测定瓶颈，wrk/k6/locust）。角色为**咨询顾问模式**：诊断 + 出有依据的策略层方案（附官方文档/benchmark/复杂度/业界实践来源），交主脑裁定，前后端开发实现，性能工程师复测。方案无依据 = 不接受；方案不得落到代码行级（越界代写 = FAIL）。
- **失败行为**：性能工程师方案无依据来源 / 方案落到代码行级 / 性能工程师直接改代码 = 监察员判 FAIL。
- **不变式**：性能工程师只评估、出报告、出有依据方案，不裁定采不采纳（主脑裁定）、不执行改代码（前后端开发执行）。性能优化方案主脑可权衡驳回（不影响发布）。
- **触发条件**：spec「方案自审」标注"性能敏感"（涉及大数据量/高并发/实时性/渲染性能）时启用；不涉及则注明"未启用性能专项及理由"。

- **失败行为**：演示页落进 src/ 或被构建系统包含 / 签约后改演示页未重新签约 = `check_spec.py` 退出码 1。
- **不变式**：演示页是"将来长这样"的表达，不是"已能跑的代码"；不触发"签约前写实现代码"红线（因其落在 spec 目录内，属文档范畴，非实现文件）。

### C4 bug 轨道复现契约（revision: 1）

- **前置条件**：bug 轨道 Step 2 必出复现契约（用户视角的复现剧本，替代/补充开发者视角的失败测试）。
- **后置条件**：复现契约四要素写入 spec §2：①复现步骤（用户能照着点的步骤，非代码操作）；②当前现象（截图/录屏/报错文案）；③期望现象（修复后的可观察结果）；④严重度（P0/P1/P2 + 影响范围）。有前端时附加"修复前后对比"（截图或演示页专门区块）；纯后端写"N/A"。

### C8 中途变更三分流 + 冻结已通过 + backlog（revision: 1）

- **前置条件**：执行中发现新 bug/新需求时，不一刀切暂停，先做分流决策（主脑判断 + 用户确认）。
- **后置条件**：按"性质(同源衍生/无关新项) × 成熟度(近完成/早期)"四格分流：
  - ①同源+近完成/早期：并入当前契约，加补充条款，只测新条款，已通过的不重跑。
  - ②无关+近完成：收尾当前契约跑到验收，新项记 `docs/backlog.md`，验收后另开契约。
  - ③无关+早期：看紧急度——新项更紧急→暂停保存在途成果切过去；不紧急→当前继续，新项排队。
  - ④同源+早期：并入当前，正常推进。
  - **冻结已通过**：已核销 ✅ 的条款、已通过的测试、已验收的项，变更后默认冻结不重跑；只有变更真的影响已冻结项（如改了共用接口）才解冻重跑，且必须显式声明"解冻原因"；无关新项导致的变更不得解冻当前已通过工作。
  - **backlog**：无关新项记入 `docs/backlog.md`（发现时间/描述/初步严重度/来源），当前完成后另开 spec 独立走 9 步。
- **失败行为**：未做分流直接一刀切暂停 / 无关变更解冻已通过工作未声明原因 = 监察员判 FAIL。
- **不变式**：这是对现有"暂停重签"(SKILL.md 第143-150行)+"防膨胀一问"(第150行)的精细化，不是推翻。现有"暂停重签"只在分流③的"新项更紧急+在途早期"才触发，其他三种不需粗暴暂停。

### C9 criterion amendments（条款版本号 + 修订台账）🔒（revision: 1）

- **前置条件**：spec §5 的每条 C 条款带 `revision` 版本号 + `修订台账`；`check_spec.py` 扩展校验 C 条款 revision 一致性。
- **后置条件**：每条 C 条款格式为 `### C1 标题（revision: 1）` 这样的格式（C 后跟编号、标题、revision 号），下附`修订台账`（每条修订记 rev/原因/依据/authority/at）。改标准的唯一合法途径是在台账追加一条，原标准一字不改保留。核销 ✅ 的条款，其 revision 必须与签约时记录的 revision 一致；不一致 = 必须有台账记录，否则 `check_spec.py --stage verify` 退出码 1。
- **失败行为**：偷偷改弱条款（改 revision 不记台账）/ 台账缺 evidence 或 reason / 矛盾台账（原标准还在激活态或被改两次）= `check_spec.py` 退出码 1（fail closed）。
- **不变式**：这不是"放宽标准的工具"，而是"测量与计划不符时倒向测量"的诚实机制——完成校验只认 ACTIVE 标准。防"同源共错"（改了标准自己也忘了原标准）。
- **authority 取值**：user（用户同意）/ main-brain（主脑裁定，仅限非 🔒 条款）/ auditor（监察员，仅限流程纠偏）。🔒 条款改弱必须 authority=user。

### C11 核销 ai/human 双模（revision: 1）

### C14 leaf-guard 叶子代理工具隔离（DSH 建议启用）（revision: 1）

- **失败行为**：DSH 环境支持却未启用 / 未注明降级 = 监察员判 WARN（不阻断）。

### C15 验收前文档质量检查（机器 + 裁判员 J2）

### 示例条款（好坏对照，写新条款前先看）

## 7. 边界与异常

| 场景 | 期望表现 |
|---|---|
| 旧 spec（日期 < 2026-11-25）无 5 轨道/C 版本号 | 按 legacy 放行，`check_spec.py` 不强制新规则；`--strict` 强制 |

## 附录 A：5 条变更轨道完整定义（C1 引用）

> 本附录是 C1 的展开，不参与 sign_hash（hash_scope=sections_1_8）。签约时 C1 引用本附录。
- **轨道定义**：
  - **feature**（新增需求）：1澄清→2 spec+前端演示→3编码→4测试→5核销→6验收→7PR→8发布→9清理。差异：Step 2 必出前端演示页（有 UI 时）；Step 4 每条 C 至少一个用例。
  - **bug**（修复缺陷）：1澄清→2 spec+复现契约→3先红后绿→4转绿+回归→5核销→6验收→7PR→8发布→9清理。差异：Step 2 必出复现契约；Step 3 失败测试先行；Step 4 该测试转绿才算修好。
  - **refactor**（重构）：1澄清→2 spec→3编码→4既有测试全绿→5核销→6验收→7PR→8发布→9清理。差异：Step 3 现有测试不许改；Step 4 既有测试全绿即达标，不加新功能用例。
  - **perf**（性能调优）：1澄清→2 spec+性能基线→3编码→4压测对比→5核销→6验收→7PR→8发布→9清理。差异：Step 2 必出性能基线（当前指标）；Step 4 必出优化前后对比；启用性能工程师专项。
  - **framework**（框架更改）：1澄清→2 spec+迁移影响图→3编码→4全量回归→5核销→6验收→7PR→8发布→9清理。差异：Step 2 必出迁移影响图（受影响模块/接口/配置）；Step 4 强制全量回归（不分级）。
