# Changelog — ship-it

## 4.1.0（2026-11-11）

**防能力幻觉与防契约逃逸**：补两道"同源共错"防线（agent 既是执行者又自判合规的漏洞）。

- **测试员角色卡加「实测为证」硬约束**（`references/team-mode.md`）：声称"不支持图片输入"前**必须先发一张探针图实测**，只有实测失败才能降级；凭记忆/印象直接说"不支持"就降级 = 违规。降级决定必须附实测失败证据（哪张图、什么报错）写入测试报告。失败处理表新增"凭记忆声称不支持"行。直击"明明支持图片输入却说不支持"的能力幻觉根因。
- **SKILL.md 关键原则新增第 10 条「禁止自证」**：agent 不可自判合规，关键节点（mini-spec 资格 / 纯文档免流程资格 / 核销✅ / 能力声明）必须机器可查或用户确认。执行者 ≠ 裁定者。
- **新增「反偷懒红线」清单**（SKILL.md 常见坑表后）：覆盖四种偷懒场景——滥用 mini-spec 快速通道 / 滥用纯文档免流程 / 跳过需求澄清 / 测试从代码派生或核销表自填✅，每种加"不可自判"约束。
- **mini-spec 与纯文档免流程加「资格不可自判」约束**：门槛由客观事实（文件数/接口签名/表结构/权限/外部输入）判定，不由 agent 主观判断；**改动涉及流程规则/skill 本身时不可免流程**（本次改动即范例：改 skill 规则走了完整 spec）。
- 调研来源：业界"evidence-first / trust but verify"共识（[Evidence-First Agentic Verification](https://arxiv.org/html/2610.17724v1)、[Verification and Self-Improvement in Agentic AI](https://arxiv.org/html/2610.10611v2)）。
- spec：`docs/specs/2026-11-11-anti-hallucination-anti-bypass.md`。

## 4.0.0（2026-11-06）

**破坏性重排**：8 步 → 9 步，新增需求澄清与提示词优化步骤 + 技术蓝图节（spec 契约模式不变）。

- **新增 Step 1 需求澄清与提示词优化**（每次做、分轻重）：用户提示词不够好/不准确时，方案自审在错误前提下盘能力全浪费；本步消除"歧义税"——联网搜索 + 向用户提问 + 主脑优化，输出优化后需求 + 澄清记录进 spec，签约时展示给用户确认。团队模式派需求澄清员 subagent（联网搜索+分析+输出问题清单，不直接面对用户）；单干主脑兼任。调研来源：Spec-Driven Development（specdriven.ai 6 阶段含 Clarify）。用户看到优化后的专业表述，间接学到"原来该这么问"。
- **spec 新增技术蓝图节**（第 3 节）：前端/后端/数据库/环境依赖 4 子领域，按涉及领域填、不涉及写"无变更"；项目有 design.md 时前端子节引用并声明遵守。编码前定技术契约，避免边写边改。调研来源：SpecKit（多领域蓝图文档）。
- **spec 新增需求澄清记录**（第 1 节）：原始需求 → 优化后需求 + 优化说明 + 用户问答，签约时展示。
- **契约条款支持受保护规则 🔒 标记**：不可被悄悄改的业务事实标 🔒，改需显式 Diff 等用户审批——防"同源共错"（实现/测试/验收都由同一 Agent 解释，一致通过却偏离业务）。调研来源：微软拆解 SDD。
- **步骤重编号 8→9 整数步**（去 X.Y 子号）：原 Step 1–8 顺延为 Step 2–9，新增 Step 1；TL;DR 表 9 行；前置系统形态表 Step 引用同步（Step 3→4 部署、Step 7→8 发布）；安全增量检查归入 Step 2；DoR 自检加入第 8 节。
- **check_spec.py 适配新 9 节布局**：REQUIRED_SECTIONS 含技术蓝图（节 3）；条款节 4→5；验收节 5→6；非目标节 3→4；三问节 7→8；边界节 6→7；核销节 8→9。旧 8 节 spec 用新校验器会报缺技术蓝图节（属主版本预期行为）。
- **team-mode.md 新增需求澄清员角色卡** + 角色能力要求表 + 9 步引用同步。
- spec：`docs/specs/2026-11-06-v4-restructure.md`。

### 主要变化

- **产出物削减**：《开发方案卡》并入 spec 的「方案自审」节；《安全审查卡》废除（改为周期审查日志）；PR 说明从五块减为四块（版本号+变更摘要 / spec 路径+核销表+安全声明 / 测试情况（两支柱）/ 影响面+回滚）。
- **检查项收敛为两支柱**：① 核心功能没修坏——分级回归（触及核心 → 按 runbook 核心功能清单回归；不触及 → 轻量冒烟：路由可打开 + 无未捕获 JS 异常 + 无 5xx）；② 新功能达标——每条 C 条款至少一个用例。异常路径只测 spec「边界与异常」声明的场景，不再自由发挥。
- **安全审查周期化**：默认每月一次、高危项目每周，输出到项目 `docs/security-review-log.md`；每次变更只做增量检查（有无新增依赖 / 新外部输入面），无新攻击面时 PR 里一句话声明即可。P0 未清零不开工/不发布的规则保留。
- **核心功能清单一次性确认**：首次接入项目时问用户要（核心路由/接口/模块），写进 `docs/deploy-runbook.md`，之后每次变更直接读取，不再每次询问。
- **用户验收闸门放宽**：接受"测试没有问题 / 没问题 / 提交 PR / 发吧"等明确验收表述；回复含糊时主动询问"测试是否无异常？可以进入下一步吗？"。
- **条件附加保留**：鼠标操作路径真实性核销（定位/浮层/菜单/下拉类改动）、UI 坐标断言、一致性复查六项——触发条件不变，编号随新步骤走。
- **`check_spec.py` 适配 8 节 spec 布局**：必需节改为 1 背景与目标 / 2 方案自审 / 3 非目标 / 4 契约条款 / 5 验收标准 / 6 边界与异常 / 7 三问；核销表在第 8 节。**注意：旧布局（6 节 + 第 7 节核销）的 spec 会在新校验器下失败**——主版本升级，属预期行为，旧 spec 按新模板补「方案自审」节即可。
- `references/spec-template.md` 重写为 8 节（新增「方案自审」节：复用盘点 / 决策 / 影响面 / 兼容性 / 成本预算 / 安全增量 / 测试策略）；`references/security-review.md` 重写为周期审查 playbook；`references/self-check.md`、`references/project-adaptation.md` 编号与内容对齐。
