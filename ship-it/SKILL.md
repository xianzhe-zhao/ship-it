# ship-it（开发发布工作流 · 契约模式）

把"用户提需求 → 改完代码 → 发布上线"这件事固化成可核销的流程：**约定先落盘（spec），代码与测试从契约派生，
验收按条款打勾，发布带回滚**。每一步都有产出物和闸门，**不跳步**——尤其不要在用户验收通过前就动生产。

## 文件地图

- `references/security-review.md` — 周期安全审查 playbook：周期、拆解表、信任边界、核验命令、风险清单、日志模板
- `references/spec-template.md` — Step 2 的 spec 模板（含「方案自审」「技术蓝图」节，复制到项目 `docs/specs/_TEMPLATE.md`）
- `references/self-check.md` — Step 3 自检：坐标断言样例、六项判据、两次真实翻车
- `references/project-adaptation.md` — 首次接入项目：两层落地、核心功能清单、编号对齐、目录盘点
- `references/team-mode.md` — 团队模式（v3.1.0+）：角色卡、能力要求表、模型发现流程、派发协议、截图协议、失败降级
- `scripts/check_spec.py` — Step 5 机器校验（`--stage spec|verify`）

## 何时使用

用户提出任何需要**修改代码并最终交付/发布**的需求时启用：

- 修 bug、加功能、重构、改配置、改接口、升级依赖
- 用户说"改一下 XX"、"修复 XX"、"加个 XX 功能"、"优化 XX"、"这个功能安全吗"

**不适用**：纯问答、只读分析、查日志、诊断但不改代码。

## 前置：判断系统形态

| 形态 | 测试系统 | 正式系统 | Step 4 部署测试 | Step 8 发布正式 |
|---|---|---|---|---|
| 单系统 | 无 | 无 | 本地测试即可 | 跳过 |
| 有测试环境 | 有 | 无 | 部署测试系统 | 跳过 |
| 测试 + 正式 | 有 | 有 | 部署测试系统 | 发布正式系统 |

判断方法：查项目文档（README/CLAUDE.md/AGENTS.md）是否提到 test/staging/prod、CI/CD、部署脚本。
不确定时**直接问用户**："这个项目有独立的测试系统和正式系统吗？"

## 团队模式（主脑 + 角色，v3.1.0+）

用户提出需求时，主脑自动判断执行形态：**多文件 / 全栈 / 用户明确要求 → 团队模式**（主脑 + 角色）；
否则主脑单干（mini-spec 快速通道恒单干）。判断结果 + 理由写进 spec「方案自审」节；用户可否决。

- **角色**：需求澄清员 / 后端开发 / 前端开发 / 代码审查员（测试前四项审查）/ 测试员（持久 teammate，截图认证）/ 改动说明员；
  主脑是 spec 唯一 owner、唯一对用户交付的成员
- **模型分配能力驱动**：模型名只存在于项目 runbook「角色分配」配置（skill/代码不写死）；首次组队从宿主模型列表工具或
  设置文件拉取（DSH：读 `~/.dsh/settings.yaml`，**配置可能滞后于实际路由，以实际为准**）+ 联网核实能力 + 探针，
  记入项目 runbook「模型能力清单」（测试员需图像输入，无满足模型 → 主脑核验截图）；列表变动（含实际路由出现未记录模型名）/ 能力异常时增量重扫并更新分配
- **闸门不变**：9 步、核销、用户验收全部保留；团队模式在 Step 3 与 Step 4 之间新增审查闸门（打回 ≤2 轮）
- 角色卡、能力要求表、模型发现流程、派发协议、截图协议、失败降级：见 `references/team-mode.md`

## 周期安全审查（流程外，不按次执行）

> 安全审查是**周期性任务**：默认**每月一次**；对外暴露面大/依赖多的项目可设为**每周一次**（周期记入项目 runbook）。
> 首次使用 / 从未审查过 → 开工前先做一次完整审查。

- **完整核验**（不允许只凭记忆）：`npm audit` + OSV（Python 按 `名称==版本`）+ 官方公告 / GHSA / NVD 原文，判定 P0/P1/P2。
  完整 playbook（需求拆解表、信任边界、核验命令、高频风险清单）见 `references/security-review.md`。
- **结果日志**：记入项目 `docs/security-review-log.md`（日期 / 范围 / 联网核验状态 / P0P1P2 清单 / 结论），入 git。
- **P0 规则**：周期审查发现 P0 → 相关功能未清零不开工/不发布；新增依赖命中已知 P0 → 禁用。
- **增量检查**（Step 2 前，1 分钟）：距上次周期审查有无**新增依赖 / 新外部输入面**？
  - 有 → 只核验增量部分（命令见 `references/security-review.md`），结论写进 spec「方案自审」节
  - 无 → PR 里一行声明："自上次审查（YYYY-MM-DD）无新增攻击面"

## 流程总览（TL;DR）

| 阶段 | 步骤 | 产出物 | 闸门（不通过不得进入下一步） |
|---|---|---|---|
| ① 问清楚 | 1 需求澄清与提示词优化 | 优化后需求 + 澄清记录 | 需求无歧义、技术可行 |
| ② 说清楚 | 2 方案自审 + 技术蓝图 + spec 契约落盘 | 一份 spec（含方案自审/技术蓝图节） | 三问全过；**用户确认 = 签约** |
| ③ 写代码 | 3 编码 + 自检 | 构建通过 | 语法/测试/门禁通过；UI 有坐标断言；六项复查过 |
| ④ 可验证 | 4 测试（两支柱）+ 部署测试系统 | 用例（名字带条款号）+ 回归报告 | 核心没修坏；每条 C 条款都有用例 |
| ⑤ 机器验收 | 5 契约核销表 | 核销表 | 条款 100% 核销；`check_spec.py` 退出码 0 |
| ⑥ 人工验收 | 6 用户按清单打勾 | 用户确认 | 用户明确表示验收通过 |
| ⑦ 交付 | 7 版本号 + PR | PR（核销表 + 回滚卡） | 发布前检查清单全过 |
| ⑧ 生产 | 8 合并后发布正式系统 | 回滚预案 + 端到端验证 | 生产健康 200 + 产物可达 |
| ⑨ 收尾 | 9 清理 + 记录 | CHANGELOG/deploy-log | 无测试/垃圾文件残留 |

## Step 1：需求澄清与提示词优化（**每次做，分轻重**）

> 用户提示词不够好/不准确时，方案自审会在错误前提下盘现有能力、定复用/扩展/新建，后面全浪费。
> 这一步消除"歧义税"：把口语化、缺关键信息、有歧义的需求，变成专业、准确、可执行的需求描述。

**三种手段按需组合**：①联网搜索（`web_search` 搜官方文档/可行方案，确认技术成立）②向用户提问（有歧义点 → 主脑用 `ask_user_question` 一次性问完）③主脑优化（口语化需求重写为专业、准确、可执行描述）。

**输出**：优化后需求描述 → spec 第 1 节；**需求澄清记录**（原始→优化+说明+用户问答）→ spec 第 1 节，**签约时展示给用户**确认"理解对不对"。

**团队模式**：主脑派**需求澄清员** subagent（一次性，不直接面对用户）做联网搜索+分析+输出问题清单；有问题 → 主脑转达用户拿答案；单干时主脑兼任。角色卡见 `references/team-mode.md`。

**分轻重**：清晰需求（一句话说清、熟悉领域）→ 快速过；模糊需求（缺关键要素/涉及不熟悉技术/有歧义）→ 深入；用户说"帮我理一下需求" → 深入做。用户看到优化后的专业表述，间接学到"原来该这么问"。

## Step 2：方案自审 + 技术蓝图 + spec 契约落盘（**签约后编码**）

> 方案自审回答"怎么做"，技术蓝图定"技术契约"，契约条款回答"**做到什么程度算对**"。
> 动手前先做**安全增量检查**（见上文「周期安全审查」）。

### 方案自审（写进 spec 的「方案自审」节，不另出卡片）

1. **现有能力盘点**（必须实际查，不许凭印象）：逐层查——页面/路由、组件、公共逻辑、后端接口、数据表、脚本工具、依赖。
   "去哪查"的目录映射表见 `references/project-adaptation.md` 的「现有能力盘点」一节。
2. **三选一决策**（必须写理由）：

   | 决策 | 条件 | 动作 |
   |---|---|---|
   | **A 复用** | 现有能力直接满足 | 只改配置/数据/文案，不加代码分支 |
   | **B 扩展** | 现有能力约 80% 满足 | 加参数/字段/分支，**保持向后兼容** |
   | **C 新建** | 确实没有，且复用显著增加复杂度 | 新建模块，**必须写"复用成本 vs 新建成本"对比** |

   > 默认 A/B；选 C 不写对比 = 未通过自审。
3. **影响面分析（blast radius）**：用 `grep` 查调用方/表/配置，写进 spec：受影响页面/路由、接口与调用方、
   表/字段（含历史数据）、配置/缓存/端口、回归范围。
   同时回答：最优实现是什么？能否砍掉"以后可能用"的部分？是否引入新状态/并发/权限分支？
   数据模型是否向前兼容（**先加列后删列**，禁止破坏性 DDL）？是否改变接口契约（参数/返回/错误码）？
4. **成本预算**：涉及 LLM/付费 API 时写单次/日上限与限流；不涉及写"无"。
5. **测试策略**：写 **3–5 条可验证的验收条件**（DoD）→ 升格为 C 条款；指明回归范围（核心路由 + 本次影响点）；
   是否需要新增 E2E 断言 / 测试数据（**只允许写测试库**）。

### 技术蓝图（写进 spec 的「技术蓝图」节，按涉及领域填）

编码前定技术契约，避免边写边改。按变更涉及的领域填对应子节，不涉及的写"无变更"：

| 子领域 | 内容 | 为什么要前置 |
|---|---|---|
| **前端** | 页面/组件改动、UI 坐标断言点、设计规范遵循 | 编码前定界面契约 |
| **后端** | 接口契约（参数/返回/错误码）、业务逻辑变更 | 接口契约是前后端协作硬约束 |
| **数据库** | 表/字段变更、向前兼容、迁移脚本 | DDL 破坏性变更要前置审批 |
| **环境依赖** | 新增依赖/服务/配置/端口/环境变量 | 安全增量检查的输入；依赖变更走审批 |

> 项目有 `design.md`/设计规范时前端子节**引用并声明遵守**，没有不强制；团队模式主脑可把子节派给对应角色整合。

### 落盘 spec 契约

路径按项目约定，默认 `docs/specs/YYYY-MM-DD-<英文短名>.md`，模板见 `references/spec-template.md`。

| 节 | 内容 | 作用 |
|---|---|---|
| 1 背景与目标 + 需求澄清记录 | what & why + 需求来源 + 原始需求→优化后需求 | 防做着做着忘为什么；签约确认理解对不对 |
| 2 方案自审 | 复用盘点/决策/影响面/成本预算/测试策略 | 回答"怎么做" |
| 3 技术蓝图 | 前端/后端/数据库/环境依赖 | 定技术契约 |
| 4 非目标 | 明确不做什么 | 防范围蔓延 |
| 5 契约条款 C1/C2/… | 前置/后置/失败/不变式（🔒 标受保护规则） | 测试与验收唯一依据 |
| 6 验收标准 | 可勾选 A1/A2/… | Step 6 用户逐条打勾 |
| 7 边界与异常 | 空/超长/超时/并发/权限不足/不存在 | Step 4 异常路径清单来源 |
| 8 三问完整性检查 + DoR | 见下 | spec 质量闸门 |

> 模板第 9 节「核销记录」在 Step 5 填写，不算"签约前必须写完"的节。

**写条款的四条硬标准**：

1. **可验证**：能写出测试用例或明确的页面断言。写不出 = 愿望，不是条款。
2. **一条一句**：一条条款只描述一个可观察行为，别把"校验 + 落库 + 缓存失效 + 文案"塞进 C1。
3. **不写实现**：写"同名分类不可重复创建，重复返回 409"，不写"用 INSERT IGNORE"。
4. **失败行为必写**：只说成功路径 = 没写完（状态码、错误文案、是否泄露内部信息）。

**受保护规则 🔒**：标 🔒 的业务事实不可被悄悄改——Agent 可补实现细节，改这些事实必须产生显式 Diff 等用户审批（防"同源共错"：实现/测试/验收都由同一 Agent 解释，一致通过却一起偏离业务）。

```markdown
### C1 删除卡片后列表总数同步
- 前置：登录用户，卡片属于当前用户
- 后置：DELETE 返回 200；列表总数 -1；前端无需刷新即更新
- 失败：非本人卡片 → 404（不返回 403，避免泄露存在性）
- 不变式：删除后同列其余卡片 order 连续，不留空洞
```

### 三问完整性检查（答不出任何一问 = 回去补）

① 每个字段的取值范围能否用正则/枚举/数值区间精确描述？
② 有状态的流程能否画成状态机（含触发条件与 guard）？
③ 每个输出的生成逻辑能否用一句话（函数调用）描述？

**DoR 自检**（Definition of Ready，需求清晰到可以进开发）：需求无歧义、技术可行、影响面已盘。

### 签约与 spec-first

- spec 文件**入 git**，随分支提交；
- 向用户汇报路径 + 条款摘要 + **需求澄清记录**，**用户确认 = 签约**，之后才写代码；
- 需求变更先改 spec 再改代码与测试（见关键原则 4）；PR 附 spec 路径，评审可逐条审计。

### 小需求快速通道（避免流程税）

同时满足三条时不建 spec 文件，在 PR 描述里写 4 行 mini-spec：

- 只改 1 个文件，且不改接口契约（参数/返回/错误码）
- 不涉及 DDL、不涉及权限判断、不涉及外部输入
- 影响面为 0（无其他调用方）

```markdown
## mini-spec
- 目标：<一句话>    - 非目标：<一句话>
- 契约：C1 <可验证条款>；C2 <可验证条款>
- 验收：A1 <可勾选>；A2 <可勾选>
```

> 越过任一条件（多文件 / 改接口 / 动表 / 动权限 / 有外部输入）→ 必须走完整 spec。
> **mini-spec 快速通道 Step 1 需求澄清仍做**（轻量），纯文档改动免 spec 但 Step 1 仍适用。
> **资格不可自判**（防偷懒红线 1）：三条门槛由**客观事实**判定（文件数 / 接口签名 / 表结构 / 权限 / 外部输入），不由 agent 主观判断；任一不符 = 必须完整 spec；疑义时走完整 spec 或问用户，**不可自行裁定走 mini-spec**。

**纯文档/流程改动直接免流程**：只改文档/注释/README/skill 说明/脚本文案，**无代码逻辑/接口/数据/权限变化** → 免安全审查与 spec，PR 写「变更摘要 + 影响面（仅文档）」即可。判断口径：**能不能跑到线上产物里**（能 → 走流程；不能 → 免流程，但写清影响面）。
> **资格不可自判**（防偷懒红线 2）："纯文档"资格由客观事实判定，不由 agent 主观判断；**改动涉及流程规则 / skill 本身 / agent 行为约束时不可免流程**，必须走完整 spec（改规则者受规则约束）。

## Step 3：编码 + 自检

### 验证无异常（按项目实际情况，缺的跳过）

```bash
# 语法
node --check <file>.js          # JS
npx tsc --noEmit                # TS
python -m py_compile <file>.py  # Python

# 现有测试 + 项目门禁
npm test / pytest / <项目测试命令>
npm run lint / npm run build    # 有静态闸门就一定跑（能抓"没被引用所以 build 不报错"的坏文件）
```

### UI 视觉自测（**坐标断言，不是属性断言**）

凡涉及 CSS / 布局 / 定位 / 浮层 / 动画的改动必做；纯后端/逻辑跳过。
用 Playwright 量**实际渲染坐标**（`getBoundingClientRect`），断言写成**数值**（"距底部 ≤10px""面板底部 < 选区顶部""45.2 ±1px"），
动画**逐帧采样**；没有 Playwright 就用 DevTools 手量并把数值记进 PR。

> 最小样例与两次真实翻车见 `references/self-check.md`。

### 一致性复查六项（防"改了 A 漏了 B"）

改完逐条过：**注释语言 / 变量声明风格 / 全局引用扫描 / 文档清单同步 / 死代码 / 错误提示准确性**。
判据与典型漏网见 `references/self-check.md`。**只在发现问题时汇报**（发现了什么、修了什么），不逐项写产出。

> 数据：一次代码审查 24 个问题里 17 个 LOW 的根因都是"改完没复查"。

## Step 4：测试（两支柱）+ 部署测试系统

> 原则：**测试从契约派生，不是从代码派生**。代码改了测试跟着改 = 测试失效。

### 支柱 2：新功能达标（契约派生用例）

- 每条 C 条款**至少一个**用例，命名带条款号：`test_c1_delete_card_total`；
- 优先 Python（`requests` 测 HTTP、`pytest`/`unittest` 组织；浏览器路径用 Playwright）；
- 覆盖三组：**新功能**（条款本身）+ **回归**（见下）+ **异常路径**（只测 spec「失败行为」/「边界与异常」节声明的项，不强制通用清单）。

### 支柱 1：核心功能没修坏（分级回归）

- **核心功能清单（一次性）**：首次使用或接入新项目时，若项目 runbook 没有「核心功能清单」→
  问用户"你认为本项目的核心功能（核心页面/路径）是什么"，记入 `docs/deploy-runbook.md`；已有清单直接复用，不重复问。
- **分级**（按本次改动判断）：
  - **触及核心功能**（同页面 / 同模块 / 共用接口 / 共用依赖 / 共用数据表）→ **核心功能回归**：按清单逐条跑（只读）；
  - **不触及** → **轻量冒烟**：改动路由可打开 + 无未捕获 JS 异常 + 无 5xx。
- 两者均**只读**（不发消息、不点删除、不写业务数据）、**只打测试环境**。
- 已有则复用项目脚本（如 `scripts/e2e/core_smoke.py`），没有就写一个最小的；
  输出 `report.json` + `report.md`，**退出码非零代表有 FAIL**。

### 测试路径真实性核销（条件：定位/浮层/菜单/下拉类改动）

- 用例的**操作方式必须与用户真实操作一致**：鼠标拖选/点击/键盘输入，而不是
  `editor.chain().setTextSelection()`、`element.click()`、直接改 store 之类的捷径；
- 涉及定位/浮层/菜单/下拉的改动，**必须**真实鼠标触发（`page.mouse.move/down/up`）；
- 技术限制必须用 API 捷径时，**额外补一个"模拟用户鼠标"的对照用例**验证两条路径一致；不一致以用户路径为准。

> 根因教训（2026-10-30 对齐菜单翻车）：用 API 设选区测"面板向上弹"PASS，但用户用鼠标拖选时场景不同，实际没上弹。**API 路径通过 ≠ 用户路径通过**。

### 部署测试系统 + 跑回归（仅当项目有测试系统时）

```bash
# 用项目既有部署脚本，不要手搓（测试环境优先）
<deploy 脚本> -Target test      # 或 ./deploy.sh test / make deploy-test
```

**若部署脚本不可用**，手动部署的要点：**先传到临时位置校验，再原子换目录**，
禁止覆盖式解压（旧产物堆积会导致 404 / 页面转圈）。后端先 `cp -p` 备份再覆盖单个文件，只重启改动的服务。

在测试系统上跑分级回归。判定：**FAIL = 0** 才继续；FAIL > 0 先修，把报告失败项贴给用户；WARN 需人工看截图确认。

**放置与清理**：

- 可复用回归用例 → 项目测试目录（如 `scripts/e2e/`、`tests/`）；一次性脚本 → `tmp/`，**Step 9 必须删掉**；
- 自动化测试禁止打生产、禁止发真实 AI 消息（产生费用）、禁止写业务数据（只写测试库）。

## Step 5：契约核销表（必须 100%）

```markdown
| 条款 | 测试用例 | 结果 | 路径真实性 |
|---|---|---|---|
| C1 | `test_c1_delete_card_total` | ✅ | 鼠标 |
| C2 | `test_c2_409_duplicate` | ✅ | API + 鼠标对照 |
- 核销率：2/2；分级回归：PASS n / WARN 0 / FAIL 0（报告路径）
```

有未覆盖条款 = 测试不合格，补用例重跑。

**机器校验（必做）**：在项目根执行下面的命令（`--stage spec` 用于签约前查结构）：

```bash
python <skill目录>/scripts/check_spec.py docs/specs/<文件> --stage verify
# skill 目录通常为 ~/.agents/skills/ship-it
```

它会核对：条款编号连续、每条含前置/后置/失败/不变式、验收项编号连续、三问已勾、
核销表的「用例名带条款号 / 结果 ✅ / 路径真实性已填」。**非零退出 = 核销不合格**，别急着通知用户。

## Step 6：请用户验收（按清单打勾，不替用户下结论）

> 自动化通过 ≠ 可以发布。

汇报必含 5 项：

1. **重点变更**：改了什么、为什么、影响范围（一句话说清就不要长篇）
2. **验收标准清单**：贴 spec 第 6 节，让用户逐条打勾（按契约验收，不凭印象）
3. **测试步骤与预期**：怎么点、用什么账号、应看到什么
4. **回滚方式**：改坏了怎么退
5. **明确请求**："请按上面流程测一下，有问题告诉我"

```markdown
## 测试环境已更新（vX.Y.Z）
- 地址：<URL>    账号：<...>
- 分级回归：PASS n / WARN n / FAIL 0（报告：<路径>）
- spec：docs/specs/<文件>

### 请按验收标准打勾
- [ ] A1 <预期...>
- [ ] A2 <预期...>

### 回归检查（每项约 1 分钟）
- [ ] 登录 → 首页
- [ ] <核心路径 1> / <核心路径 2> / <核心路径 3>

> 请先强刷（Ctrl+Shift+R）；有问题把截图或操作时间点发我。
```

**验收判定**：接受任何明确表示验收通过的表述——"测试没问题"、"没问题"、"提交 PR"、"发吧"等都算通过；
用户回复含糊、不能确定其已测试通过时 → **主动询问**："测试是否无异常？可以进入下一步吗？"得到明确肯定才进 Step 7。

**遇阻即停**：用户发现问题 → 回 Step 2 改 spec（spec-first）→ 改代码 → 重跑 4/5 → 重新验收。
不要带病推进，也不要顺手加需求。

## Step 7：版本号 + PR

### 版本号

先找项目的版本来源：`package.json` / `pyproject.toml` / `VERSION` / `CHANGELOG.md` 顶部 / git tag。
有则按 SemVer 递增，无则从 `1.0.0` 起。**在项目里明确唯一来源，别让两处版本号打架**
（很多项目的 `package.json` version 与发布版本无关，此时以 CHANGELOG/deploy-log 为准）。

### 提交 + PR

```bash
git checkout main && git pull
git checkout -b feature/<简短描述>      # fix/xxx、chore/xxx
git add -A
git commit -m "<type>(<scope>): <摘要> [v<版本号>]"
git push origin <branch>
gh pr create --base main --head <branch> --title "<标题>" --body "<描述>"
```

> `git push` 不可用（公司代理/网络限制）时：改用项目既有的 push 脚本或其他可用的上传方式。

PR 说明四块缺一不可：

```markdown
## 版本号：vX.Y.Z
## 变更摘要：<一句话>

### spec 契约
- 文件：docs/specs/<...>（含方案自审/技术蓝图节；或 PR 内 mini-spec）
- 安全：自上次审查（YYYY-MM-DD）无新增攻击面 / 增量核验结论 <...>
- 契约核销表：<逐条 ✅>

### 测试情况
- 两支柱：核心功能 <分级回归结果> + 新条款 <用例数/通过数>
- 测试环境：<用户已验证的项>

### 影响范围 / 兼容性 / 回滚方式
```

## Step 8：合并后发布正式系统（含回滚预案）

> **合并前不碰生产**（代码、数据库、缓存、进程都算）。没有正式系统则跳过本步。

### 回滚预案（部署前先填，不填不部署）

| 项 | 记录 |
|---|---|
| 当前生产版本 | <commit / tag / 构建号> |
| 上次可用产物 | <目录/镜像/包路径> |
| 最新数据备份 | <备份文件路径；太旧就先做一次> |
| 回滚触发条件 | 登录失败 / 核心页面空白 / 接口 5xx 持续 >1% / 数据错乱 |
| 回滚动作 | 前端：换回旧产物目录；后端：回退文件并重启对应服务；数据：按备份恢复 |

### 发布 + 端到端验证（缺一不可）

```bash
# 1. 服务/进程状态
<pm2 list / docker ps / systemctl status>
# 2. 源站健康检查
curl -s http://127.0.0.1:<port>/health
# 3. 对外入口端到端（不能只测本地）
curl -s -o /dev/null -w 'HTTP %{http_code} - %{time_total}s' https://<域名>/
# 4. 产物 hash 对比（确认外网拿到的是新版本）
#    本地: ls dist/assets/index-*.js   远端: curl -s https://<域名>/ | grep -o 'index-[a-zA-Z0-9_-]*\.js'
# 5. 入口资源可达
curl -s -o /dev/null -w "chunk: %{http_code}\n" "https://<域名>/<入口chunk>"
```

**服务类安全规则**（通用）：

- ❌ 禁止 `pm2 kill` / `pm2 delete all` / `pm2 delete` 不带服务名；只操作具体服务名
- ✅ 操作前先 `pm2 list` 确认当前状态；重启后确认全部 online
- ✅ 前端部署"先清后放"（原子换目录），禁止在旧产物上覆盖
- ✅ 部署前确认目标路径（测试 vs 生产），并确认基线 commit 已合入 main
- ❌ 凭据（`.env` 值、口令、密钥）一律不写进文档、脚本、commit；需要时写"见服务器 `.env`"

> ⚠️ 耗时**不能**作为部署失败判据（跨境链路可能 10–60s）。看 **状态码 + 产物大小/hash** 是否与本地一致；
> 有内网/VPN 入口优先用它验证。

## Step 9：清理 + 变更记录

1. 删远程/本地已合并分支：`git push origin --delete <branch>` / `git branch -d <branch>`
2. **垃圾零容忍**：一次性测试脚本、诊断脚本、临时日志、截图、`.bak` 备份全部清掉；
   `git status` 只剩有意提交的文件；确认 `.gitignore` 覆盖到位
3. 写变更记录（`CHANGELOG.md` 顶部或项目既有的 `deploy-log.md`）：

```markdown
## YYYY-MM-DD <变更标题>（vX.Y.Z）
### 变更内容
**PR #N**：
- **feat/fix**: 具体改动
### 测试环境验证（YYYY-MM-DD HH:MM）
- 实测数据（数值/接口返回/回归结果）
### 生产部署与验证（YYYY-MM-DD HH:MM）
- 部署方式、commit、服务状态、端到端验证、回滚基线
```

4. 同步受影响的文档（端口/表结构/接口/文件清单）
5. 向用户汇报：合并的 PR、版本号、生产状态、清理结果、**请强刷提示**

## 版本号规则

| 类型 | 递增 | 示例 |
|---|---|---|
| Bug 修复 | patch | `1.4.2` → `1.4.3` |
| 新功能 | minor | `1.4.3` → `1.5.0` |
| 破坏性更新（DB schema / API 不兼容） | major | `1.5.0` → `2.0.0` |

破坏性变更必须在变更摘要里显式标注 ⚠️。

## 关键原则

1. **不跳步**：Step 6 用户验收不能省——自动化通过 ≠ 用户验收通过。
2. **每步汇报**：每完成一步就汇报（做了什么 / 结果 / 下一步），不要闷头做完整个流程才说话。
3. **遇阻即停**：任何一步失败停下修或等指示，不带病推进。
4. **spec-first**：需求变更先改 spec，再派生代码与测试。
5. **默认复用**：A/B 优先，选 C 新建必须写成本对比。
6. **自测两层性**：①逻辑正确（条款核销）②路径真实（鼠标操作 + 坐标断言）。只过第一层就交付 = 返工。
7. **垃圾文件零容忍**：收尾必须复查，临时脚本/截图/备份不留仓库。
8. **凭据纪律**：口令/密钥不进文档/脚本/commit。
9. **测试只读、只打测试环境**：不写业务数据、不发付费请求、不对生产执行。
10. **禁止自证**：agent 不可自判合规，关键节点（mini-spec 资格 / 纯文档免流程资格 / 核销✅ / 能力声明）必须**机器可查或用户确认**。执行者 ≠ 裁定者——agent 可执行但不可自判通过 🔒。详见下方「反偷懒红线」。

## 常见坑（通用根因，来自真实事故）

| 坑 | 表现 | 对策 |
|---|---|---|
| 需求没澄清就做方案 | 在错误前提下盘能力、定复用，全浪费 | Step 1 需求澄清（每次做） |
| 只测 happy path | 流式错误收集没监听 error、损坏配置被静默覆盖、解析失败被 catch 吞掉 | Step 4 异常路径（按 spec 声明） |
| 属性断言当视觉验收 | CSS 属性对了但视觉错位 | Step 3 坐标数值断言 |
| API 捷径当用户路径 | 脚本过、用户操作不过 | Step 4 路径真实性核销 |
| 改完不复查 | 英文注释遗留、`var`/`const` 混用、迁移漏改引用点、新增文件没进文档清单 | Step 3 六项复查 |
| 部署"看起来成功" | 覆盖式解压旧产物堆积、变更检测为空导致静默不部署、tar 报错被忽略 | 原子换目录 + 明确基线 + 失败即中止 |
| 用耗时判断部署成败 | 链路慢被误判为部署失败，反复回滚 | 看状态码 + 产物 hash/大小 |
| 版本号两处打架 | `package.json` 与 CHANGELOG 各说一套 | Step 7 明确唯一来源 |
| 没回滚预案 | 出事时不知道退到哪 | Step 8 回滚卡 |

## 反偷懒红线（防契约逃逸，配合关键原则 10「禁止自证」）

> agent 既是执行者又自判合规 = "同源共错"。下面四种偷懒路径，每种都加"不可自判"约束。
> 开工前逐条自检；命中任一 = 必须走完整 spec 或问用户，**不可自行裁定走捷径**。

| # | 偷懒场景 | 表现 | 红线（不可自判） |
|---|---|---|---|
| 1 | **滥用 mini-spec 快速通道** | 多文件 / 改接口 / 动表 / 动权限 / 有外部输入，却声称"只改 1 个文件"走 mini-spec | mini-spec 三条门槛由**客观事实**判定（文件数 / 接口签名 / 表结构 / 权限 / 外部输入），不由 agent 主观判断；任一不符 = 必须完整 spec；疑义时走完整 spec 或问用户（见 Step 2 mini-spec 节） |
| 2 | **滥用纯文档免流程** | 有逻辑 / 接口 / 数据 / 权限变化的改动说成"纯文档"免安全审查免 spec | 判断口径"能不能跑到线上产物里"由客观事实判定；**改动涉及流程规则 / skill 本身 / agent 行为约束时不可免流程**，必须走完整 spec（见 Step 2 纯文档免流程节） |
| 3 | **跳过需求澄清** | 声称"需求很清楚"直接做方案，Step 1 走过场 | Step 1 每次做、分轻重——清晰需求快速过 ≠ 跳过；需求澄清记录（原始→优化+问答）必须进 spec 第 1 节，签约时展示给用户确认 |
| 4 | **测试从代码派生 / 核销表自填✅** | 改了代码顺手改测试使测试永远过；或没真跑用例 / 没覆盖就在核销表打✅ | 测试从契约派生不从代码派生（代码改了测试跟着改 = 测试失效）；核销表✅必须有对应用例名 + 路径真实性 + 报告路径，`check_spec.py` 机器校验退出码 0；agent 不可自判核销通过 |

## 项目适配（首次接入 / 换项目时）

默认**两层**：本 skill 管流程；项目 `CLAUDE.md`/`AGENTS.md` 写约定与红线；`docs/deploy-runbook.md` 写环境值、部署/回退/验证命令与回滚卡、**核心功能清单**；`docs/specs/_TEMPLATE.md` 存模板。
**不要给项目再造一份流程 skill**（两份必然漂移，还会互抢触发）。

> 逐项替换清单、核心功能清单、编号对齐、保密要求、例外条件与接入检查清单见 `references/project-adaptation.md`。
> `examples/baobao-deploy/SKILL.md`（仓库根目录下，不在本 skill 目录内）是 v2.0.0 时期项目级 skill 的历史快照（已脱敏），**不代表当前推荐做法**。
