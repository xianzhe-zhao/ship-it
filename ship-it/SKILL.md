# ship-it（开发发布工作流 · 契约模式）

把"用户提需求 → 改完代码 → 发布上线"这件事固化成可核销的流程：**约定先落盘（spec），代码与测试从契约派生，
验收按条款打勾，发布带回滚**。每一步都有产出物和闸门，**不跳步**——尤其不要在用户验收通过前就动生产。

## 文件地图

- `references/security-review.md` — 周期安全审查 playbook：周期、拆解表、信任边界、核验命令、风险清单、日志模板
- `references/security-kb.md` — 代码安全员安全审查库（v4.6.0+）：OSV/GHSA/NVD/KEV/EPSS/EOL 数据源、SonarQube 可选适配、SAST/SCA/密钥/IaC 工具矩阵、严重度规则、报告模板、更新机制、离线降级
- `references/spec-template.md` — Step 2 的 spec 模板（含「方案自审」「技术蓝图」节，复制到项目 `docs/specs/_TEMPLATE.md`）
- `references/self-check.md` — Step 3 自检：坐标断言样例、六项判据、两次真实翻车
- `references/project-adaptation.md` — 首次接入项目：两层落地、核心功能清单、编号对齐、目录盘点
- `references/team-mode.md` — 团队模式（v3.1.0+）：角色卡、能力要求表、模型发现流程、派发协议（含运行时模型决策 v4.5.0+）、代码安全员/审查员/裁判员（v4.6.0+）、角色按需启用矩阵、目标驱动编排（v4.4.0+，可选）、截图协议、失败降级
- `scripts/check_spec.py` — Step 5 机器校验（`--stage spec|verify`）

## 何时使用

用户提出任何需要**修改代码并最终交付/发布**的需求时启用：

- 修 bug、加功能、重构、改配置、改接口、升级依赖
- 用户说"改一下 XX"、"修复 XX"、"加个 XX 功能"、"优化 XX"、"这个功能安全吗"

**不适用**：纯问答、只读分析、查日志、诊断但不改代码。

## 前置：判断系统形态

| 形态 | 测试系统 | 正式系统 | Step 4 部署测试 | Step 8 发布正式 |
|---|---|---|---|---|
| 单系统 | 无 | 无 | 本地测试即可 | 跳过 |
| 有测试环境 | 有 | 无 | 部署测试系统 | 跳过 |
| 测试 + 正式 | 有 | 有 | 部署测试系统 | 发布正式系统 |

判断方法：查项目文档（README/CLAUDE.md/AGENTS.md）是否提到 test/staging/prod、CI/CD、部署脚本。
不确定时**直接问用户**："这个项目有独立的测试系统和正式系统吗？"

### 部署通道（v4.2.0+，与系统形态正交）

在系统形态之外，还要判定**部署通道**：**手动/脚本部署**（agent 主动执行部署脚本）还是 **CI/CD 自动发布**（分支推送/合并即触发流水线自动部署）。

- **判定依据**：查项目文档与流水线配置文件（`.github/workflows/`、`.gitlab-ci.yml` 等）中是否存在**分支→环境的部署映射**（如 test 分支→测试环境、main 分支→生产环境）。只有跑测试/构建、没有部署 job 的流水线**不算** CI/CD 自动发布通道。
- 判定为 CI/CD 自动发布 → 把 **分支→环境→workflow 名**的映射记入项目 `docs/deploy-runbook.md`；Step 4/6/8 一律按该映射执行，不猜。
- 文档与流水线文件均无法判定时**直接问用户**，不得默认假设任一通道。

## 团队模式（主脑 + 角色，v3.1.0+）

用户提出需求时，主脑自动判断执行形态：**多文件 / 全栈 / 用户明确要求 → 团队模式**（主脑 + 角色）；
否则主脑单干（mini-spec 快速通道恒单干）。判断结果 + 理由写进 spec「方案自审」节；用户可否决。

- **角色**：需求澄清员 / 后端开发（遵循后端+数据库标准）/ 前端开发（遵循 `design.md`，无则先问是否建立标准）/ 代码安全员（代码审查+安全检查，团队模式必执行）/ 审查员（异常与偷懒审查）（图像输入优先，审查员是主脑唯一汇总接口）/ 裁判员（测试+审查/安全通过后审契约，不审代码/不测试）/ 测试员（只做验收测试，不审代码）；
  主脑是 spec 唯一 owner、唯一对用户交付的成员，只派活/决策/回复用户；单写「审查员」指异常与偷懒审查角色，安全职责一律写「代码安全员」；**改动说明员已删除，Step 6 五项报告由主脑汇总团队产出后起草**
- **模型派发运行时自适应（v4.5.0+）**：默认路由优先——派发 subagent 不指定模型，由宿主默认路由/继承会话模型决定；仅硬能力不满足（测试员需图像输入 🔒，实测为证）或用户显式要求（省钱/指定模型）时，
  查**本会话实际放行集合**（DSH：`list_subagent_models`；**配置可能滞后于实际路由，以本会话实测为准**）按硬能力 > 软能力 > 性价比动态挑选（DSH 显式指定入口：`workflow` 的 `agent(prompt,{provider,model})`）；
  路由不可用自动回退并在汇报注明，不停摆、不人工改分配表；模型能力/成本/默认路由记入项目 runbook「模型能力清单」（**不维护角色分配表**，skill 正文零模型名）；清单变动（含实际路由出现未记录模型名）/ 能力异常 / 价格折扣变动时增量重扫
- **闸门不变**：9 步、核销、用户验收全部保留；团队模式在 Step 3 与 Step 4 之间保留 J2 流程/文档闸门（不审代码），Step 4 后由测试员只做验收测试、代码安全员代码审查+安全检查，裁判员 J3/J4 在测试+安全通过后审契约（打回 ≤2 轮）
- **监督角色（v4.6.0+）**：**审查员是主脑唯一汇总接口**，默认每 1 分钟主动巡视所有成员（含主脑/裁判员/代码安全员/测试员/开发），收集开发/测试/安全/裁判报告，整理给主脑；发现 inactive 未完成、主脑 idle 有剩余任务、running 无进展即催办/上报，可直发 `continue`/`retry_same`，换模型/换范围/新派发交主脑，同一任务初次 + 2 次重试 = 3 次尝试，仍失败带证据上报；**主脑不持续轮询，但 5 分钟无审查员消息 → 主动询问/唤醒审查员重试；审查员 5 分钟无主脑确认 → 再次上报/唤醒主脑**；宿主不支持持久 teammate/定时 → 事件触发巡视并声明「无主动定时巡视」降级；**测试员只做验收测试**（按 spec + `design.md`/后端/数据库标准；浏览器真实操作+截图，Playwright 提前适配）；**代码安全员代码审查+安全检查**；**裁判员不审代码/不测试**，只在测试+审查/安全通过后审契约并核查安全检查是否通过，裁判单报审查员汇总；审查员图像输入优先，图片交主脑决定临时识图子智能体；**需求模糊/跳过需求澄清员 → 主脑+审查员+裁判员契约互审（至少 1 轮）后再向用户总结**；**审查员汇总每个子代理报告前必须分析并至少反问 1 个问题，主脑可反向质疑，未解决不呈现**；主脑是用户唯一对接人，用户提问优先回复，不亲自开发/测试/审代码
- **角色按需启用矩阵（v4.6.0+）**：形态 0 单干 / 1 小改 / 2 中改 / 3 大改高风险；需求澄清员按需、代码安全员/审查员/裁判员/测试员团队模式必须执行（主脑单干例外且自测）、前后端只派相关侧；深度安全审计/方案评审/发布验证为可选专项，不新增常设角色。选择写进 spec「方案自审」
- **目标驱动编排（v4.4.0+，可选增强）**：签约时**问用户**是否启用"目标 + 任务树"（主脑不代选）；启用则 `create_goal` +
  按 Step 1–9 分组建任务树（叶子为可检查动作、节点 ≤40）、派发带 `Timeline: tree=…; tasks=…` 标识与完成标准、每步把进度/阻塞写回树，
  Step 5 核销表增加「目标树」机器校验行，Step 6 用户验收后关闭目标。**收益**：进度外置、跨中断可恢复（重读上千行文档 → 一次 `timeline_pull`）；
  **成本**：工具净内容 8k–25k token/需求，小改动为负收益。细节见 `references/team-mode.md`「目标驱动编排」节
- **subagent 派发权限预检（反越权红线 #6）**：派发前判定任务类型——**只读**（扫描/分析/审查/裁判/出报告）→ 可派；**写任务**（改代码/写文件）→ 先确认子代理会话有写权限（never-ask/受限权限模式下子代理的写操作会被自动拒绝，**派了必白跑**）。**派发失败**（权限/路由/工具缺失）→ 同类失败一次后主脑自做；**执行失败**（已跑但报错/超时/空产出）→ 按审查员分诊重试/续派，受「初次 + 2 次重试 = 3 次尝试」上限约束；**审计角色例外**：审查员失败 → 主脑内联并声明「无独立审查」；裁判员失败 → 换新 subagent/`workflow`，仍失败报用户，不得自判 PASS。附注：子代理即便跑完也可能只带回元信息不带回正文报告——要求"最终消息必须包含完整产出物"，首轮就丢报告的代理换主脑直做
- 角色卡、能力要求表、模型发现流程、派发协议、截图协议、失败降级：见 `references/team-mode.md`

## 周期安全审查（流程外，不按次执行）

> 安全审查是**周期性任务**：默认**每月一次**；对外暴露面大/依赖多的项目可设为**每周一次**（周期记入项目 runbook）。
> 首次使用 / 从未审查过 → 开工前先做一次完整审查。

- **完整核验**（不允许只凭记忆）：`npm audit` + OSV（Python 按 `名称==版本`）+ 官方公告 / GHSA / NVD 原文，判定 P0/P1/P2。
  完整 playbook（需求拆解表、信任边界、核验命令、高频风险清单）见 `references/security-review.md`。
- **结果日志**：记入项目 `docs/security-review-log.md`（日期 / 范围 / 联网核验状态 / P0P1P2 清单 / 结论），入 git。
- **P0 规则**：周期审查发现 P0 → 相关功能未清零不开工/不发布；新增依赖命中已知 P0 → 禁用。
- **增量检查**（Step 2 前，1 分钟）：距上次周期审查有无**新增依赖 / 新外部输入面**？
  - 有 → 只核验增量部分（命令见 `references/security-review.md`），结论写进 spec「方案自审」节
  - 无 → PR 里一行声明："自上次审查（YYYY-MM-DD）无新增攻击面"

## 流程总览（TL;DR）

| 阶段 | 步骤 | 产出物 | 闸门（不通过不得进入下一步） |
|---|---|---|---|
| ① 问清楚 | 1 需求澄清与提示词优化 | 优化后需求 + 澄清记录 | 需求无歧义、技术可行 |
| ② 说清楚 | 2 方案自审 + 技术蓝图 + spec 契约落盘 | 一份 spec（含方案自审/技术蓝图节） | 三问全过；**用户确认 = 签约** |
| ③ 写代码 | 3 编码 + 自检 | 构建通过 | 语法/测试/门禁通过；UI 有坐标断言；六项复查过 |
| ④ 可验证 | 4 测试（两支柱）+ 部署测试系统 | 用例（名字带条款号）+ 回归报告 | 核心没修坏；每条 C 条款都有用例 |
| ⑤ 机器验收 | 5 契约核销表 | 核销表 | 条款 100% 核销；`check_spec.py` 退出码 0；启用目标时目标树 Step 1–5 100%（全树于 Step 9 收尾） |
| ⑥ 人工验收 | 6 用户按清单打勾 | 用户确认 | 用户明确表示验收通过 |
| ⑦ 交付 | 7 版本号 + PR | PR（核销表 + 回滚卡） | 发布前检查清单全过 |
| ⑧ 生产 | 8 合并后发布正式系统 | 回滚预案 + 端到端验证 | 生产健康 200 + 产物可达 |
| ⑨ 收尾 | 9 清理 + 记录 | CHANGELOG/deploy-log | 无测试/垃圾文件残留 |

> **团队模式监督闸门（v4.6.0+）**：代码安全员必执行；审查员按异常/偷懒介入；裁判员 J1 签约前 / J2 编码后 / J3 核销前 / J4 验收前（BLOCK 可阻断下一步；PASS 不替代用户验收与 `check_spec.py`）。9 步编号与用户验收归属不变（见 `references/team-mode.md`）。

## Step 1：需求澄清与提示词优化（**每次做，分轻重**）

> 用户提示词不够好/不准确时，方案自审会在错误前提下盘现有能力、定复用/扩展/新建，后面全浪费。
> 这一步消除"歧义税"：把口语化、缺关键信息、有歧义的需求，变成专业、准确、可执行的需求描述。

**三种手段按需组合**：①联网搜索（`web_search` 搜官方文档/可行方案，确认技术成立）②向用户提问（有歧义点 → 主脑用 `ask_user_question` 一次性问完）③主脑优化（口语化需求重写为专业、准确、可执行描述）。

> 🔴 **跨仓库主体确认（反越权红线 #4）**：需求涉及 ≥2 个仓库/项目时（如"规范在 A
> 项目、要改 B 项目"），必须显式确认**"规范基准是哪个项目？改动对象是哪个项目？"**
> 并写进需求澄清记录——弄反主体会让整套工作做在错误对象上（真实事故：用户要改
> 豹豹助手，agent 却把 living-styleguide 改了一整套）。

**输出**：优化后需求描述 → spec 第 1 节；**需求澄清记录**（原始→优化+说明+用户问答）→ spec 第 1 节，**签约时展示给用户**确认"理解对不对"。

**团队模式**：**按需**派**需求澄清员** subagent（一次性，不直接面对用户）做联网搜索+分析+输出问题清单；清晰需求/小改由主脑兼任；有问题 → 主脑转达用户拿答案；单干时主脑兼任。**需求模糊或跳过需求澄清员 → 主脑组织审查员/裁判员契约互审（至少 1 轮）后再向用户总结最终契约**。角色卡见 `references/team-mode.md`。

**分轻重**：清晰需求（一句话说清、熟悉领域）→ 快速过；模糊需求（缺关键要素/涉及不熟悉技术/有歧义）→ 深入；用户说"帮我理一下需求" → 深入做。用户看到优化后的专业表述，间接学到"原来该这么问"。

## Step 2：方案自审 + 技术蓝图 + spec 契约落盘（**签约后编码**）

> 方案自审回答"怎么做"，技术蓝图定"技术契约"，契约条款回答"**做到什么程度算对**"。
> 动手前先做**安全增量检查**（见上文「周期安全审查」）。

### 方案自审（写进 spec 的「方案自审」节，不另出卡片）

1. **现有能力盘点**（必须实际查，不许凭印象）：逐层查——页面/路由、组件、公共逻辑、后端接口、数据表、脚本工具、依赖。
   "去哪查"的目录映射表见 `references/project-adaptation.md` 的「现有能力盘点」一节。
2. **三选一决策**（必须写理由）：

   | 决策 | 条件 | 动作 |
   |---|---|---|
   | **A 复用** | 现有能力直接满足 | 只改配置/数据/文案，不加代码分支 |
   | **B 扩展** | 现有能力约 80% 满足 | 加参数/字段/分支，**保持向后兼容** |
   | **C 新建** | 确实没有，且复用显著增加复杂度 | 新建模块，**必须写"复用成本 vs 新建成本"对比** |

   > 默认 A/B；选 C 不写对比 = 未通过自审。
3. **影响面分析（blast radius）**：用 `grep` 查调用方/表/配置，写进 spec：受影响页面/路由、接口与调用方、
   表/字段（含历史数据）、配置/缓存/端口、回归范围。
   同时回答：最优实现是什么？能否砍掉"以后可能用"的部分？是否引入新状态/并发/权限分支？
   数据模型是否向前兼容（**先加列后删列**，禁止破坏性 DDL）？是否改变接口契约（参数/返回/错误码）？
4. **成本预算**：涉及 LLM/付费 API 时写单次/日上限与限流；不涉及写"无"。
5. **测试策略**：写 **3–5 条可验证的验收条件**（DoD）→ 升格为 C 条款；指明回归范围（核心路由 + 本次影响点）；
   是否需要新增 E2E 断言 / 测试数据（**只允许写测试库**）。

### 技术蓝图（写进 spec 的「技术蓝图」节，按涉及领域填）

编码前定技术契约，避免边写边改。按变更涉及的领域填对应子节，不涉及的写"无变更"：

| 子领域 | 内容 | 为什么要前置 |
|---|---|---|
| **前端** | 页面/组件改动、UI 坐标断言点、设计规范遵循 | 编码前定界面契约 |
| **后端** | 接口契约（参数/返回/错误码）、业务逻辑变更 | 接口契约是前后端协作硬约束 |
| **数据库** | 表/字段变更、向前兼容、迁移脚本 | DDL 破坏性变更要前置审批 |
| **环境依赖** | 新增依赖/服务/配置/端口/环境变量 | 安全增量检查的输入；依赖变更走审批 |

> 项目有 `design.md`/设计规范时前端子节**引用并声明遵守**，没有不强制；团队模式主脑可把子节派给对应角色整合。

### 落盘 spec 契约

路径按项目约定，默认 `docs/specs/YYYY-MM-DD-<英文短名>.md`，模板见 `references/spec-template.md`。

| 节 | 内容 | 作用 |
|---|---|---|
| 1 背景与目标 + 需求澄清记录 | what & why + 需求来源 + 原始需求→优化后需求 | 防做着做着忘为什么；签约确认理解对不对 |
| 2 方案自审 | 复用盘点/决策/影响面/成本预算/测试策略 | 回答"怎么做" |
| 3 技术蓝图 | 前端/后端/数据库/环境依赖 | 定技术契约 |
| 4 非目标 | 明确不做什么 | 防范围蔓延 |
| 5 契约条款 C1/C2/… | 前置/后置/失败/不变式（🔒 标受保护规则） | 测试与验收唯一依据 |
| 6 验收标准 | 可勾选 A1/A2/… | Step 6 用户逐条打勾 |
| 7 边界与异常 | 空/超长/超时/并发/权限不足/不存在 | Step 4 异常路径清单来源 |
| 8 三问完整性检查 + DoR | 见下 | spec 质量闸门 |

> 模板第 9 节「核销记录」在 Step 5 填写，不算"签约前必须写完"的节。

**写条款的四条硬标准**：

1. **可验证**：能写出测试用例或明确的页面断言。写不出 = 愿望，不是条款。
2. **一条一句**：一条条款只描述一个可观察行为，别把"校验 + 落库 + 缓存失效 + 文案"塞进 C1。
3. **不写实现**：写"同名分类不可重复创建，重复返回 409"，不写"用 INSERT IGNORE"。
4. **失败行为必写**：只说成功路径 = 没写完（状态码、错误文案、是否泄露内部信息）。

**受保护规则 🔒**：标 🔒 的业务事实不可被悄悄改——Agent 可补实现细节，改这些事实必须产生显式 Diff 等用户审批（防"同源共错"：实现/测试/验收都由同一 Agent 解释，一致通过却一起偏离业务）。

```markdown
### C1 删除卡片后列表总数同步
- 前置：登录用户，卡片属于当前用户
- 后置：DELETE 返回 200；列表总数 -1；前端无需刷新即更新
- 失败：非本人卡片 → 404（不返回 403，避免泄露存在性）
- 不变式：删除后同列其余卡片 order 连续，不留空洞
```

### 三问完整性检查（答不出任何一问 = 回去补）

① 每个字段的取值范围能否用正则/枚举/数值区间精确描述？
② 有状态的流程能否画成状态机（含触发条件与 guard）？
③ 每个输出的生成逻辑能否用一句话（函数调用）描述？

**DoR 自检**（Definition of Ready，需求清晰到可以进开发）：需求无歧义、技术可行、影响面已盘。

### 签约与 spec-first

- spec 文件**入 git**，随分支提交；
- 向用户汇报路径 + 条款摘要 + **需求澄清记录**，**用户确认 = 签约**，之后才写代码；
- **团队模式签约前过裁判员 J1**：裁判员检查 spec 结构/用户约束/条款可验证性/角色矩阵；J1 BLOCK 不得请用户签约；J1 结论附入签约汇报；**所有需要用户拍板的选项必须在正文完整列出**（不得只依赖工具 UI）；
- **团队模式签约时顺带问一句**："本次是否启用目标管理（目标 + 任务树）？"——用户选择写进 spec 需求澄清记录；
  **未答 / 不启用 = 不创建目标**，主脑不得代选（见 `references/team-mode.md`「目标驱动编排」）；
- 需求变更先改 spec 再改代码与测试（见关键原则 4）；PR 附 spec 路径，评审可逐条审计。

### 执行中需求变更 / 重签约（v4.6.0+）

用户在执行中追加/修改需求时：

1. **主脑先回应用户**（当前状态/影响/下一步），不得沉默；
2. **回 Step 2 改 spec（spec-first）**，更新契约/验收/范围；
3. **通知审查员暂停所有子智能体新工作**、保留已有产出、待命；审查员盘点进度并汇总主脑；
4. **暂停期间不跑旧契约**；宿主无中断能力 → 等在跑子智能体到安全点/自然结束，只停止新派发，记录「未能立即停住」；
5. **更新契约给用户重新签约**，签约后才继续；
6. 审查员汇报最新进度，主脑按角色判断**继续/重派**（如后端不需要重开发可继续）；受影响闸门（J1–J4/测试/安全）重跑。

### 小需求快速通道（避免流程税）

同时满足三条时不建 spec 文件，在 PR 描述里写 4 行 mini-spec：

- 只改 1 个文件，且不改接口契约（参数/返回/错误码）
- 不涉及 DDL、不涉及权限判断、不涉及外部输入
- 影响面为 0（无其他调用方）

```markdown
## mini-spec
- 目标：<一句话>    - 非目标：<一句话>
- 契约：C1 <可验证条款>；C2 <可验证条款>
- 验收：A1 <可勾选>；A2 <可勾选>
```

> 越过任一条件（多文件 / 改接口 / 动表 / 动权限 / 有外部输入）→ 必须走完整 spec。
> **mini-spec 快速通道 Step 1 需求澄清仍做**（轻量），纯文档改动免 spec 但 Step 1 仍适用。
> **资格不可自判**（防偷懒红线 1）：三条门槛由**客观事实**判定（文件数 / 接口签名 / 表结构 / 权限 / 外部输入），不由 agent 主观判断；任一不符 = 必须完整 spec；疑义时走完整 spec 或问用户，**不可自行裁定走 mini-spec**。

**纯文档/流程改动直接免流程**：只改文档/注释/README/skill 说明/脚本文案，**无代码逻辑/接口/数据/权限变化** → 免安全审查与 spec，PR 写「变更摘要 + 影响面（仅文档）」即可。判断口径：**能不能跑到线上产物里**（能 → 走流程；不能 → 免流程，但写清影响面）。
> **资格不可自判**（防偷懒红线 2）："纯文档"资格由客观事实判定，不由 agent 主观判断；**改动涉及流程规则 / skill 本身 / agent 行为约束时不可免流程**，必须走完整 spec（改规则者受规则约束）。

## Step 3：编码 + 自检

### 验证无异常（按项目实际情况，缺的跳过）

```bash
# 语法
node --check <file>.js          # JS
npx tsc --noEmit                # TS
python -m py_compile <file>.py  # Python

# 现有测试 + 项目门禁
npm test / pytest / <项目测试命令>
npm run lint / npm run build    # 有静态闸门就一定跑（能抓"没被引用所以 build 不报错"的坏文件）
```

### 批量文本操作纪律（反越权红线 #5，防编码/结构事故）

跨文件批量替换是高频事故源（真实事故：UTF-8 文件被 shell 按本地编码读写 → 中文注释永久损坏；edit 吞换行 → `</style>` 结构破坏；.ps1 丢 BOM → PowerShell 语法错误）。四条纪律：

1. **优先小步 edit**（编辑工具按 UTF-8 处理），shell 批量替换只在同构替换 ≥10 处时用
2. shell 批量替换必须**显式 UTF-8 读写**（如 .NET `ReadAllText` + `UTF8Encoding`，禁用依赖系统默认编码的 `Get-Content`/`Set-Content` 组合）
3. **写后必验**：`git diff` 抽查含中文的行是否完好（乱码/大面积中文行变更 = 立即回滚）
4. 改 `.ps1` 后保持 **UTF-8 带 BOM**（无 BOM 会被 Windows PowerShell 按 ANSI 解析中文注释导致语法错误）

### UI 视觉自测（**坐标断言，不是属性断言**）

凡涉及 CSS / 布局 / 定位 / 浮层 / 动画的改动必做；纯后端/逻辑跳过。
用 Playwright 量**实际渲染坐标**（`getBoundingClientRect`），断言写成**数值**（"距底部 ≤10px""面板底部 < 选区顶部""45.2 ±1px"），
动画**逐帧采样**；没有 Playwright 就用 DevTools 手量并把数值记进 PR。

> 最小样例与两次真实翻车见 `references/self-check.md`。

### 一致性复查六项（防"改了 A 漏了 B"）

改完逐条过：**注释语言 / 变量声明风格 / 全局引用扫描 / 文档清单同步 / 死代码 / 错误提示准确性**。
判据与典型漏网见 `references/self-check.md`。**只在发现问题时汇报**（发现了什么、修了什么），不逐项写产出。

> 数据：一次代码审查 24 个问题里 17 个 LOW 的根因都是"改完没复查"。

### 团队模式：编码后先过 J2（v4.6.0+）

- 编码/自检完成后，裁判员 J2 只做**流程/文档/自检证据**审计（不审代码、不测试）；代码审查+安全检查由代码安全员做；测试员只做验收测试；J2 PASS 后主脑才进 Step 4。
- 审查员对子代理返回做轻量分诊（主脑内联）；异常时深度审查；同一任务 3 次尝试仍失败带证据上报主脑。
- J2 BLOCK → 修正后复审（≤2 轮）；仍不过报用户，不得带病进测试。

## Step 4：测试（两支柱）+ 部署测试系统

> 原则：**测试从契约派生，不是从代码派生**。代码改了测试跟着改 = 测试失效。

### 支柱 2：新功能达标（契约派生用例）

- 每条 C 条款**至少一个**用例，命名带条款号：`test_c1_delete_card_total`；
- 优先 Python（`requests` 测 HTTP、`pytest`/`unittest` 组织；浏览器路径用 Playwright）；
- 覆盖三组：**新功能**（条款本身）+ **回归**（见下）+ **异常路径**（只测 spec「失败行为」/「边界与异常」节声明的项，不强制通用清单）。

### 支柱 1：核心功能没修坏（分级回归）

- **核心功能清单（一次性）**：首次使用或接入新项目时，若项目 runbook 没有「核心功能清单」→
  问用户"你认为本项目的核心功能（核心页面/路径）是什么"，记入 `docs/deploy-runbook.md`；已有清单直接复用，不重复问。
- **分级**（按本次改动判断）：
  - **触及核心功能**（同页面 / 同模块 / 共用接口 / 共用依赖 / 共用数据表）→ **核心功能回归**：按清单逐条跑（只读）；
  - **不触及** → **轻量冒烟**：改动路由可打开 + 无未捕获 JS 异常 + 无 5xx。
- 两者均**只读**（不发消息、不点删除、不写业务数据）、**只打测试环境**。

**扫描清单完备性守则（2026-11-15 增补，来自两轮用户人肉抓漏）**：
- ① **新增页面/路由当天必须进回归与扫描清单**——路由列表漏一页，那一页就是盲区，用户会成为你的测试员（真实事故：白底扫描漏了 guanjia/admin 路由，暗色不可读由用户连抓两轮）
- ② 白底/对比度类元素扫描的**尺寸阈值须覆盖小元素**（≥60×24px 级别），大块阈值（如 120×60）会放过胶囊/标签类小面积漏网
- ③ 断言对构建产物一律**归一化匹配**（去空白、接受 hex8/rgba 等价形式、允许 scoped 属性插入）——构建器压缩与 CSSOM 序列化都会改写格式，精确匹配 = 必然误报
- ④ 断言自身 bug 返工 ≥2 次 = 停下重构断言，不要继续打补丁（测试的测试也是债）
- 已有则复用项目脚本（如 `scripts/e2e/core_smoke.py`），没有就写一个最小的；
  输出 `report.json` + `report.md`，**退出码非零代表有 FAIL**。

### 测试路径真实性核销（条件：定位/浮层/菜单/下拉类改动）

- 用例的**操作方式必须与用户真实操作一致**：鼠标拖选/点击/键盘输入，而不是
  `editor.chain().setTextSelection()`、`element.click()`、直接改 store 之类的捷径；
- 涉及定位/浮层/菜单/下拉的改动，**必须**真实鼠标触发（`page.mouse.move/down/up`）；
- 技术限制必须用 API 捷径时，**额外补一个"模拟用户鼠标"的对照用例**验证两条路径一致；不一致以用户路径为准。

> 根因教训（2026-10-30 对齐菜单翻车）：用 API 设选区测"面板向上弹"PASS，但用户用鼠标拖选时场景不同，实际没上弹。**API 路径通过 ≠ 用户路径通过**。

### 部署测试系统 + 跑回归（仅当项目有测试系统时）

按前置判定的**部署通道**二选一：

**通道 A：手动/脚本部署**（默认）

```bash
# 用项目既有部署脚本，不要手搓（测试环境优先）
<deploy 脚本> -Target test      # 或 ./deploy.sh test / make deploy-test
```

**若部署脚本不可用**，手动部署的要点：**先传到临时位置校验，再原子换目录**，
禁止覆盖式解压（旧产物堆积会导致 404 / 页面转圈）。后端先 `cp -p` 备份再覆盖单个文件，只重启改动的服务。

**通道 B：CI/CD 自动发布**（分支推送即触发部署）

1. 推送代码到部署映射对应的分支（如 test 分支）：`git push origin test`；
2. **等 workflow 结论为 success** 再做任何验证：`gh run watch` / `gh run list --branch test`（GitLab 看对应 pipeline 状态）；
3. **核对线上版本/产物与待测 commit 一致**（版本号接口 / 产物 hash / 部署 run 记录的 commit SHA）；
4. 之后才在测试系统上跑分级回归。

> **workflow 未完成就跑回归 = 测的是旧版本，全部"通过"是假通过。**
> workflow 失败 / 取消 / 长时间不结束（含 runner 掉线卡在 queued）→ **遇阻即停**、排查流水线；
> **禁止手动部署绕过**——绕过会造成环境与 git 状态漂移，且下次自动部署会覆盖手工改动，问题被掩盖而非解决。

在测试系统上跑分级回归。判定：**FAIL = 0** 才继续；FAIL > 0 先修，把报告失败项贴给用户；WARN 需人工看截图确认。

**放置与清理**：

- 可复用回归用例 → 项目测试目录（如 `scripts/e2e/`、`tests/`）；一次性脚本 → `tmp/`，**Step 9 必须删掉**；
- 自动化测试禁止打生产、禁止发真实 AI 消息（产生费用）、禁止写业务数据（只写测试库）。

## Step 5：契约核销表（必须 100%）

```markdown
| 条款 | 测试用例 | 结果 | 路径真实性 |
|---|---|---|---|
| C1 | `test_c1_delete_card_total` | ✅ | 鼠标 |
| C2 | `test_c2_409_duplicate` | ✅ | API + 鼠标对照 |
| 目标树 | `timeline_pull` Step 1–5 分组无未完成叶子 | 完成 X/Y ✅ | 机器读取（非自填） |
| 裁判员 | J3/J4 裁判单 | ✅ / BLOCK | 内联：spec §9 / PR 描述 |
- 核销率：2/2（条款行；目标树/裁判员行独立校验，不计入核销率）；分级回归：PASS n / WARN 0 / FAIL 0（报告路径）
```

有未覆盖条款 = 测试不合格，补用例重跑。

> **「目标树」行（团队模式启用目标时必填）**：**分母只计 Step 1–5 分组的叶子**（Step 6–9 的叶子只能在核销后完成，
> 纳入分母会死锁），X = Y **且** `timeline_pull` 中 Step 1–5 分组无未完成叶子才算通过；数值由任务树状态读取、
> 不由主脑自填；它与 `check_spec.py --stage verify` 退出码 0 是**两个并列且独立**的必要条件。Step 1–5 存在未完成叶子 →
> 回对应步骤补齐，或显式 `retired` 并说明理由；`paused` 属未完成，**核销前必须清零**（Step 1–5 分组内 `paused` 叶子数必须为 0）。核销通过后 Step 6–9 叶子仍须全部 `done`，全树 100% 在 Step 9 收尾汇报给出
> （见 `references/team-mode.md`「目标驱动编排」）。
>
> **裁判员行（团队模式 v4.6.0+）**：J3 核销前结论先填，J4 验收前完成后补入；不计入条款核销率；`check_spec.py` 只识别首列为 `C<n>` 的行，不会误判裁判员行。团队模式 J3 BLOCK 不得核销；裁判员 PASS 不替代 `check_spec.py`。

**机器校验（必做）**：在项目根执行下面的命令（`--stage spec` 用于签约前查结构）：

```bash
python <skill目录>/scripts/check_spec.py docs/specs/<文件> --stage verify
# skill 目录通常为 ~/.agents/skills/ship-it
```

它会核对：条款编号连续、每条含前置/后置/失败/不变式、验收项编号连续、三问已勾、
核销表的「用例名带条款号 / 结果 ✅ / 路径真实性已填」。**非零退出 = 核销不合格**，别急着通知用户。

## Step 6：请用户验收（按清单打勾，不替用户下结论）

> 自动化通过 ≠ 可以发布。

汇报必含 5 项：

1. **重点变更**：改了什么、为什么、影响范围（一句话说清就不要长篇）
2. **验收标准清单**：贴 spec 第 6 节，让用户逐条打勾（按契约验收，不凭印象）
3. **测试步骤与预期**：怎么点、用什么账号、应看到什么
4. **回滚方式**：改坏了怎么退
5. **明确请求**："请按上面流程测一下，有问题告诉我"

> **团队模式 v4.6.0+**：J4 验收前裁判员必须出具裁判单（PASS / DEVIATION / BLOCK），**依据测试员报告、代码安全员代码审查/安全结论与 `check_spec.py` 结果审契约，不执行测试、不审代码**；BLOCK 不得请用户验收；汇报附裁判单摘要（原文可内联或 `tmp/`）；**裁判员 PASS ≠ 用户验收**。用户明确验收后 Step 7 复用 J4 结论；若 Step 6 后改代码/spec，重跑 J4。

> **CI/CD 自动发布项目**：通知用户"测试环境已更新"**之前**，必须确认部署 workflow 结论为 success
> 且线上版本与待验收 commit 一致（见 Step 4 通道 B 的核对方法）；不一致 → 先回部署环节修复，
> **不得让用户验收旧版本**。汇报模板中的"部署"一行必须真实填写。

```markdown
## 测试环境已更新（vX.Y.Z）
- 地址：<URL>    账号：<...>
- 部署：workflow <#run> success @ <commit>（CI/CD 项目必填；手动部署写脚本与时间）
- 分级回归：PASS n / WARN n / FAIL 0（报告：<路径>）
- spec：docs/specs/<文件>

### 请按验收标准打勾
- [ ] A1 <预期...>
- [ ] A2 <预期...>

### 回归检查（每项约 1 分钟）
- [ ] 登录 → 首页
- [ ] <核心路径 1> / <核心路径 2> / <核心路径 3>

> 请先强刷（Ctrl+Shift+R）；有问题把截图或操作时间点发我。
```

**验收判定**：接受任何明确表示验收通过的表述——"测试没问题"、"没问题"、"提交 PR"、"发吧"等都算通过；
用户回复含糊、不能确定其已测试通过时 → **主动询问**："测试是否无异常？可以进入下一步吗？"得到明确肯定才进 Step 7。

> **团队模式启用目标时**：用户明确验收通过后调用 `update_goal` 置 `complete`，并在汇报中说明目标已关闭；
> **未验收不得关闭**（目标 `complete` 与用户验收一一对应，同「禁止自证」）；同一阻塞连续 **3 个自动续轮**未解除才置 `blocked` 并写明具体条件——以 `get_goal` 返回的 **`roundsStarted`** 为准，**不得**用汇报次数或重试次数替代；宿主无自动续轮计数时降级为"每轮汇报显式记录同一阻塞出现次数"并注明"轮次口径降级"。

**遇阻即停**：用户发现问题 → 回 Step 2 改 spec（spec-first）→ 改代码 → 重跑 4/5 → 重新验收。
不要带病推进，也不要顺手加需求。

## Step 7：版本号 + PR

### 版本号

先找项目的版本来源：`package.json` / `pyproject.toml` / `VERSION` / `CHANGELOG.md` 顶部 / git tag。
有则按 SemVer 递增，无则从 `1.0.0` 起。**在项目里明确唯一来源，别让两处版本号打架**
（很多项目的 `package.json` version 与发布版本无关，此时以 CHANGELOG/deploy-log 为准）。

### 提交 + PR

```bash
git checkout main && git pull
git checkout -b feature/<简短描述>      # fix/xxx、chore/xxx
git add -A
git commit -m "<type>(<scope>): <摘要> [v<版本号>]"
git push origin <branch>
gh pr create --base main --head <branch> --title "<标题>" --body "<描述>"
```

> `git push` 不可用（公司代理/网络限制）时：改用项目既有的 push 脚本或其他可用的上传方式。

> **团队模式 v4.6.0+**：PR 前复用 J4 裁判单做交付合规复核（版本/CHANGELOG/PR 四块/未代合并/清理计划）；J4 后若有变更 → 重跑 J4。

> 🔴 **PR 创建即停（反越权红线 #1）**：`gh pr create` 是 agent 在本步的**最后一个动作**。
> 合并按钮永远属于用户——**任何时候禁止 agent 执行 `gh pr merge`**（无一例外，即使
> 用户说了"可以了/发布吧/做吧"也按最窄解释，见反越权红线 #2）。创建后把 PR 链接
> 交给用户："PR 已就绪，请审核后点击合并"。用户点合并 → CI 自动部署（Step 8 由
> 用户的合并动作触发，agent 只负责部署后验证与汇报）。
>
> **创建 PR ≠ 任务完成**：主脑必须停在「等待用户审核/合并」，不得把任务/目标标记完成。
> 用户合并或明确关闭后才进入 Step 8/9；用户要求修改 → 更新同一 PR。审查员按 C23
> 保持生命周期，直到用户审核/合并完成且下游无任务。

PR 说明四块缺一不可：

```markdown
## 版本号：vX.Y.Z
## 变更摘要：<一句话>

### spec 契约
- 文件：docs/specs/<...>（含方案自审/技术蓝图节；或 PR 内 mini-spec）
- 安全：自上次审查（YYYY-MM-DD）无新增攻击面 / 增量核验结论 <...>
- 契约核销表：<逐条 ✅>

### 测试情况
- 两支柱：核心功能 <分级回归结果> + 新条款 <用例数/通过数>
- 测试环境：<用户已验证的项>

### 影响范围 / 兼容性 / 回滚方式
```

## Step 8：合并后发布正式系统（含回滚预案）

> **合并前不碰生产**（代码、数据库、缓存、进程都算）。没有正式系统则跳过本步。
> **CI/CD 自动发布项目：合并 PR = 触发生产部署**——合并就是发布动作本身，因此这条红线更严格：
> 合并按钮**由用户本人点击**（agent 任何时候禁止合并 PR，见反越权红线 #1），
> Step 6 用户验收未通过不得合并。合并后 watch 生产 workflow 结论为 success，再执行下面的端到端验证
> （**workflow 绿灯不免除独立验证**——流水线只能证明部署执行了，不能证明用户可用）。

### 回滚预案（部署前先填，不填不部署）

| 项 | 记录 |
|---|---|
| 当前生产版本 | <commit / tag / 构建号> |
| 上次可用产物 | <目录/镜像/包路径> |
| 最新数据备份 | <备份文件路径；太旧就先做一次> |
| 回滚触发条件 | 登录失败 / 核心页面空白 / 接口 5xx 持续 >1% / 数据错乱 |
| 回滚动作 | 前端：换回旧产物目录；后端：回退文件并重启对应服务；数据：按备份恢复 |

**CI/CD 自动发布的回滚变体**（替换上表"当前生产版本 / 上次可用产物 / 回滚动作"三行的取值，其余行不变）：

| 项 | CI/CD 通道记录 |
|---|---|
| 当前生产版本 | main 上的 commit / 最近一次成功部署的 workflow run |
| 上次可用产物 | 上一个成功部署的 workflow run（或 release tag） |
| 回滚动作 | `git revert <commit>` 后推回 main，触发自动重新部署；或重跑旧 workflow run |

> ❌ 禁止直接手改服务器文件回滚（下次自动部署会冲掉、与 git 真源漂移）；
> 确需应急手工介入，事后**必须**把变更以 commit 形式补回 main，并在变更记录中注明。

### 发布 + 端到端验证（缺一不可）

```bash
# 1. 服务/进程状态
<pm2 list / docker ps / systemctl status>
# 2. 源站健康检查
curl -s http://127.0.0.1:<port>/health
# 3. 对外入口端到端（不能只测本地）
curl -s -o /dev/null -w 'HTTP %{http_code} - %{time_total}s' https://<域名>/
# 4. 产物 hash 对比（确认外网拿到的是新版本）
#    本地: ls dist/assets/index-*.js   远端: curl -s https://<域名>/ | grep -o 'index-[a-zA-Z0-9_-]*\.js'
# 5. 入口资源可达
curl -s -o /dev/null -w "chunk: %{http_code}\n" "https://<域名>/<入口chunk>"
```

**服务类安全规则**（通用）：

- ❌ 禁止 `pm2 kill` / `pm2 delete all` / `pm2 delete` 不带服务名；只操作具体服务名
- ✅ 操作前先 `pm2 list` 确认当前状态；重启后确认全部 online
- ✅ 前端部署"先清后放"（原子换目录），禁止在旧产物上覆盖
- ✅ 部署前确认目标路径（测试 vs 生产），并确认基线 commit 已合入 main
- ❌ 凭据（`.env` 值、口令、密钥）一律不写进文档、脚本、commit；需要时写"见服务器 `.env`"

> ⚠️ 耗时**不能**作为部署失败判据（跨境链路可能 10–60s）。看 **状态码 + 产物大小/hash** 是否与本地一致；
> 有内网/VPN 入口优先用它验证。

## Step 9：清理 + 变更记录

1. 删远程/本地已合并分支：`git push origin --delete <branch>` / `git branch -d <branch>`
2. **垃圾零容忍**：一次性测试脚本、诊断脚本、临时日志、截图、审查员/裁判员 `tmp/` 报告、`.bak` 备份全部清掉；
   `git status` 只剩有意提交的文件；确认 `.gitignore` 覆盖到位
3. 写变更记录（`CHANGELOG.md` 顶部或项目既有的 `deploy-log.md`）：

```markdown
## YYYY-MM-DD <变更标题>（vX.Y.Z）
### 变更内容
**PR #N**：
- **feat/fix**: 具体改动
### 测试环境验证（YYYY-MM-DD HH:MM）
- 实测数据（数值/接口返回/回归结果）
### 生产部署与验证（YYYY-MM-DD HH:MM）
- 部署方式、commit、服务状态、端到端验证、回滚基线
```

4. 同步受影响的文档（端口/表结构/接口/文件清单）
5. 向用户汇报：合并的 PR、版本号、生产状态、清理结果、**请强刷提示**

## 版本号规则

| 类型 | 递增 | 示例 |
|---|---|---|
| Bug 修复 | patch | `1.4.2` → `1.4.3` |
| 新功能 | minor | `1.4.3` → `1.5.0` |
| 破坏性更新（DB schema / API 不兼容） | major | `1.5.0` → `2.0.0` |

破坏性变更必须在变更摘要里显式标注 ⚠️。

## 关键原则

1. **不跳步**：Step 6 用户验收不能省——自动化通过 ≠ 用户验收通过。
2. **每步汇报**：每完成一步就汇报（做了什么 / 结果 / 下一步），不要闷头做完整个流程才说话。
3. **遇阻即停**：任何一步失败停下修或等指示，不带病推进。
4. **spec-first**：需求变更先改 spec，再派生代码与测试。
5. **默认复用**：A/B 优先，选 C 新建必须写成本对比。
6. **自测两层性**：①逻辑正确（条款核销）②路径真实（鼠标操作 + 坐标断言）。只过第一层就交付 = 返工。
7. **垃圾文件零容忍**：收尾必须复查，临时脚本/截图/备份不留仓库。
8. **凭据纪律**：口令/密钥不进文档/脚本/commit。
9. **测试只读、只打测试环境**：不写业务数据、不发付费请求、不对生产执行。
10. **禁止自证**：agent 不可自判合规，关键节点（mini-spec 资格 / 纯文档免流程资格 / 核销✅ / 能力声明）必须**机器可查或用户确认**。执行者 ≠ 裁定者——agent 可执行但不可自判通过 🔒。详见下方「反偷懒红线」。
11. **监督分离**：审查员是主脑唯一汇总接口，管执行健康（**默认每 1 分钟主动巡视所有成员，含主脑与裁判员；主脑不持续轮询，但 5 分钟无审查员消息 → 主动询问/唤醒审查员重试；审查员 5 分钟无主脑确认 → 再次上报/唤醒主脑**；宿主不支持持久 teammate/定时 → 事件触发巡视并声明「无主动定时巡视」降级）；**测试员只做验收测试**（按 `design.md`/后端/数据库标准；浏览器真实操作+截图；Playwright 提前适配）；**代码安全员代码审查（正确性/质量/注释/重复功能）+ 安全检查**；裁判员不审代码/不测试，只在测试+审查/安全通过后审契约并核查安全检查，裁判单报审查员汇总；审查员图像输入优先，图片交主脑决定临时识图子智能体；三者只读、只报告、不替主脑决策；裁判员有 BLOCK 权但 PASS 不替代用户验收与机器校验；三者本身也是 agent，其结论是审计意见，不是最终裁定 🔒。详见 `references/team-mode.md`「代码安全员/审查员/裁判员」。

## 常见坑（通用根因，来自真实事故）

| 坑 | 表现 | 对策 |
|---|---|---|
| 需求没澄清就做方案 | 在错误前提下盘能力、定复用，全浪费 | Step 1 需求澄清（每次做） |
| 只测 happy path | 流式错误收集没监听 error、损坏配置被静默覆盖、解析失败被 catch 吞掉 | Step 4 异常路径（按 spec 声明） |
| 属性断言当视觉验收 | CSS 属性对了但视觉错位 | Step 3 坐标数值断言 |
| API 捷径当用户路径 | 脚本过、用户操作不过 | Step 4 路径真实性核销 |
| 改完不复查 | 英文注释遗留、`var`/`const` 混用、迁移漏改引用点、新增文件没进文档清单 | Step 3 六项复查 |
| 部署"看起来成功" | 覆盖式解压旧产物堆积、变更检测为空导致静默不部署、tar 报错被忽略 | 原子换目录 + 明确基线 + 失败即中止 |
| 用耗时判断部署成败 | 链路慢被误判为部署失败，反复回滚 | 看状态码 + 产物 hash/大小 |
| 版本号两处打架 | `package.json` 与 CHANGELOG 各说一套 | Step 7 明确唯一来源 |
| 没回滚预案 | 出事时不知道退到哪 | Step 8 回滚卡 |
| workflow 未完成就跑回归 | 流水线还在跑就开始验证，测的是旧版本，全部"通过"是假象 | 等结论 success + 版本/产物 hash 核对后才跑（Step 4 通道 B） |
| 为消流水线警告吞错误码 | 给命令加 `\|\| true` 压版本警告，把真实部署失败也吞成成功退出码，workflow 绿灯但服务没起来 | 根治警告来源，或把吞错范围缩小到单条已知无害命令 |
| 手改服务器救火 | CI/CD 项目直接改服务器文件，与 git 真源漂移，下次自动部署被冲掉 | 一切变更走 git 提交触发重部署；应急手工介入事后以 commit 补回（Step 8） |
| AI 代合并 PR | 用户说"可以了/发布吧"，agent 执行 `gh pr merge` 触发生产部署，跳过用户审核 | **任何时候禁止 AI 合并 PR**；PR 创建即停，链接交用户点合并（反越权红线 #1/#2） |
| 跨仓库主体弄反 | 规范在 A 项目、要改 B 项目，整套工作做在错误对象上 | Step 1 显式确认基准项目与改动对象（反越权红线 #4） |
| shell 批量替换毁编码 | UTF-8 被按本地编码读写，中文注释永久损坏；写后不验证 | 批量替换显式 UTF-8 + 写后 git diff 抽查中文行（反越权红线 #5） |
| 外部服务故障死等 | MCP/CLI 401 后反复重试原路径，主线被阻塞 | 一轮重试后立即降级替代方案并告知（反越权红线 #7） |
| 审查员越权改代码/直接换模型 | 审查员把分诊变成执行，绕过主脑 | 审查员只可直发 `continue`/`retry_same`；换模型/换范围/新派发交主脑（team-mode「审查员」） |
| 主脑轮询审查员 | 主脑持续查审查员有没有内容，工作被拖住 | 审查员默认每 1 分钟主动巡视并推送；主脑不持续轮询，但 5 分钟无消息必须主动询问/唤醒审查员；无持久 teammate 时事件触发并声明降级（team-mode「主动巡视」） |
| 主脑静默等待 | 主脑直接等 tester/security，10+ 分钟不回复用户；审查员未激活 | 等待前先激活审查员；等待中每 5 分钟向用户发状态（在等谁/多久/下一步）；审查员 inactive 时主脑主动唤醒（C14/C16） |
| 审查员提前结束 | 契约没结束、PR 没创建，审查员就 inactive/被释放 | 审查员从签约到 PR/Step 9 常驻/可复用；inactive 不是结束，主脑必须唤醒；下游无任务才可结束（C23） |
| 等待工具设 10 分钟 | `wait_agent timeout_ms=600000`，5 分钟无法发状态，用户长时间无回复 | 单次等待 ≤5 分钟（300000ms）；超时先向用户发状态 + 唤醒审查员/催办，再继续（C14/C16） |
| §9 报告前预填 ✅ | J2/J3 连续 BLOCK；主脑自检冒充 tester | 报告后回填；J2 前 C 行“待测”；回填依据写报告时间/哈希 |
| 哈希先报后改 | 消息里的 spec 哈希与当前文件不一致，J2/J4 BLOCK | 最后一次编辑后重新取哈希；消息/报告用同一冻结值 |
| 公司网络 push 403 用 API gzip | 源码被 `.gz` 替换，分支不可用 | 逐文件小 commit push；不要用 gzip 替换源码；push 后核对远端文件 |
| 裁判员替测试员跑测试/审代码 | 裁判员自己跑 unittest/E2E 或审代码，既当运动员又当裁判 | 裁判员不执行测试、不审代码；J2 只审流程/文档/自检；J3/J4 在测试+安全通过后根据测试员报告与代码安全员结论审契约（C15/C16） |
| 主脑直接等裁判员 | 主脑跳过审查员汇总，直接等裁判员/下游，用户提问也不回 | 主脑只等审查员汇总；所有下游回报经审查员整理；用户提问优先回复（C16） |
| 测试员审代码/代码安全员不审代码 | 测试员越权审代码，代码安全员只做安全，正确性/质量没人管 | 代码审查+安全检查归代码安全员；测试员只做验收测试（C19） |
| 无 design.md 未询问 | 前端无标准、测试无依据 | 首次/新项目先问是否建立标准；否则按用户经验总结并记录（C19） |
| Playwright 未适配却声称跑过 | 浏览器测试假通过、无截图 | 提前适配环境；真实浏览器操作+截图汇总；不可用声明降级（C20） |
| 审查员无识图却假装分析图片 | 图片结论幻觉 | 报告主脑，由主脑决定临时识图子智能体；审查员只汇总（C20） |
| 需求模糊/跳过澄清员未互审 | 主脑单方面理解需求，契约偏差 | 主脑+审查员+裁判员至少 1 轮互审（假设/反驳/替代/风险/全局）后再向用户总结（C21） |
| 审查员只汇总不反问 | 下游报告未经质疑，错误被直接放大 | 审查员对每个报告至少 1 个质疑/反问，拿到回答再总结；主脑可反向质疑（C21） |
| 主脑 5 分钟不回复审查员/用户 | 审查员卡住没人唤醒；用户提问两次没人回 | 主脑 5 分钟无审查员消息主动询问/唤醒；审查员 5 分钟无主脑确认再次上报/唤醒；用户提问优先回复当前状态 |
| 审查员只盯开发不盯裁判员/主脑 | 裁判员 inactive、主脑 idle 有剩余任务却没人催 | 审查员巡视范围含主脑/裁判员/代码安全员/测试员/开发；inactive 未完成即催办/上报（C14） |
| 裁判员 PASS 当用户验收 | 主脑拿裁判单跳过 Step 6 / `check_spec.py` | 裁判员 PASS 只是必要条件；用户验收 + `check_spec.py` 仍是独立闸门（关键原则 11） |
| 主脑未等子代理结论就推进 | 子代理只回部分/未回，主脑已进下一步 | 裁判员 J2/J3/J4 必查时序；未等结论 = DEVIATION/BLOCK |
| 审计角色只看转述不看原文 | 裁判员凭主脑摘要 PASS | 裁判员必须读规则原文 + 证据 `path:line`/退出码；无证据 PASS 无效 |
| 后台不可见却声称已审查 | 报告写"已审查主脑后台"但无证据 | 强制写「后台可见性：完整/降级/不可见」；证据包 + 仓库落地物（team-mode C8） |

## 反偷懒红线（防契约逃逸，配合关键原则 10「禁止自证」）

> agent 既是执行者又自判合规 = "同源共错"。下面四种偷懒路径，每种都加"不可自判"约束。
> 开工前逐条自检；命中任一 = 必须走完整 spec 或问用户，**不可自行裁定走捷径**。

| # | 偷懒场景 | 表现 | 红线（不可自判） |
|---|---|---|---|
| 1 | **滥用 mini-spec 快速通道** | 多文件 / 改接口 / 动表 / 动权限 / 有外部输入，却声称"只改 1 个文件"走 mini-spec | mini-spec 三条门槛由**客观事实**判定（文件数 / 接口签名 / 表结构 / 权限 / 外部输入），不由 agent 主观判断；任一不符 = 必须完整 spec；疑义时走完整 spec 或问用户（见 Step 2 mini-spec 节） |
| 2 | **滥用纯文档免流程** | 有逻辑 / 接口 / 数据 / 权限变化的改动说成"纯文档"免安全审查免 spec | 判断口径"能不能跑到线上产物里"由客观事实判定；**改动涉及流程规则 / skill 本身 / agent 行为约束时不可免流程**，必须走完整 spec（见 Step 2 纯文档免流程节） |
| 3 | **跳过需求澄清** | 声称"需求很清楚"直接做方案，Step 1 走过场 | Step 1 每次做、分轻重——清晰需求快速过 ≠ 跳过；需求澄清记录（原始→优化+问答）必须进 spec 第 1 节，签约时展示给用户确认 |
| 4 | **测试从代码派生 / 核销表自填✅** | 改了代码顺手改测试使测试永远过；或没真跑用例 / 没覆盖就在核销表打✅ | 测试从契约派生不从代码派生（代码改了测试跟着改 = 测试失效）；核销表✅必须有对应用例名 + 路径真实性 + 报告路径，`check_spec.py` 机器校验退出码 0；agent 不可自判核销通过 |
| 5 | **监督角色形同虚设** | 派了代码安全员/审查员/裁判员但不采纳、不附报告、无证据 PASS；主脑自判核销/验收 | 三者报告原文必须附入汇报；裁判员无 `path:line`/命令+退出码不得 PASS；主脑不得自判核销/验收（关键原则 10/11） |

## 反越权红线（防越俎代庖，2026-11-15 增补，配合关键原则 10「禁止自证」）

> 反偷懒红线防"**少做该做的**"；本节防"**多做不该做的**"。两者互为镜像，共同根因是 agent 的过度自信：
> 把模糊授权扩大解释、批量操作不验证、派发不预检。镜像原则：执行者 ≠ 裁定者——
> **agent 不可自判"用户已经放行了"**。开工前逐条自检；命中任一 = 停下来问用户。

| # | 越权场景 | 表现 | 红线（不可自判） |
|---|---|---|---|
| 1 | **AI 合并 PR** 🔴 | 用 `gh pr merge` / 网页自动化等任何方式代点合并按钮 | **任何时候都禁止 AI 合并 PR，无一例外**——合并只能由用户本人点击 PR 页面的合并按钮。agent 到「PR 已创建」即停，把链接交给用户并等待。**建议用户在 Git 平台设置收窄 agent 凭据权限**（不给 merge 权限 / 分支保护要求 code owner 审批 / 限制合并途径为网页操作），使"代合并"在物理上不可行，而非仅靠纪律 |
| 2 | **模糊授权语扩大解释** | "可以了 / 发布吧 / 做吧 / 提交吧 / 试试"被解读为全流程授权，代用户走完合并+部署 | 一律按**最窄解释**：授权到哪一步就停在哪一步，超出部分停下来问（"你说的发布，是指我创建 PR 后停下等你合并，还是你自己去点合并？"）。用户嘴里的终点 ≠ agent 可代办的终点 |
| 3 | **部署生产 / 删数据 / 删服务 / 改生产 .env** | 跳过用户确认直接执行高危变更 | 这四类动作执行前必须显式确认（"我即将执行 X，确认？"）；PR 合并触发的 CI 自动部署除外（合并按钮本身即用户授权） |
| 4 | **跨仓库需求主体弄反** | 规范在 A 项目、改动对象是 B 项目，agent 在错误对象上做了整套工作 | 需求涉及 ≥2 个仓库时，Step 1 必须显式确认"**规范基准是哪个项目？改动对象是哪个项目？**"，写进需求澄清记录，签约时展示 |
| 5 | **批量文本操作事故** | shell 批量替换按错误编码读写（UTF-8 被 ANSI 解读）→ 中文永久损坏；edit 吞换行破坏结构；PowerShell 脚本丢 BOM 后语法错误 | ① 跨文件批量替换必须显式 UTF-8 读写；② 写后必验（中文行 git diff 抽查）；③ 优先小步 edit 而非 shell 批改；④ 改 .ps1 后保持 UTF-8 BOM |
| 6 | **subagent 派发失效** | never-ask 权限模式下派写任务给子代理，全部被拒，每个白跑一轮；或把执行失败误判为派发失败绕过重试 | 派发前判定任务类型：**只读**（扫描/分析/审查/裁判）→ 可派；**写任务** → 先确认子代理有写权限。**派发失败**（权限/路由/工具缺失）→ 同类失败一次后主脑自做；**执行失败**（已跑但报错/超时/空产出）→ 按审查员分诊重试/续派，受「初次 + 2 次重试 = 3 次尝试」上限约束。**审计角色例外**：审查员失败 → 主脑内联并声明「无独立审查」；裁判员失败 → 换新 subagent/`workflow`，仍失败报用户，不得自判 PASS |
| 7 | **外部服务故障不降级** | MCP/CLI 401/断连后仍按原路径反复重试，阻塞主线 | 一轮重试后立即切换手工/替代方案并告知用户（通道坏了≠需求停摆） |
| 8 | **监督角色越权** | 代码安全员/审查员改代码/改 spec/换模型/新派发；裁判员改文件/替用户验收；主脑删除 BLOCK 或代写裁判单 | 三者只读；审查员只可直发 `continue`/`retry_same`；裁判员 BLOCK 由主脑整改、PASS 不替代用户验收/`check_spec.py`；报告原文不得删除/篡改；违反 → 报告作废 + 记违规 + 重派 |

> 越权与偷懒的对称性：偷懒的判定主体是**客观事实**（文件数/接口签名/覆盖率）；越权的判定主体是**授权边界**（哪一步是用户的）。两者都不许 agent 自行裁定。
