# 团队模式（主脑 + 角色化多智能体协作）

> 本文件是团队模式执行形态的细节。9 步流程、闸门、契约模式（spec-first / 条款派生测试 / 核销 / 用户验收）**全部不变**；
> 团队模式只改变"谁来执行"：同样的 9 步，由"主脑 + 角色"执行。
> v4.6.0 起团队模式内部增加三个**只读审查角色**（代码安全员 / 审查员 / 裁判员）与「角色按需启用矩阵」；它们只决定"谁检查、检查什么"，不改变 9 步编号与用户验收归属。
> **本 skill 不硬编码任何具体模型名或模型特有数值限制**——模型信息一律来自项目 runbook 的「模型能力清单」（见下）。

## 何时使用（主脑自动判断）

用户提出需求时，主脑按三条判断（满足任一 → 启用团队模式）：

1. 需求涉及多文件（前后端都有，或多个模块）
2. 全栈（前端 + 后端都动）
3. 用户明确要求团队模式

三条都不满足，或需求符合 mini-spec 快速通道 → 主脑单干。
判断结果 + 理由写进 spec「方案自审」节。
用户明确说"不用组队 / 你自己做" → 主脑单干，即使需求大。

## 角色能力要求表

| 角色 | 能力要求 | 形态 |
|---|---|---|
| 主脑 | 会话模型（固定） | 会话本身 |
| 需求澄清员 | 联网搜索能力 | subagent（一次性） |
| 后端开发 | 大上下文优先 | subagent |
| 前端开发 | 无特殊要求 | subagent |
| 代码安全员 | 大上下文优先 | subagent（每轮派发一次） |
| 审查员（异常与偷懒审查） | 大上下文优先；只读 | subagent（异常时深度审查；轻量分诊由主脑内联） |
| 裁判员 | 大上下文优先；规则阅读；只读 | subagent（J1–J4 + 交付复核） |
| 测试员 | **必须图像输入** | 持久 teammate（失败降级 subagent） |

- **命名消歧**：单写「审查员」= 异常与偷懒审查角色；安全职责一律写「代码安全员」；代码审查（正确性/质量/注释/重复功能）归**代码安全员**，测试员只做验收测试。历史 CHANGELOG / 历史 spec 不改写。
- **按需启用**：角色不是每轮全上；按「角色按需启用矩阵」裁剪（见角色卡后）。
- "大上下文优先"是软要求：模型列表未声明上下文大小时，不影响挑选。
- "必须图像输入"是硬要求：测试员实际使用的模型（默认或动态挑选）必须经探针验证支持图像输入；无模型满足 → 截图认证降级为主脑亲自核验，或经用户同意跳过并注明。
- **性价比是能力满足后的软排序因子**：硬要求（如测试员图像输入）> 软要求（如大上下文）> 性价比。在能力满足的候选中按 Credits 消耗/订阅折扣窗口排序，高并发、批量类角色优先轻快模型；成本不得覆盖硬能力要求。订阅折扣时段（如夜间）与限时促销记入 runbook 成本列，动态挑选时参考（见「派发时模型决策」）。

## 模型发现流程（首次做一次）

首次使用团队模式（项目 runbook 无「模型能力清单」节）时：

1. **拉模型列表**：优先用宿主的模型列表工具（DSH：`list_subagent_models`，传 provider + model 可验证**单条路由是否放行**）；无此工具、或需完整模型池时读宿主配置文件（DSH：`~/.dsh/profiles/<profile>/cordis.patch.yml` 的 `llm-pi-ai.providers.<id>.models` 给模型池与上下文窗口，`agent-default-model` 给默认路由；旧版 `~/.dsh/settings.yaml` 在新版可能不存在，读不到时按此路径找）；其他环境用 provider 的模型列表接口。
2. **联网核实能力定位**：对主脑不熟悉的模型（新发布 / 新命名），**联网搜索官方文档 / 发布页**确认"擅长定位 + 输入模态"（如编程特化、多模态视觉、长推理），写入注册表「备注」列——**不许凭记忆猜新模型能力**；查不到官方信息 → 按"无特殊能力"处理，不挑选给有硬要求的角色（如测试员）。
3. **实测探针**（仅对列表/官方文档未确认的能力，如图像输入在本环境是否透传）：向候选模型发一张小测试图（如 64×64 PNG），记录成功/失败。成本小，只做一次。
4. **记录注册表**：写入项目 `docs/deploy-runbook.md` 的「模型能力清单」节（模板见下）。
5. **记录能力注册表**：把模型能力/成本/定位写入项目 runbook「模型能力清单」（模板见下），并记录该环境的**默认路由**（宿主 `agent-default-model` / 会话模型）。**不维护角色 → 模型分配表**——派发时用哪个模型由「派发时模型决策」规则在运行时决定（v4.5.0+：默认路由优先，仅硬能力不满足或用户显式要求时动态挑选）；模型名只存在于 runbook，禁止写死在 skill 正文或代码里。
6. **派发可行性预检（派发时）**：动态挑选前用宿主单路由验证工具（DSH：`list_subagent_models`）确认该路由**对本会话放行**。DSH 的子代理白名单 `allowedModels` 在**会话创建时固化**进会话事件流（`subagent/model-selection-policy`，写入条件为全新会话），改配置只对**新开会话**生效——当前会话仍报 `not allowed for this Session`。两类报错含义不同：`has no configured model` = 模型池里没有该 ID（改 ID）；`not allowed for this Session` = 会话白名单未放行（**新开会话**，不要反复改配置）。

**复核触发**（不为每个需求重复拉取；触发后 = 增量扫描 + 更新能力注册表 + 写回 runbook）：

- 用户更新模型配置（列表出现新模型 / 移除 / 改名）→ **对新模型联网核实能力定位**（禁止凭记忆猜）
- **会话实际路由出现注册表未记录的模型名**（配置文件滞后于实际路由，以实际为准）→ 同上
- 用户报告能力异常（如某模型图像输入突然报错）
- **订阅价格/折扣变动（限时促销开始/结束、模型到期下线）→ 增量更新注册表成本列；到期模型在 runbook 注明回退，运行时派发不得继续使用已下线模型（按「派发时模型决策」自动回退）**
- **宿主默认路由变动（`agent-default-model` / 会话模型切换）→ 更新 runbook 各环境「默认路由」记录**
- 复核是增量的：只对变动模型做能力搜索 + 探针；能力/成本变动写回项目 runbook「模型能力清单」，下次派发即生效（运行时决策，无需人工改分配表）。

**离线回退**：拉取模型列表失败 → 用最近注册表并注明"能力信息可能过期"；无注册表 → 全部角色回退会话模型，注明，联网后补建。

## 角色卡

### 主脑（会话本身）
- **职责**：spec 唯一 owner；定角色集，模型决策按「派发时模型决策」规则（默认优先）；**只派活、决策、对用户交付**；统一派发所有 subagent；持有跨轮状态；**唯一对用户交付的成员**；契约把控（spec-first / 核销 / 验收闸门）；**Step 6 汇总团队产出（安全审查报告/测试报告/裁判单/核销表）并起草五项报告**；**不亲自开发/测试/审代码**；**所有下游回报经审查员汇总，不直接等裁判员**；用户提问优先回复当前状态/在等什么；**等待前先激活审查员；等待中每 5 分钟向用户发状态（在等谁/多久/下一步），不得静默等待；等待工具单次 ≤5 分钟，超时先发状态/唤醒审查员，不得 10 分钟静默等待**；**5 分钟无审查员消息 → 主动询问/唤醒审查员重试**
- **输入**：用户需求、spec、各角色产出
- **输出**：spec（含方案自审：角色集 + 形态 + 派发决策 + 理由）、每步汇报（可附 ≤2 条流程优化建议）、Step 6 五项报告、最终交付
- **能力要求**：会话模型，固定
- **形态**：会话本身（不 spawn）
- **闸门**：不向任何角色让渡契约权；不跳步
- **契约互审**：需求模糊或未派需求澄清员时，主脑组织主脑+审查员+裁判员互审（假设/反驳/替代/风险/全局影响，至少 1 轮）后再向用户总结最终契约；主脑可反向质疑审查员总结
- **临时识图子智能体**：下游返回图片/截图时，审查员报告后由主脑决定是否派临时识图子智能体；结果交审查员汇总；主脑单干必须自测并注明
- **审查员生命周期**：审查员 inactive 不等于结束；主脑必须唤醒并确认下游无任务；PR 前不得释放审查员

### 需求澄清员
- **职责**：Step 1 需求澄清——联网搜索需求相关技术/方案、识别歧义点、输出优化后需求 + 澄清记录 + 待问用户的问题清单
- **输入**：用户原始需求、代码库现状线索（主脑提供）
- **输出**：优化后需求描述 + 优化说明 + 待问用户的问题清单（主脑审核后转达用户）
- **能力要求**：联网搜索能力
- **形态**：subagent（一次性，主脑统一派发）
- **闸门**：不直接面对用户；输出经主脑审核；主脑用 `ask_user_question` 转达问题、拿答案；**需求模糊时与主脑/审查员/裁判员互审**；被排除时由主脑组织互审

### 后端开发
- **职责**：后端代码改动（接口 / 数据 / 逻辑）
- **标准**：遵循后端标准 + 数据库标准（项目文档 / `design.md` / runbook）；无标准 → 主脑询问/总结并记录
- **输入**：spec 相关条款、文件作用域、自检要求
- **输出**：代码 diff + 自检结果（语法 / 测试 / 门禁）
- **能力要求**：大上下文优先
- **形态**：subagent（一次性，按任务派发）
- **闸门**：产出可追溯到条款；自检通过才提交

### 前端开发
- **职责**：前端代码改动（页面 / 组件 / 样式）
- **设计标准**：有 `design.md` 必须遵循；无 `design.md` → 主脑询问是否建立标准（首次使用/新项目必须问），用户不建立则按用户经验总结前端规范并记录
- **输入**：同后端开发
- **输出**：代码 diff + 自检结果（UI 改动含坐标断言要求）
- **能力要求**：无特殊要求
- **形态**：subagent
- **闸门**：同后端开发

### 代码安全员
- **职责**：**团队模式必执行**；负责**代码审查**（正确性 / 质量 / 注释 / 重复功能）+ **安全检查**（安全漏洞 / 依赖 / 权限 / 敏感信息 / 安全相关重复接口）；**测试员不审代码**；不通过 → 告审查员 → 审查员汇总主脑 → 开发修 → 再测试/再安全检查，循环；报告交审查员汇总，不直接报主脑。
- **输入**：本轮 diff + spec 相关条款 + 现有能力/接口清单 + 测试员报告（如已有）；第 2 轮必含第 1 轮问题清单与修复说明
- **安全审查库**：必须使用 `references/security-kb.md`——查 OSV/GHSA/NVD/KEV/EPSS/endoflife.date，记录包名+版本+来源 URL+查询日期；按技术栈跑 Semgrep/CodeQL/Trivy/gitleaks 等；SonarQube 仅可选适配（环境变量，token 不入库/入报告）；无工具/无网络必须标「工具缺失/未联网核验」，不得凭记忆说「最新」
- **输出**：结构化代码审查+安全报告（文件 / 行 / 严重度 / 证据 / 建议）
- **能力要求**：大上下文优先
- **形态**：subagent（开发交付后派发；可与测试员并行；跨轮状态由主脑持有）
- **闸门**：代码审查+安全检查不可跳过；正确性/高危问题 → 打回对应开发角色，修复后复审，最多 2 轮；仍不过 → 主脑报用户决策；报告交审查员汇总

### 审查员（异常与偷懒审查）
- **职责**：**审查员是主脑唯一汇总接口**——实时巡视所有成员状态/回复，收集开发、测试员、代码安全员、裁判员的报告，整理后给主脑判断；审查子智能体返回与主脑后台异常/偷懒——失败 / 超时 / 空产出 / 仅元信息 / 产出不可追溯条款 / 工具被拒 / 上下文超限 / 明显偷懒（只做部分、无证据、把活推回主脑）/ 疑似偏移；判定优先级 P0/P1/P2；可继续/重试的，**直接向子代理发 `continue` / `retry_same`**（同任务、同条件）；**换模型 / 换 prompt / 缩范围 / 新派发 / 续派剩余部分交主脑**；同一任务**初次 + 最多 2 次重试 = 共 3 次尝试**，第 3 次失败带报错原文、尝试次数、已试方案、建议上报主脑；**按主脑证据包**核对后台 job / 任务树 / 派发记录一致性（按 C8 证据口径）；**不审代码、不做测试、不决策**。
- **输入**：子代理返回/报错原文、退出码、耗时、产出摘要、任务标识（Timeline/任务）、派发记录、后台 job 状态、任务树/看板快照。
- **汇总前反问（必做）**：对每个子代理报告先自己分析，至少提出 1 个质疑/反问（为什么这样做 / 有没有更好方法 / 边界与异常 / 替代方案）给下游子代理；拿到回答后再总结给主脑；未解决疑问不得向用户呈现为最终结论。
- **输出**：分诊单（`task` / `attempt` / `failure_class` / `severity` / `evidence` / `recommended` / `reason` / 只读声明）。
- **能力要求**：大上下文优先；只读。
- **形态**：subagent（异常时深度审查；跨轮状态由主脑持有；宿主支持时复用同一会话）。
- **图像审查**：优先使用具备图像输入的模型；下游返回图片/截图/报告时，向主脑报告并说明需要识图；主脑决定是否派临时识图子智能体，结果交审查员汇总；**不得假装识图**。
- **契约生命周期**：审查员从签约到 PR 创建/Step 9 完成**不得主动结束**；同一会话复用，inactive 不是结束标志；只有下游（开发/测试/代码安全员/裁判员）无任务、无内容可汇总时才可结束；**C14 的「换新审查员」是角色替换，不是结束角色**，旧审查员可退役，新审查员必须立即接续。
- **闸门**：只审不裁；不改代码/spec/任务树；只可直发 `continue`/`retry_same`/`question`（question 仅质疑/澄清，不含新范围/模型）；不面向用户；报告原文由主脑保存并可按需附入汇报。
- **失败分类枚举**：`dispatch_failed` / `timeout` / `empty_output` / `meta_only` / `unreachable_clause` / `tool_denied` / `context_overflow` / `laziness` / `suspected_drift`。
- **主动巡视（watchdog）**：默认**每 1 分钟**巡视所有成员——主脑、需求澄清员、后端/前端开发、代码安全员、裁判员、测试员；检查 `list_agents` 状态（running / inactive / corrupt / unsupported / unavailable；failed 语义按证据包归入对应状态）、任务树/看板叶子与成员状态是否一致、最近产出/最后活动（**以主脑证据包/看板快照为准；子代理无 `timeline_*`，不能直读主脑后台/会话日志**）、是否超时/空产出/仅元信息/明显偷懒。成员 inactive 且有未完成任务 → 直接发 `continue`/`retry_same`；**主脑 idle 且有未完成叶子/待派发任务 → 提醒主脑继续**；成员 running 但长时间无进展 → 催办/上报；同一成员连续 2 次巡视无响应 → 带尝试次数上报主脑；异常即时上报，无异常每 5 分钟一次心跳；**主脑不持续轮询，但 5 分钟无审查员消息 → 主动询问/唤醒审查员重试；审查员 5 分钟无主脑确认 → 再次上报/唤醒主脑；双方都卡住 → 主脑换新审查员并记录尝试次数**。
- **巡视形态**：优先持久 teammate 循环；宿主不支持 → 事件触发巡视（每次派发/返回/检查点触发一次完整巡视）并声明「无主动定时巡视」；**不得要求主脑定时轮询**；巡视间隔默认 1 分钟，可配置 1–5 分钟，高风险项目必须 1 分钟。
- **建议/决策映射**：`continue` → 审查员直发（同任务同条件，固定消息模板：仅指令 + task id + 证据，不含新范围/模型），主脑记录不重派；`retry_same` → 审查员直发（同模板）；`question` → 审查员直发（仅质疑/澄清，不含新范围/模型）；`retry_with_changes(model|prompt|scope)` → 主脑决策①/②；`main_do` → ④；`escalate_user` → ⑤；续派剩余部分 → ③由主脑。
- **主脑决策集（封闭 5 选 1）**：换模型重派 / 换 prompt / 缩范围重派 / 基于已有产出续派剩余部分 / 主脑自做 / 报用户；决策写入当步汇报与任务树/看板。
- **派发失败 vs 执行失败**：派发失败（权限/路由/工具缺失，重派必白跑）→ 主脑自做；执行失败（已跑但报错/超时/空产出）→ 按 C4 计数重试/续派。
- **总尝试 ≤3**：同一任务超过 3 次尝试仍未成功 → 停止自动重试，交主脑决策；**审计角色例外**：审查员/裁判员自身派发失败不适用「主脑自做」——审查员失败由主脑内联并声明「无独立审查」，裁判员失败换新 subagent/`workflow`，仍失败报用户，不得自判 PASS。

### 测试员
- **职责**：**只做验收测试**：按 spec + `design.md` / 后端标准 / 数据库标准执行两支柱（契约派生用例 + 分级回归），找问题、给更正建议；**不审代码、不做安全检查**；截图认证；测试执行权归测试员
- **输入**：spec 条款、`design.md`/后端/数据库标准、回归范围（runbook 核心功能清单）、测试环境地址、Playwright/浏览器环境
- **输出**：测试报告（用例清单 + 结果 + 报告路径 + 问题/建议）、截图/路径汇总
- **能力要求**：**必须图像输入**
- **形态**：持久 teammate（多轮记忆；创建失败降级 subagent）
- **闸门**：测试只读、只打测试环境；不写业务数据、不发付费请求；FAIL>0 → 审查员汇总主脑 → 开发修 → 重测，最多 2 轮；**不审代码**
- **执行环境**：必要时使用实际可控的 Windows/macOS 工具/方法；浏览器测试必须真实浏览器操作 + 截图汇总；Playwright 等环境**提前适配**；不可用 → 声明降级/替代，不得声称跑过
- **实测为证（防能力幻觉）**：声称"不支持图片输入"前**必须先发一张探针图实测**（如 64×64 PNG），只有实测失败才能降级；凭记忆/印象直接说"不支持"就降级 = 违规。降级决定必须附实测失败证据（哪张图、什么报错），写入测试报告。无证据 = 不可降级 🔒

### 裁判员
- **职责**：规则符合性审计，**不审技术方案优劣 / 代码质量 / 不审代码，不执行测试**。读取用户约束、项目 `AGENTS.md`/`CLAUDE.md`/rules/agent 目录、全局 `AGENTS.md`、skill 正文、spec 契约、任务树/看板；在 **J1 签约前 / J2 编码后 / J3 核销前 / J4 验收前**检查每个角色是否按规则工作；**J2 只审流程/文档/自检证据（不审代码）**；**J3/J4 在测试员验收测试、代码安全员代码审查+安全检查都通过后**，根据测试员报告（用例名/结果/报告路径）与代码安全员代码审查/安全结论审契约，并核查安全检查是否通过（防主脑偷懒）；**裁判员不得运行 unittest/E2E/回归测试、不得审代码、不得替测试员或代码安全员出结论**；可运行 `check_spec.py` 作为契约结构校验（非测试）。防主脑未等子代理结论/部分结论就推进、跳过 Step 1/2/5/6、自判核销/验收/PASS、未按 spec 派发、提前合并 PR、擅自扩大范围；防子代理超文件作用域、改 spec、跳自检、只回元信息、伪造测试结果、擅自改需求、越权对用户交付；出裁判单，BLOCK 可阻断进入下一步；PASS **不替代**用户验收与 `check_spec.py`；**裁判单交审查员汇总**，不直接报主脑；最终确认契约完成度（审计意见，不是最终裁定）。
- **输入**：spec、用户约束、规则文件原文、git diff、测试员报告、代码安全员安全报告、任务树/看板快照、审查员报告、主脑派发记录/汇报草稿。
- **输出**：裁判单（`checkpoint` / `rules_source` / `checks` / `verdict` / `required_action` / 非最终裁定声明）。
- **能力要求**：大上下文优先；能读仓库文件；只读。
- **形态**：subagent（J1–J4 + 交付复核；跨检查点状态由主脑持有）。
- **闸门**：只读；BLOCK ≤2 轮；争议交用户；主脑不得删除/篡改裁判单；裁判员不是最终裁定者。
- **检查表（19 条）**：反偷懒 4 + 反越权 7 + 主脑时序 3（B1 未等结论推进 / B2 自判核销验收 / B3 未按 spec 派发或扩大范围）+ 子代理越权/偷懒 5（C1 超作用域 / C2 跳自检 / C3 只回元信息 / C4 伪造测试或擅改需求 / C5 明显偷懒）。
- **规则源缺失**：本仓库根**无** `AGENTS.md` / `CLAUDE.md`，`.agents/` 无规则文件；按 runbook + 全局 AGENTS.md 读取，缺失记「未找到」，不得编造。
- **证据口径**：每条 deviation/BLOCK 必须有 `path:line` 或命令+退出码；后台审查写「后台可见性：完整 / 降级 / 不可见」；证据不足标 `evidence_missing`，**禁止声称审查了不可见对象**。
- **测试/代码边界**：裁判员**不执行测试、不审代码**；J2 只审流程/文档/自检证据（不审代码）；J3/J4 在测试+安全通过后引用测试员报告路径/用例名与代码安全员结论；裁判单必须声明「未执行测试、未审代码；测试归测试员，代码审查+安全检查归代码安全员」；可运行 `check_spec.py` 作为契约结构校验（非测试）。

## 角色按需启用矩阵（v4.6.0+）

> 角色不是每轮全上。主脑按改动规模/风险选形态，把选择写进 spec「方案自审」并汇报；矩阵只决定「派谁」，**不降低任何闸门**。

| 形态 | 适用 | 必派 | 按需/条件 | 闸门 |
|---|---|---|---|---|
| **0 单干 / mini-spec** | 单文件、不改接口、不动表/权限、无外部输入 | 主脑 | 无 | Step 1 主脑兼任；Step 5/6 不变 |
| **1 小改** | 多文件但单模块、低风险、无外部输入 | 主脑 + 相关开发 + 代码安全员 + 审查员 + 测试员 + 裁判员（J1/J3/J4；J2 流程审计轻量） | 无 | 9 步 + J1/J3/J4 |
| **2 中改** | 跨模块 / 前后端联动 / 有外部输入 | 主脑 + 相关前后端 + 代码安全员 + 审查员 + 测试员（验收测试）+ 裁判员 J1–J4 | 需求澄清员（模糊时） | 9 步 + J1–J4 |
| **3 大改/高风险** | 全栈 / 多模块 / 对外暴露 / 不可逆 / 安全敏感 | 全部 8 角色 + 裁判员 J1–J4 | 深度安全审计（代码安全员专项扩展）、方案评审（独立 subagent）、发布验证（有正式环境时） | 9 步 + J1–J4 + 可选专项 |

- **需求澄清员**：按需；清晰需求/小改由主脑兼任；模糊需求/大改才派。
- **代码安全员、审查员、裁判员、测试员**：团队模式形态 1–3 **必须执行**；只有主脑单干例外，主脑必须自测并注明。
- **审查员巡视**：默认每 1 分钟巡视所有成员（含主脑/裁判员/代码安全员/测试员/开发）；异常即时上报、无异常每 5 分钟心跳；**主脑不持续轮询，但 5 分钟无审查员消息主动询问/唤醒；审查员 5 分钟无主脑确认再次上报/唤醒**；宿主不支持定时则事件触发巡视并声明「无主动定时巡视」降级。
- **测试员**：团队模式形态 1–3 必执行；只做验收测试（不审代码）；主脑单干例外且必须自测。
- **前端/后端标准**：前端有 `design.md` 必须遵循，无则先问是否建立标准（首次/新项目），否则按用户经验总结；后端遵循后端+数据库标准，无则询问/总结并记录。
- **契约互审**：需求模糊或跳过需求澄清员时，主脑+审查员+裁判员至少 1 轮互相质疑（假设/替代/风险/全局影响），主脑收敛后再向用户总结最终契约。
- **主脑第一版契约后自审**：完成第一版契约后（尤其单干）自我质疑假设/替代方案/前瞻性/可维护性/可扩展性；**不要等实现完再改契约**；质疑语气友善，对方合理就直接总结给上游。
- **前后端开发**：只派相关侧，不强制双端。
- **Step 6 报告**：主脑汇总团队产出（安全审查报告/测试报告/裁判单/核销表）后起草五项报告；裁判员 J4 只审合规、不代写。
- **可选专项**：不新增常设角色；代码安全员是常设必执行角色，不属可选专项；未启用专项时在 spec/汇报注明「未启用及理由」。

## 信息流与循环升级（v4.6.0+）

> **用户 ↔ 主脑 ↔ 审查员 ↔（代码安全员 / 裁判员 / 前后端开发 / 测试员）**。
> 主脑不直接等裁判员；所有下游回报经审查员汇总后给主脑判断。

1. **主脑派活** → 开发（前端按 `design.md`/标准，后端按后端+数据库标准；无标准先问/总结）；主脑只派活/决策/对用户，不亲自开发/测试/审代码。
2. **开发交代码** → **代码安全员做代码审查（正确性/质量/注释/重复功能）+ 安全检查**；**测试员做验收测试**（按 spec + `design.md`/后端/数据库标准；可并行）；测试员不审代码。
3. **任一不通过** → 审查员汇总主脑 → 主脑判断 → 开发修 → 回 2，循环（最多 2 轮）。
4. **代码审查/安全 + 验收测试都通过** → 裁判员审契约（不审代码、不测试；核查安全检查是否通过，防主脑偷懒）→ 裁判单报审查员汇总 → 主脑 → 用户。
5. **图片/截图**：下游返回图片 → 审查员报告主脑 → 主脑决定是否派临时识图子智能体 → 结果交审查员汇总给主脑；审查员不得假装识图。
6. **用户提问**：主脑优先回复当前状态/在等审查员汇总/下一步，不得以等待下游为由沉默。

### 执行中需求变更 / 重签约（v4.6.0+）

用户在执行中追加/修改需求时，**不要继续跑旧契约**：

1. **主脑先回用户**：当前状态/影响/下一步。
2. **回 Step 2 改 spec（spec-first）**：更新契约、验收、范围、非目标；不绕过 spec 直接改代码。
3. **主脑通知审查员**：暂停所有子智能体新工作、保留已有产出、待命；审查员转达并**盘点进度**（各角色做到哪/产出/未完成/阻塞），汇总给主脑。
4. **暂停期间不跑旧契约**：不派新活、不让子智能体继续旧契约；宿主无中断能力 → 等在跑子智能体到安全点/自然结束，只停止新派发，记录「未能立即停住」。
5. **更新契约给用户重新签约**：展示 spec diff/新增条款/验收变化；用户重新签约后才继续。
6. **签约后判断继续/重派**：审查员汇报最新进度；主脑按角色判断——未受影响的角色可继续（如后端不需要重开发），受影响角色重派/重跑；更新任务树。
7. **受影响闸门重跑**：契约变更影响已完成的测试/安全/裁判结论 → 重跑对应 J1/J2/J3/J4，不得拿旧结论冒充新契约。

### 派发时模型决策（v4.5.0+：默认优先 + 动态挑选）

> 取代 v3.1.4–v4.4.2 的「runbook 角色分配表静态绑定」。派发时用哪个模型在**运行时**决定，不查静态表——
> 配置变更 / 会话策略固化 / 模型下线不再需要人工改分配表。runbook 只维护「模型能力清单」（能力参考）与「默认路由」记录。

**决策顺序**：

1. **默认路由优先**：角色无硬能力要求、或硬能力被默认模型满足，且用户无显式模型要求 → 派发**不指定 provider/model**，由宿主默认路由决定（DSH：`subagent`/`subagent_fork` 无模型参数走默认路由；`spawn_teammate` 继承主脑会话模型）。主脑 = 用户选择的会话模型，固定不分配。
2. **动态挑选（仅两类触发）**：① 角色硬能力不被默认模型满足（当前唯一硬要求：测试员图像输入）；② 用户显式要求（省钱 / 指定模型）。→ 用 `list_subagent_models` 查**本会话实际放行集合**，按硬要求 > 软要求 > 性价比过滤排序，经宿主按调用指定模型入口（DSH：`workflow` 的 `agent(prompt,{provider,model})`）显式派发；挑选结果 + 理由（能力 + 成本）写入当步汇报。
3. **硬能力未知先探针**：默认模型图像能力未知时先发探针图实测（实测为证），再决定是否触发动态挑选；无证据不可降级 🔒。
4. **审查角色**：代码安全员/审查员/裁判员无硬能力要求 → 默认路由；不因审查角色触发动态挑选（除非用户显式要求）。

**自动回退（不停摆、不每次问用户）**：派发路由不可用（会话固化 / 网关故障 / 模型下线 / 派发失败）→ 自动切换到下一个满足该角色能力的放行候选；无候选 → 主脑自做（测试员 → 主脑核验截图降级）；汇报注明「模型回退」及原因。回退链穷尽仍失败 → 遇阻即停报用户。回退不得绕过硬能力（测试员回退模型仍须图像输入，否则走主脑核验降级）；同类派发失败一次后主脑自己做，不再重派（反越权红线 #6）。

**真源口径**：派发决策以本会话 `list_subagent_models` 实测为准，**不是**配置文件静态白名单、也不是 runbook「可派发」列（后者仅为历史实测证据记录，须注明验证会话与日期）。用户显式指定的模型未放行 → 如实报告原因 + 替代建议，不静默换模型。两类报错：`has no configured model` = 模型池无此 ID（改 ID）；`not allowed for this Session` = 会话白名单固化（提示新开会话，不反复改配置）。

### 截图协议（测试员）

- 读图分批；**批量大小 = 测试员实际使用模型的单次请求图片上限（注册表记录）**（用户全局指令有更严限制时从严）
- 优先关键页面（核心路由、本次改动页面），不逐页截图
- 坐标断言用数值（与 Step 3 UI 视觉自测一致）

## 目标驱动编排（v4.4.0+，团队模式可选增强）

> 团队模式默认靠主脑的会话上下文维护进度；启用目标驱动后，进度外置为**目标 + 任务树**，
> 机器可查、跨中断可恢复。9 步流程、闸门、契约模式**全部不变**——本机制只改变"进度存在哪、谁来读"。
> 收益边界：跨会话/跨天、角色 ≥3、步骤 ≥5 时收益明显；单文件小改动为负收益（纯开销）。

### 何时启用（用户决定，主脑不代选）

spec 签约时（Step 2 末），主脑用 `ask_user_question` 问一句："本次是否启用目标管理（目标 + 任务树）？"

- 用户选**启用** → 签约确认后 `create_goal`，按本节流程执行
- 用户选**不启用 / 未答** → 按原流程执行，spec 注明"未启用目标"，**不创建任何目标**
- 主脑**不得**替用户默认启用或默认跳过（与关键原则 10「禁止自证」一致）

### 目标生命周期

| 阶段 | 动作 | 触发条件 |
|---|---|---|
| 创建 | `create_goal`（objective = 优化后需求 + 验收标准） | 用户签约**且**选择启用 |
| 进行 | `timeline_tasks` 更新叶子状态 | 每次角色产出返回 / 出现阻塞 |
| 关闭 | `update_goal` 置 `complete` | Step 6 用户**明确**验收通过 |
| 阻塞 | `update_goal` 置 `blocked` + 具体条件 | 同一阻塞连续 **3 个自动续轮**未解除（以 `get_goal` 返回的 **`roundsStarted`** 为准；**不得**用汇报次数或重试次数替代，**不得**以"困难/不确定"为由置 blocked） |

### 任务树结构

- **分组**：根下按 Step 1–9 分组，每组至少 1 个叶子
- **叶子**：必须是**可检查动作**——完成判据一眼可判（如"check_spec.py 退出码 0"），不能是"做开发"这类模糊表述
- **拆不出来怎么办**：某步无法拆出可检查叶子 → 该步建单叶，并在描述中写明"不可拆分"的具体原因（不留空步，也不强行二拆）
- **状态**：仅用 pending / active / done / blocked / paused / retired
- **`paused` 语义（短期暂停，等外部输入）**：
  - **进入条件**：叶子当前为 `active`，且因**外部输入**无法推进（等用户决策 / 等第三方响应 / 等资源）。
  - **必填 note**：置 `paused` 时**必须同时写**两项非空内容——**暂停原因**与**恢复条件**；任一缺失 → 不得置 `paused`，应保持 `active` 或置 `blocked`（按"是否真的卡住"判断）。
  - **恢复路径**：恢复条件满足 → 置回 `active`（或直接 `done`）。
  - **核销前清零**：Step 5 核销时，Step 1–5 分组内 `paused` 叶子数**必须为 0**；仍有 `paused` → 核销不合格，不得进入 Step 6，须恢复该叶子或显式 `retired` 并说明理由。
  - **不算完成 / 不等于不阻塞**：`paused` **不计入 done**，也与 `pending`/`active`/`blocked` 一样属于"未完成"，**不得被解释为"不阻塞"**。
  - **不得用于"以后再说"**：暂缓实现 / 优先级降低 → 用 `retired`（不做，需理由）；真正卡住 → 用 `blocked`。`paused` 只服务于"等外部输入的短期暂停"。
- **规模上限**：节点总数（含根与分组）**≤40**。每次更新都是一次工具往返，节点越多开销越大；超出即拆分过度，必须合并

### 派发标识

派发 subagent 时，prompt 在既有三要素（条款号 / 文件作用域 / 自检要求）之外**追加任务标识行与完成标准**：

```
Timeline: tree=tree-8f8ac828ae16da2f; tasks=clarify,design
```

- **完成标准**：写明该任务的完成判据（即对应叶子的可检查动作标准，如"check_spec.py 退出码 0"），让子代理知道"做完"长什么样；与自检要求并存，不互相替代
- 条款号**不得**被任务标识替代——两者并存，条款号是契约锚点
- 子代理无 timeline 工具或读取失败 → 主脑把完整任务描述**内联**进 prompt，不依赖外部读取
- 内联后仍失败一次 → 主脑自己做，不再重派（同反越权红线 #6）

### 进度写回

- 角色产出返回后、进入下一步**之前**更新对应叶子：完成 → `done` 附结果摘要；受阻 → `blocked` 附具体条件
- 裁判员 J1–J4 结论写回树/看板；代码安全员/审查员/裁判员报告内联或落 `tmp/`，Step 9 必删；PR 引用内联内容，不引用已删除文件
- 每步汇报带完成度数字（已完成 / 总数）
- 写回失败 → 汇报里文字列出状态并注明"任务树未同步"，不得静默跳过
- **状态与汇报冲突时以任务树为准**，并立即修正汇报

### 核销增强（Step 5）

启用目标时，核销表在条款行之后增加一行「目标树」：

| 条款 | 测试用例 | 结果 | 路径真实性 |
|---|---|---|---|
| C1 | `test_c1_...` | ✅ | 鼠标 / API+对照 |
| **目标树** | `timeline_pull` Step 1–5 分组无未完成叶子 | 完成 X/Y ✅ | 机器读取（非自填） |

- **分母口径**：Y 只计**核销时点应完成的叶子**（Step 1–5 分组）。Step 6–9 的叶子只能在核销之后完成，纳入分母会形成死锁
  （2026-11-17 自举实测发现：核销时点必然存在 Step 6 验收 / Step 9 清理叶子未完成）
- 通过条件：X = Y **且** `timeline_pull` 中 **Step 1–5 分组**无未完成叶子
- 与 `check_spec.py --stage verify` 退出码 0 是**两个并列且独立**的必要条件，任一不满足即核销不合格
- Step 1–5 存在未完成叶子 → 回对应步骤补齐，或显式 `retired` 并说明理由
- 核销通过后 Step 6–9 叶子仍须全部 `done`；**全树 100%** 在 Step 9 收尾汇报中给出

### 中断恢复（本机制的核心收益）

上下文中断（换模型 / 压缩 / 跨天续做）后，主脑先 `timeline_pull` 取未完成叶子，按树恢复"做到哪、剩什么、卡在哪"，
**不重读全部文档**。目标已存在（同一需求续做）时复用既有目标与树，不重复 `create_goal`。

## 协调原语与实时查看

### 能力要求（平台无关，向下兼容）

团队模式只要求宿主环境提供下列能力（**任何实现均可**；角色卡、闸门、契约模式不变，按能力映射即可）：

| # | 能力 | 用途 | 缺失时回退 |
|---|---|---|---|
| 1 | 创建持久 teammate（命名、多轮记忆、同会话可复用） | 测试员 | 降级为 subagent |
| 2 | 一次性 subagent（每次调用可选模型） | 代码安全员 / 开发角色 | 主脑亲自做 |
| 3 | 消息传递（teammate ↔ 主脑） | 星型协调 | 必需项——缺失则不启用团队模式 |
| 4 | 共享任务看板（依赖 + 文件写入范围） | ≥2 个 teammate 并行防踩文件 | 主脑持有依赖表（spec 仍是契约层） |
| 5 | 等待 / 打断（等状态变化不轮询；打断跑偏 teammate） | 调度 | 等自然结束后重派 |
| 6 | 目标生命周期（创建 / 状态更新 / 关闭） | 目标驱动编排 | 主脑在 spec 内维护文字目标，注明"无目标原语" |
| 7 | 任务树（分组 + 叶子状态 + 机器可读进度） | 目标驱动编排 | 文字版进度表（主脑在每步汇报中维护） |
| 8 | 独立只读审查角色（代码安全员/审查员/裁判员） | 代码安全 / 异常分诊 / 规则审计 | 主脑内联检查表并注明「无独立审查」 |
| 9 | 后台任务 / 会话日志可观测性 | 审查后台 | 主脑证据包 + 仓库落地物；声明「后台可见性降级」 |

### DSH 映射（本环境适配）

| 能力 | DSH 工具 |
|---|---|
| 创建持久 teammate | `spawn_teammate`（**继承主脑会话模型**，无模型参数；实测：主脑切换会话模型后，新 teammate 跟随主脑） |
| 一次性 subagent（默认路由） | `subagent` / `subagent_fork`（无模型参数）；`subagent_claude_code` / `subagent_codex`（切换 CLI 后端） |
| 一次性 subagent（**指定模型**） | `workflow` 的 `agent(prompt, { provider, model })` —— 按调用指定模型的入口（适合批量编排） |
| 消息传递 | `send_message` / `list_agents`（`send_message` 支持同一 subagent 树任意成员互发，含兄弟/堂兄弟/回主脑；仅拒绝 self） |
| 代码安全员/审查员/裁判员只读审查 | `subagent`（只读 prompt）；审查员可用 `send_message` 直发 `continue`/`retry_same`；裁判单 BLOCK 由主脑执行 |
| 后台任务 | `job_list` / `job_output`（主脑侧；子代理只能读自己启动的 job） |
| 共享任务看板 | `team_task_create` / `team_task_list` / `team_task_update` |
| 等待 / 打断 | `wait_agent` / `interrupt_agent` |
| 目标生命周期 | `create_goal` / `get_goal` / `update_goal` |
| 任务树（目标驱动编排） | `timeline_tree` / `timeline_tasks` / `timeline_pull` / `timeline_read` |
| 模型列表 | `list_subagent_models`（provider + model 查路由可用性）；无此工具时读宿主配置文件，快照记入项目 runbook |

其他支持多智能体的环境（Claude Code / Codex 等）：按上表能力列映射到对应原语；无共享看板时由主脑在 spec「方案自审」节持有依赖表。

> 工具面随会话/权限变化，派发前以**实际工具列表**为准；`spawn_teammate`/`interrupt_agent`/`timeline_*` 非恒有。子代理无 timeline 时主脑内联快照；子代理看不到主脑后台 job 与会话日志，按「后台可见性降级」处理。

### 使用规则

- **共享看板**：≥2 个持久 teammate 并行时，用看板声明依赖（blocked_by）+ 文件写入范围（write_scopes）防互相踩文件；看板是操作层，spec 是契约层
- **作用域不相交**：并行角色的文件作用域必须不相交；相交则串行
- **teammate 复用**：同一会话内复用同一 teammate，不逐任务重建
- **等待**：主脑用等待原语等状态变化，不轮询
- **打断**：teammate 跑偏 / 卡住 → 打断重派（见失败处理表）
- **只读审查**：代码安全员/审查员/裁判员只读；报告原文附入汇报；裁判员 BLOCK 未解决不得进入下一步；主脑不得自判 PASS
- **角色按需启用**：按矩阵裁剪，选择写进 spec「方案自审」并汇报

### 实时查看（DSH Web GUI）

- 会话头部**「智能体团队」按钮**（双人图标）→ 面板：**成员**（实时状态：运行中 / 未运行 / 准备中 / 失败 + 模型）+ **任务**（只读看板）
- **点击成员行 = 打开成员会话**：在主视图打开该 teammate 自己的对话框，实时看它干活，也可直接给它发消息
- 一次性 subagent 不进成员列表：进度在主会话显示为后台任务通知，最终报告交主脑
- 代码安全员/审查员/裁判员为一次性 subagent，不进团队面板；报告由主脑转述；审查员可直接给子代理发消息（同树），裁判员 BLOCK 由主脑执行

## 失败处理与降级

| 失败 | 处理 |
|---|---|
| 模型不可用（网关故障 / 模型下线 / 会话固化） | 按「派发时模型决策」自动回退（放行候选 → 会话模型 / 主脑自做），汇报注明「模型回退」，不阻塞流程 |
| 默认模型不满足角色硬能力（如测试员需读图而默认纯文本） | 触发动态挑选：查本会话放行集合按能力过滤显式派发；无满足的放行模型 → 主脑核验截图降级 |
| 用户显式指定模型未对本会话放行 | 如实报告原因（两类报错含义）+ 替代建议，不静默换模型 |
| 代码安全员 subagent 派发失败或超时 | 主脑亲自做同样工作并注明；不得跳过安全审查 |
| 审查员（异常与偷懒审查）派发失败/超时 | 主脑内联做同样审查并注明「无独立审查」；不跳过 |
| 裁判员派发失败/超时 | 主脑**不得自判 PASS**；换新 subagent 或 `workflow`；仍失败报用户暂停进入下一步 |
| 审查员直发 `continue`/`retry_same` 失败 | 主脑转发或执行；记录「审查员直发失败」 |
| 审查员与主脑结论冲突 | 主脑决定并留痕；审查员报告原文附入汇报；规则/契约争议交裁判员 |
| 裁判员与主脑结论冲突 | 主脑可回应，不得删除裁判单；争议交用户；未解决不得进入下一步 |
| 代码安全员/审查员/裁判员越权（改文件/spec/树、直接对用户） | 报告作废，主脑记违规并重派；必要时报用户 |
| 后台不可见 / 证据缺失 | 标 `evidence_missing` 或「后台可见性：降级」，要求补齐；不得凭空 PASS/BLOCK |
| 同一检查点 BLOCK 超 2 轮 | 停止循环，报用户裁决 |
| 裁判员运行测试 / 替测试员补测 | 违规：裁判单作废；测试执行权归测试员；J3/J4 只引用测试员报告 |
| 测试员审代码 / 代码安全员不审代码 | 违规：代码审查+安全检查归代码安全员；测试员只做验收测试 |
| 无 `design.md` 未询问是否建立标准 | 违规：前端首次/新项目必须问；否则按用户经验总结并记录 |
| Playwright 未适配却声称跑过 / 无截图汇总 | 违规：浏览器测试必须真实操作+截图；环境提前适配；不可用声明降级 |
| 团队模式小改不派测试员 | 违规：形态 1–3 测试员必执行；只有主脑单干例外且必须自测 |
| 审查员无识图却假装分析图片 | 违规：报告主脑，由主脑决定临时识图子智能体；不得假装识图 |
| 审查员契约结束前被结束 / 主脑把 inactive 当结束 | 违规：审查员从签约到 PR/Step 9 常驻/可复用；inactive 必须唤醒；下游无任务才可结束 |
| PR 前释放审查员 | 违规：PR 创建/Step 9 完成前不得释放审查员 |
| 需求模糊/跳过澄清员未契约互审 | 违规：主脑+审查员+裁判员至少 1 轮互审后再向用户总结 |
| 审查员只汇总不反问 | 违规：每个子代理报告至少 1 个质疑/反问，拿到回答再总结 |
| 主脑质疑未回应 / 未解决疑问就呈现 | 违规：主脑可反向质疑；未解决不得作为最终结论给用户 |
| 测试员未交测试报告 | J3/J4 不得由裁判员补测；标 `evidence_missing`，要求测试员补报告，BLOCK 核销 |
| 审查员 5 分钟无心跳/主脑 5 分钟无审查员消息 | 主脑主动询问/唤醒审查员重试；审查员 5 分钟无主脑确认 → 再次上报/唤醒主脑；双方卡住 → 主脑换新审查员并记尝试次数 |
| 代码安全员/审查员/裁判员只回元信息 | 主脑内联并注明「无独立审查/裁判」；不把元信息当结论 |
| 单干 / mini-spec 被要求启用监督角色 | 降级内联检查表并注明；不创建角色、不派发 |
| 测试员 teammate 创建失败（provisioning / failed） | 降级为 subagent（按「派发时模型决策」挑选的模型）执行同样测试工作，注明 |
| teammate 缺工具（无终端 / 无读图） | 该角色工作改由主脑派发的 subagent 完成 |
| teammate 跑偏 / 卡住 | 主脑打断（DSH：`interrupt_agent`）重派；环境无打断能力 → 等自然结束后重派 |
| 无支持图像输入的模型 | 截图认证降级为主脑亲自核验（宿主主脑自带读图能力时直接用它），或经用户同意跳过并注明 |
| 凭记忆/印象声称"不支持图片输入"（未实测） | **违规**——必须先发探针图实测；只有实测失败才能降级，降级决定附失败证据（哪张图、什么报错）写入测试报告 |
| 代码审查 / 测试打回超 2 轮 | 停止循环，报用户决策，不带病推进 |
| 角色产出无法追溯到条款 | 主脑退回重做 |
| 目标 / 任务树原语不可用（任意宿主，含本机瞬时失败） | 降级为文字版进度表（主脑每步汇报维护），注明"任务树不可用"，流程继续 |
| 子代理无 timeline 工具 / 读取失败 | 主脑把完整任务描述内联进 prompt；内联后仍失败一次 → 主脑自己做 |
| 任务树节点超 40 | 合并叶子；合并后仍超限 → 重做树结构（属拆分过度） |
| 子代理路由报 `not allowed for this Session` | 会话白名单在创建时固化（非配置错误）→ 提示用户**新开会话**，不重复改配置 |
| 目标已存在（同一需求续做） | 复用既有目标与树，不重复 `create_goal`；先 `timeline_pull` 恢复进度 |
| 宿主无自动续轮计数（其他环境） | 降级为"主脑在每轮汇报中显式记录同一阻塞的出现次数"，并在汇报中注明"轮次口径降级"；未达 3 次不得置 `blocked`，保持 `active` |
| `paused` 超过一个阶段（如跨 Step）仍无法恢复 | 不得无限 `paused`：转 `blocked`（写明具体阻塞条件）或 `retired`（写明理由）；`paused` 只服务于"等外部输入的短期暂停" |

## 契约把控与流程优化建议

- 主脑是 spec 唯一 owner；各角色产出（代码 / 安全审查报告 / 测试报告 / 裁判单 / Step 6 五项报告）必须可追溯到 spec 条款
- **裁判员不是最终裁定者**：PASS 不替代用户验收与 `check_spec.py`；BLOCK 由主脑执行整改，争议交用户
- **测试执行权归测试员；代码审查+安全检查归代码安全员**：裁判员不执行测试/不审代码，只按测试员报告与代码安全员结论审契约；裁判单必须引用测试员报告路径/用例名与代码安全员结论
- 代码安全员/审查员/裁判员报告原文附入当步汇报；主脑可回应但不得删除/篡改
- **角色按需启用矩阵**的选择写进 spec「方案自审」；未启用项注明理由
- 主脑每步向用户汇报时可附 ≤2 条"流程优化建议"（含理由与采纳成本）
- 被采纳的建议记入项目 runbook 或本 skill 的 CHANGELOG
