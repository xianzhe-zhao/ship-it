# 项目适配：把通用流程接到真实项目上

> 这份文档回答一个问题：**装好 `ship-it` 之后，在一个具体项目里还要放什么？**

## 结论先行：默认两层，不要复制第二份流程 skill

| 层 | 放哪 | 写什么 | 谁维护 |
|---|---|---|---|
| **流程**（通用） | 全局 skill：`~/.agents/skills/ship-it`（junction 到源仓库） | 9 步的顺序、spec + 核销表 + 回滚卡、条款写法、验收与发布纪律 | 源仓库（`ship-it`） |
| **约定/红线**（项目） | 项目 `CLAUDE.md` / `AGENTS.md` | "本项目执行 ship-it 的 Step 1–9"、PR 必带内容、版本号来源、禁止事项 | 项目仓库 |
| **操作细节**（项目） | `docs/deploy-runbook.md` | 环境值、部署脚本与手动回退、部署后验证、只读回归、回滚卡、服务操作红线、常用命令 | 项目仓库 |
| **契约模板**（项目） | `docs/specs/_TEMPLATE.md` | 从 skill 的 `references/spec-template.md` 复制，按项目补"回归范围"等具体项 | 项目仓库（改动需回灌） |

这样"流程只有一份、项目值随仓库走"：任何 agent、任何机器 clone 下来都读得到，不依赖某台机器的 skill 目录。

## 为什么不要第二份流程 skill

把整套流程再写成一个项目级 skill，实际代价是：

- **两处 80% 重复**，任何一方改规则都要手动同步 → 必然漂移；
- 常见后果是**陈旧副本**（例如某份副本缺了整个周期安全审查环节），而 agent 恰好加载了它；
- 触发竞争：一句"改代码"同时命中两个流程 skill，而它们的步骤编号、PR 与用户验收的先后可能相反。

**真实案例**：某项目曾同时维护全局 skill 与 910 行的项目级 skill，最后删除项目级副本、把环境与操作细节搬进 `docs/deploy-runbook.md`，才止住漂移。迁移时还发现两个旧 worktree 里留着更早的 245 行副本 —— 这类"影子副本"最容易复发。

## 四步落地

1. **装全局 skill**（真源模式，不要复制）：

   ```powershell
   # Windows
   .\install.ps1          # 在 skill 源仓库执行；建 junction 到 ~/.agents/skills
   ```
   ```sh
   ./install.sh           # macOS / Linux；建 symlink
   ```

2. **项目约定文件**里写明流程归属，例如：

   ```markdown
   ## 开发部署流程（必须遵守）
   安全审查是周期任务（默认每月一次，高危项目每周） —— 执行全局 skill `ship-it` 的「周期安全审查」（P0 未清零不开工/不发布）
   1. 方案自审 + spec 契约 —— 同上；spec 放 `docs/specs/<日期>-<英文短名>.md`
   ……
   发布前检查清单：见本文件「发布前检查清单」与 `docs/deploy-runbook.md`
   ```

3. **`docs/deploy-runbook.md`** 只放"本项目才知道的事"：环境与端口、部署脚本与手动回退、部署后验证、只读回归命令、回滚预案卡、服务操作红线、常用运维命令。**不要复述通用流程**。

4. **`docs/specs/_TEMPLATE.md`** 从 `references/spec-template.md` 复制，把"回归范围"换成本项目的核心功能清单；在文件头写明来源与"模板级改动需回灌"，避免静默分叉。

## 现有能力盘点（Step 1.1 用）

接入一个需求前，按项目实际目录逐层查——清单通用，"去哪查"要按项目替换：

| 层 | 查什么 | 去哪查（按项目替换） |
|---|---|---|
| 页面/路由 | 是否已有相似页面或入口 | `src/router/`、`src/views/`、`app/` |
| 组件 | 弹窗/表单/表格/图表/字段 是否已有 | `src/components/` |
| 公共逻辑 | 分页/上传/轮询/请求封装/校验 | `src/composables/`、`src/lib/`、`utils/` |
| 后端接口 | 是否已有 API 可扩展 | 路由目录（`api/`、`routers/`、`*_api.py`） |
| 数据表 | 是否已有表/字段可承载 | schema 定义、迁移文件、项目文档表清单 |
| 脚本/工具 | 导出/同步/清理/备份 | `scripts/`、`tools/` |
| 依赖 | 是否已有库覆盖（图表/日期/加密/文件） | `package.json`、`requirements.txt`、`pyproject.toml` |

### 逐项替换清单（接入时照着填）

- 系统形态：有无测试/正式系统（决定 Step 3 / 7 是否执行）
- 核心功能清单：首次接入时问用户要（核心路由/接口/模块），写进 runbook，Step 3.2 分级回归的依据
- 安全审查周期：默认每月一次；高危项目（对外暴露/处理敏感数据）每周
- 服务与端口、部署脚本、健康检查地址
- 版本来源与变更记录位置（`package.json` / `CHANGELOG.md` / `docs/deploy-log.md`）
- 测试账号、测试库名、只读回归脚本路径
- 静态闸门命令（lint / build / `--check`）与测试命令
- 可重启服务白名单（哪些能重启、哪些绝对禁止批量操作）

## 编号对齐（最容易踩的坑）

项目约定文件里的步骤编号**必须与 skill 一致**，否则 agent 读到"Step 5"时无法判断你说的是"用户验收"还是"提交 PR"。

- 若项目确实要调整顺序（例如 PR 先于用户验收），**显式写出这是有意偏离**，并在每一步后面标注 `(skill Step N)`；
- 不要靠"读者自己推断"；跨文件引用一律用全名（"skill Step 5 用户验收"）。

## 保密与脱敏

- runbook 里**不写凭据**：口令/密钥写"见服务器 `.env` 的 `XXX`"；
- 示例与文档中的**内网 IP、域名、账号、服务器别名**一律用占位符（`<服务器内网IP>`、`<生产域名>`、`<测试账号>`）；
- 项目 skill / 文档若曾被提交过敏感值，删除文件不等于清除 —— 历史提交仍可检出，正确做法是**轮换凭据**并在记录里注明。

## 例外：什么时候才建项目级 skill

只有一种情况值得：**该项目有通用流程装不下的独特工序**（例如必须走内部合规审批、或有独立的硬件烧录流程），且你能保证：

- 项目 skill 只写"独特工序"，通用步骤用一句话指回全局 skill；
- 指定一个同步责任人/检查点（每次全局 skill 升级后核对一次）；
- 项目 skill 头部写明"依赖全局 skill vX.Y.Z"。

否则就用两层。

## 检查清单（新项目接入时逐条过）

- [ ] 全局 skill 已安装，且是 junction/symlink（改源仓库即时生效）
- [ ] 项目约定文件里写明"执行 ship-it"，并列出本项目超出通用流程的规则
- [ ] `docs/deploy-runbook.md` 覆盖：环境值、部署、回退、验证、回滚卡、服务红线、核心功能清单、安全审查周期
- [ ] `docs/specs/_TEMPLATE.md` 已复制并标注来源
- [ ] 步骤编号与 skill 对齐，有意偏离处已显式标注
- [ ] 文档内无凭据、无内网地址、无真实账号
- [ ] 项目里没有第二份流程 skill 副本（含 worktree、旧分支）
