# 周期安全审查 playbook

> 安全审查是**周期性任务，不按次执行**：默认**每月一次**；对外暴露面大/依赖多的项目可设为**每周一次**（周期记入项目 runbook）。
> 首次使用 / 从未审查过 → 开工前先做一次完整审查。
> 每次改动的流程内只做**增量检查**（见 1.5）。
> 返回：`SKILL.md` 的「周期安全审查」一节。

## 1.1 审查范围与触发

- **完整审查**（周期触发）：全部依赖 + 全部对外接口 + 信任边界。
- **增量审查**（流程内，Step 1 前）：自上次审查以来的新增依赖 / 新外部输入面 / 新接口。
- **事后回查**（开发完成后）：再跑一次 `npm audit`/OSV，确认新依赖没引入新告警；依赖必须进 lockfile。

## 1.2 需求/系统拆解

| 维度 | 要回答的问题 |
|---|---|
| 涉及数据 | 新增/读取/导出哪些表、字段？是否含个人信息、凭据、支付/设备数据？ |
| 涉及接口 | 新增/修改哪些 API？暴露面：公网 / 内网 / VPN / 仅本机？ |
| 身份与权限 | 是否需要登录？普通用户还是 admin？是否可能访问他人数据？ |
| 外部输入 | 用户输入、上传文件、URL 抓取、第三方 API、**LLM 输出**？ |
| 依赖变化 | 新增 npm/pip 包？升级主版本？ |
| 部署影响 | 新端口、新环境变量、DDL、进程/容器变更？ |

## 1.3 信任边界与数据流

按实际链路标出每一跳的鉴权与校验：

```
浏览器/客户端 → 网关/CDN → 服务A → 服务B → 数据库/缓存 → LLM/外部 API
```

必须标注：哪一跳做认证、哪一跳做输入校验、哪一跳会把外部内容当指令（提示注入面）、哪一跳持有 secrets。

## 1.4 联网漏洞核验（强制，不允许只凭记忆）

```bash
# npm 生态
npm audit --json
# Python 生态：OSV API，按 名称==版本 精确匹配
for p in fastapi==0.115.6 requests==2.34.2; do
  name=${p%%==*}; ver=${p##*==}
  curl -s -X POST https://api.osv.dev/v1/query -H 'Content-Type: application/json' \
    -d "{\"package\":{\"name\":\"$name\",\"ecosystem\":\"PyPI\"},\"version\":\"$ver\"}"
done
# 运行时版本
node -v && npm -v && python -V
```

再用 `web_search` / `web_fetch` 交叉核对，**必须打开官方公告 / GitHub Advisory / NVD 原文**，不能只看搜索摘要：

- `web_search`：`<组件> <版本> CVE <当前年份>`、`<库> security advisory`、`Node.js security releases`
- `web_fetch`：`https://github.com/advisories/GHSA-...`、官方安全公告、NVD

判定：

| 结论 | 条件 |
|---|---|
| **P0 阻断** | 版本在受影响区间，且漏洞可被本系统触达（RCE / 鉴权绕过 / 注入 / 用户可见 XSS） |
| P1 需缓解 | 受影响但触发条件苛刻（需 admin、需本地、仅 dev 工具），或缓解措施明确可验证 |
| P2 记录 | 仅传递依赖、仅构建期、或业务不可达 |

输出必须含：公告 URL、受影响版本区间、项目实际版本、判定理由、修复版本。

> ⚠️ **联网不可用时**：用 `npm audit` / OSV 兜底；仍不可用就标注「未联网核验」，相关组件一律 P1，
> **禁止写"已确认无漏洞"**。

## 1.5 高频风险清单（完整审查时逐项过）

| 风险 | 必查点 |
|---|---|
| XSS / HTML 注入 | 富文本、AI 输出、第三方正文是否净化（DOMPurify 等）；`v-html`/`dangerouslySetInnerHTML` 是否只接可信内容；链接 scheme 白名单 |
| 提示注入 | 外部内容（网页/文档/邮件）是否拼进 system prompt；工具调用是否受权限约束 |
| 越权（IDOR） | 新接口是否按 `user_id` 过滤；admin 接口是否走统一鉴权 |
| 密钥泄漏 | 新配置走 `.env`？是否会被前端打包进 bundle？日志是否打印 token/口令 |
| SSRF | 是否按用户输入请求 URL；是否限制内网/回环地址 |
| 文件上传/解析 | 大小/类型限制；解析库版本；落盘目录是否可执行 |
| 限速与滥用 | 登录/AI/发信接口是否限速；是否有防爆破 |
| **AI 成本预算** | 涉及 LLM/付费 API：单次与每日 token/调用上限、限流、失败重试是否放大计费 |
| 数据最小化 | 收集字段是否必要；日志/导出是否脱敏 |
| 依赖引入 | 维护活跃度、许可证、包体积；锁版本进 lockfile |
| 暴露面 | 新端口是否绑 `127.0.0.1`；是否意外暴露公网 |

## 1.6 输出：审查日志条目

每次审查（完整/增量）在 `docs/security-review-log.md` 追加一条（入 git）：

```markdown
## YYYY-MM-DD 安全审查（完整 / 增量）
- 范围：<全部依赖 / 增量：新增依赖清单>
- 联网核验：✅ 已核验（npm audit + OSV + 官方公告）/ ⚠️ 未联网（降级）
- 受影响组件：<组件@版本 → 公告 URL → 判定>
- P0 阻断：无 / <列表 + 修复方案>
- P1 缓解：<措施 + 验证方式>
- P2 已知：<记录>
- 结论：✅ 通过 / ⛔ P0 未清零，相关功能不开工/不发布
```

**P0 规则**：发现 P0 → 相关功能未清零不开工/不发布；新增依赖命中已知 P0 → 禁用。

**流程内增量检查（Step 1 前，1 分钟）**：距上次审查有无新增依赖/新外部输入面？
有 → 按 1.4 只核验增量部分，结论写进 spec「方案自审」节；无 → PR 里一行声明"自上次审查（YYYY-MM-DD）无新增攻击面"。
